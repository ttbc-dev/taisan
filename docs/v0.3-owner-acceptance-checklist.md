# v0.3 owner-run real-Worker acceptance checklist

This checklist is executed by the owner (or an operator the owner
designates) on a real installation running a **real conforming
Worker** — an executable that implements the
`taisan.worker.declaration/1`, `taisan.worker.request/2`, and
`taisan.worker.report/2` surface — bound through the `github` host
adapter on **one** isolated repository. It prepares instructions only
until the owner records authorization: absent that authorization no
live Issue is created, no credential is installed, no live model is
run, and no live host effect is performed.

Record every result in the
[owner-run evidence template](v0.3-evidence-template.md). Label each
row **automated fixture/contract evidence** or **owner-run live
evidence**. An owner-run live row is never marked passed from a
fixture or contract result — including the fixture-Worker transcripts
quoted in the
[installation guide](v0.3-installation.md), which are automated
evidence only.

## Roles and record locations

| Role | Responsibility |
| --- | --- |
| `owner` | Authorizes the run, selects the repository and Issues, designates the operator, approves the evidence, performs or delegates the real PR review. |
| `operator` | Runs the commands, captures times and outputs, fills the evidence template, operates the host review surface. |
| `worker` | The real conforming Worker under test; never an author of evidence — its reports are claims the supervisor validates. |

Record locations: `CFG` = sanitized `config.toml` **and** the
sanitized installation record (`store.config.json` beside `--db`, or
the `--config` path); `STATE` = the installation state directory
(`store.db`, `bodies/`, `workspaces/`); `JSON` = retained command
envelopes; `WIRE` = the per-Invocation `request.json`, `report.json`,
and `describe` output captured from the Worker's out directories;
`RUNS` = the durable scheduled-intake run records (`intake_runs` rows
in `store.db`, or the retained intake-run capture when one is taken);
`HOST` = the real branch, change request, review, and check references
on the source host; `TEMPLATE` = the owner-run evidence record.

## Preconditions

| # | Who | Check | Expected |
| --- | --- | --- | --- |
| 0.1 | owner | One dedicated, isolated repository is selected for the cutover; the legacy operator system's admission for that repository is identified and frozen per the [installation guide](v0.3-installation.md#one-repository-cutover-and-rollback). | No second system can admit or dispatch Work for the repository. |
| 0.2 | owner | A real conforming Worker is selected and its `describe` output is captured **before** installation. | `format_version` present; `protocol_versions` includes `taisan.worker.request/2` and `taisan.worker.report/2`; the intended roles are declared; `resume` is `unsupported`. |
| 0.3 | operator | Profile and installation record are written per the [installation guide](v0.3-installation.md); credentials are `env:`/`file:`/`command:` references only; `worker_dispatch` names the real `source_path`, budgets, `invariant_set`, and capability floor. | No secret value in `CFG`, `JSON`, `WIRE`, logs, or evidence. |
| 0.4 | operator | `taisan check` passes end-to-end; `taisan check --probe` is **not** part of the gate — its `probe_capabilities` stage fails closed `capability.unknown` because no probe backend is wired. | Ordered per-stage pass recorded. |
| 0.5 | operator | Intake starts with `enabled = false`. | No scheduled admission before scenario S-1. |
| 0.6 | owner | The live authorization — scope (one repository, bounded duration), Issues, Worker identity, credential scope, evidence retention, expiration, and the designated operator — is recorded **before** the first live command. | Timestamped authorization reference precedes 1.1. |
| 0.7 | owner | The publish-path capability gate produces real evidence. The in-process `github` driver records a `CapabilityReport` on each source pass — `support` from the adapter's declared operation surface, `authorization` from the credential's repository permission read, `unknown` when unconfirmed ([#355](https://github.com/shimpeiws/taisan/issues/355)). | The first `taisan run` pass records one report; publish intents appear only for `supported` + `authorized` capabilities; a denied or `unknown` entry blocks the corresponding intent visibly. If the owner's credential lacks write permission, publish-dependent rows (M-3 onward) are `unexercised` with that recorded reason — never bypassed. |

## Manual scenarios — one Work through the full Worker lifecycle

Submit one Work bound to one real eligible Issue and drive it with
`taisan run` (intake disabled). Every step's durable evidence is
inspected with `work-detail`, `work-list`, `attention`, and `capacity`.

### M-1 — real coding

| # | Who | Action | Expected result | Record |
| --- | --- | --- | --- | --- |
| 1.1 | operator | Submit Work for the selected Issue with the intended constraints and verification argv. | `accepted`; one Work, one queued Execution; `command-result` replay of the idempotency key returns the same decision. | `JSON`, `HOST` |
| 1.2 | operator | Start `taisan run`; let dispatch admission bind the immutable `taisan.worker.request/2` body and launch the real Worker through the recorded argv under the recorded isolation profile and credential reference. | One Coding Invocation reaches `Done`; the Worker wrote exactly one `report.json`; `describe` output matches the request's stored binding field-for-field. | `WIRE`, `STATE`, `JSON` |
| 1.3 | operator | Inspect `work-detail`: artifact presence/digest, process evidence, verification results. | Artifact `Present` with a recorded digest; `VerificationResult` rows come from the supervisor runner — never from Worker-claimed checks; `claimed_head`/`claimed_checks` are claims, not facts. | `JSON` |
| 1.4 | operator | Confirm the Worker produced local commits in the managed workspace and the handoff recorded them. | Handoff artifact resolves to the produced revision; no remote effect yet. | `JSON`, `STATE` |

| 2.2 | operator | Inspect the report and the recorded exit evidence. | The report's `invariant_items` are claims only; the durable gate requires a `Done` Invocation **and** a proven process exit code `0`. A non-zero or unverifiable exit does not open the publish gate. | `JSON`, `WIRE` |

### M-8 — stop, restart, and recovery

| # | Who | Action | Expected result | Record |
| --- | --- | --- | --- | --- |
| 8.1 | operator | Stop `taisan run` (SIGINT/SIGTERM) mid-lifecycle — preferably while a Worker Invocation is in flight or intents are outstanding — then restart against the same `--db` and record. | Durable identities survive; dispatch re-attaches by recorded identity; no second writer for the same Execution; no reused out directory; no duplicate host effect. | `JSON`, `STATE` |
| 8.2 | operator | Inspect `work-detail` and `capacity` after restart. | Unknown liveness/stop/effect outcomes stay `unknown`/`uncertain` with ownership retained until inspected evidence resolves them; an unproven writer keeps its slot and reservations. | `JSON` |
| 8.3 | operator | If a transport failure occurs during the run, observe the retry path. | Retries are bounded by the Work's durable counter across restart and successor Executions; a definite failure re-issues under backoff; authorization verdicts are terminal and pause for an operator decision. | `JSON` |

### M-9 — Attention

| # | Who | Action | Expected result | Record |
| --- | --- | --- | --- | --- |
| 9.1 | operator | Inspect `attention` at each human-gate point (paused Execution, unsupported/authorization-blocked effect, unreconciled unknown). | Each Attention is evidence-backed and names the decision needed; `attention` output is consistent with `work-detail`. | `JSON` |
| 9.2 | operator | Acknowledge/resolve an Attention through the command surface where the scenario produces one. | The acknowledgement is a durable command; the Attention clears only on resolved evidence, never on timeout. | `JSON` |

## Scheduler scenarios — v0.2 internal scheduling, two distinct Works

These exercise the unchanged v0.2 intake machinery on the v0.3
Worker path: one manually submitted Work and one scheduled-intake
Work, both running real Workers.

| # | Who | Action | Expected result | Record |
| --- | --- | --- | --- | --- |
| S-1 | operator | With intake `enabled = false`, submit Work A manually and let it run. | Work A advances through the M-series lifecycle independently; no intake run is created. | `JSON`, `RUNS`, `HOST` |
| S-2 | operator | Enable intake while `taisan run` is live; wait for the settings tick and the next interval grid point. | One scheduled run at the interval; the selector admits at most one Work per eligible source; the admitted Work B is distinct from Work A. | `RUNS`, `JSON`, `HOST` |
| S-3 | operator | Let both Works progress concurrently within `capacity`. | Two distinct Executions, two distinct Workspaces/branches, two independent Worker Invocations; capacity accounting is correct; neither Work's evidence satisfies the other's gates. | `JSON`, `HOST` |
| S-4 | operator | Verify no duplicate dispatch with the legacy operator system. | The legacy system admitted nothing for the repository during the run (frozen at cutover step 1); exactly one Work exists per source across both systems; no Work was dispatched by both. | `HOST`, `TEMPLATE` |
| S-5 | operator | Restart `taisan run` with intake enabled and a scheduled run due or in flight. | The live/uncertain run reconciles by durable owner evidence; no catch-up burst; missed periods collapse to the next future grid point. | `RUNS`, `JSON` |
| S-6 | operator | Disable intake (`enabled = false`) and observe the settings tick. | The pending due is cancelled; an in-flight run completes under its captured settings; existing Work is unaffected. | `RUNS`, `JSON` |

## Success, Attention, and recovery expectations

| Condition | Expected |
| --- | --- |
| Success path | Every Invocation `Done` with validated report evidence; artifacts digest-bound; host intents `Applied` with receipts; completion assessment sees exact current-target evidence; terminal Outcome recorded. |
| Attention | Human-gate conditions (paused Execution, authorization/unsupported verdict, unreconciled `unknown` effect, capacity hold) surface as evidence-backed Attention items — never silent stalls, never auto-resolved. |
| Recovery | Stop/restart preserves durable identity; retries bounded by durable counters; unknown outcomes stay `unknown` until inspected evidence resolves them; an unproven writer retains ownership and resources. |
| Fail-closed | Missing/malformed/stale/mismatched evidence produces a typed refusal or bounded failure — never a silent pass, never a fabricated declaration, never a degraded fixture fallback. |

## Evidence to retain

Per the [evidence template](v0.3-evidence-template.md), retain:

- **Exact versions**: tested `taisan` revision and binary version
  output; the Worker's `describe` output (`adapter`,
  `adapter_version`, `runtime.product`/`runtime.version`,
  `protocol_versions`, `roles`, `capabilities`, `resume`);
  `contract_version` from the installation record.
- **Exact configuration identity**: sanitized `config.toml` and
  `store.config.json` — `worker_argv`, `worker_isolation_profile`,
  `worker_dispatch` (source_path, budgets, invariant_set id+revision,
  capability floor), credential **reference names** only, host binding
  (`host_instance`, `repository` stable id, `adapter`), `capacity`,
  `workspace_root`, intake settings.
- **Durable identities**: Work/Execution/Invocation ids; request and
  report digests; artifact digests; action intent ids and receipts;
  round/judgment ids; command ids and idempotency keys; run ids.
- **Observed results**: per-scenario expected-vs-observed with UTC
  timestamps and retained JSON envelopes.

## Disable, drain, and rollback

- **Safe disable**: follow the drain procedure in the
  [installation guide](v0.3-installation.md#safe-disable-and-drain) —
  stop admission, finish or stop in-flight Invocations with verified
  stop proof, reconcile intents/reservations, then change bindings.
  Config changes apply only to unbound requests.
- **Rollback criteria**: any Worker contract violation that cannot be
  bounded, a containment or egress escape, unreconciled `unknown`
  host effects, duplicate dispatch with the legacy system, or an owner
  decision to revert triggers the
  [rollback procedure](v0.3-installation.md#rollback). A fixture or
  contract pass never waives a criterion.
- **Duplicate dispatch**: at no point may the legacy operator system
  and the v0.3 installation both admit or dispatch Work for the cutover
  repository. Scenario S-4 verifies this explicitly.

## Failure handling

- A failing precondition stops the run; record it and do not proceed
  to a live row.
- A scenario may be marked `unexercised` with a reason; it is never
  marked passed by implication. Publish-dependent rows blocked by a
  denied or `unknown` capability authorization ([#355](https://github.com/shimpeiws/taisan/issues/355))
  are `unexercised`, not `fail`.
- A fixture/contract result cited alongside a live row is supplemental
  only.
- Any credential appearing in a retained surface is an incident: stop,
  redact the record, and rotate the credential before continuing.
