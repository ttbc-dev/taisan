# v0.3: Executable Worker request and report contract

Status: **design only, normative target for a future v0.3 unit**. This
document reconciles the Worker design in
[worker protocol](worker-protocol.md) with the actual narrow
`WorkerRequest` export, the `execution` supervisor, and the independent
contract Worker at the exact revision below. It publishes a
provider-neutral, versioned request/report wire contract and records the
open owner decisions that must be settled before any dependent runtime
implementation. It authorizes no runtime change, credential change,
dependency, store migration, live execution, publication, or Work
completion, and it does not depend on v0.2 acceptance.

The design baseline is taisan `main` at
`51f0b34daf33a1975a39b7614f5ceeac7dabf431`. The checkout used for this
inventory is that commit; the local `origin/main` reference also resolves
to it. No overlapping pull request was available in the offline
checkout, so every dependent implementation unit must recheck current
`main` and overlapping PRs before it starts. The baseline revision is an
evidence locator, not a claim that this document was exercised at that
revision.

## 1. Scope, claims, and evidence boundary

This is a public, provider-neutral contract. It names no private source
repository, private implementation, private URL, or private symbol. A
Worker is any process that executes one bounded Invocation through the
approved transport; a "reference adapter" below means only the first
conforming adapter behind the same boundary.

The contract reuses existing U1–U8/v0.2 behavior and evidence where it
is already safe. It does not create a parallel control plane or weaken a
previously approved guard; a mismatch between an approved default and
the implementation is recorded as a gap and an owner decision.

The inventory in section 2 is derived from source and tests at the
baseline. "Actual" means the behavior the code can currently exercise.
"Designed" means the target stated in the Worker design. A closed
fixture issue, a retained fixture record, or a contract test is evidence
for the narrow behavior it exercises only. It is never evidence of live
integration, a real coding-agent runtime, namespace isolation, egress
enforcement, a live four-role Worker, publication, or Work completion.

At the baseline there is live evidence for the authorized isolated S1
scenario through a scenario bridge and a deterministic scenario shim,
but that evidence does not exercise this v0.3 executable request/report
transport, a real coding-agent runtime, four distinct Worker roles, or
the namespace/egress profile. Those remain unclaimed gaps.

## 3. Common wire rules

### 3.1 JSON, canonicalization, and digests

- Every body is UTF-8 JSON with string object keys. Unknown fields at any
  level are refused, not ignored, unless this document names the field
  as extensible.
- Canonical bytes are produced by recursively sorting object keys,
  emitting arrays in order, no insignificant whitespace, and the
  primitive encoding used by `canonical_json`
  (`workloop-core/src/domain.rs:77`).
- `request_digest` is SHA-256 over the tag `worker-request-v2`, one
  ASCII colon, and the canonical bytes of the request object **with the
  `request_digest` member omitted**. `report_digest` uses tag
  `worker-report-v2` and omits only `report_digest`. No other field is
  omitted or normalized.
- Hex is lowercase, exactly 64 characters. Timestamps are integer Unix
  seconds. Durations are integer seconds. Byte sizes are integer bytes.
- `format_version` is a closed string, never a range. A reader that does
  not know the exact value refuses; it never guesses, downgrades, or
  partially parses.

### 3.2 Identities

| Identity | Owner and exact meaning |
| --- | --- |
| `request_id` | Core/supervisor durable dispatch identity of one attempt, `<execution_id>:inv:<sequence>` (`domain.rs:690`). Immutable once the request row exists. |
| `invocation_id` | Supervisor identity for the one spawned process tree, allocated in the consume commit (`supervisor.rs:1155`). One request produces at most one Invocation. |
| `request_digest` | Supervisor-produced SHA-256 of the exact request body, excluding its own member. Stored with the export/invocation binding. |
| `report_digest` | Worker-produced SHA-256 of the exact report body, excluding its own member. Never used to decide success without the envelope checks below. |
| `capability_digest` | Supervisor-produced digest of the exact `describe` declaration surface (`adapter.rs:60`). |
| `manifest_digest` | Supervisor-produced digest of the canonical artifact manifest (`handoff.rs:598`). |
| `environment_digest` | Supervisor-produced digest of the exact verification argv, produced commit, and ref (`handoff.rs:790`). |

The same `request_id` never names a second execution attempt. A retry,
re-run, or continuation is a new `request_id` and a new `invocation_id`.
`invocation_id` is never reused, including after its record is terminal. A report is valid only for the
pair `(request_id, invocation_id)` and the exact `request_digest`; it is
not transferable to another attempt.

## 4. Executable request `taisan.worker.request/2`

### 4.1 Transport

For v2 the approved transport is `argv-v2`:

```text
<worker_argv...> describe
<worker_argv...> run --request /taisan/request.json --out /taisan/out
```

- `describe` is effect-free and must not read the workspace as an input
  or write outside its bounded stdout. It is run in its own process
  group with a bounded wait; a wedged probe is killed with its group.
- `run` receives exactly one request file and one fresh out directory.
  The request file is a read-only bind; the out directory is read-write
  and belongs to exactly one Invocation. The workspace is read-write
  only for `coding` and `fix`, and read-only for `invariant_check` and
  `review`.
- A Worker that cannot implement this exact argv must not be selected
  for a v2 request. No shell expansion, shell fallback, stdin protocol,
  or "equivalent" transport is allowed for v2 without an owner decision
  (OD-1). The existing fixture/contract Worker modes are test harnesses,
  not an approved v2 transport.
- The supervisor validates the request file's digest before spawn and
  requires the Worker not to mutate it. The Worker writes at most
  `report.json`, `runtime.log`, and `checkpoint.json` into the out
  directory; anything else in the out directory is not evidence.

### 4.2 Envelope and task bodies

A request has these top-level members. The `task` body is exactly one of
the four variants below; `role` and `task.kind` must agree.

```json
{
  "format_version": "taisan.worker.request/2",
  "request_id": "e-7:inv:2",
  "invocation_id": "inv-41",
  "request_digest": "<64 lowercase hex>",
  "store_id": "store-1",
  "work_id": "w-7",
  "execution_id": "e-7",
  "role": "coding",
  "repository": {"host": "host-1", "repository": "repo-a"},
  "base": {"repository": {"host": "host-1", "repository": "repo-a"}, "object": "<40 lowercase hex>"},
  "spec": {"revision": 3, "digest": "<64 lowercase hex>"},
  "workspace": {"workspace_id": "ws-w-7", "mount": "/workspace", "read_only": false},
  "budget": {
    "deadline_unix_seconds": 1800000600,
    "max_runtime_seconds": 1800,
    "max_turns": 200,
    "max_report_bytes": 1048576,
    "max_log_bytes": 33554432,
    "max_verification_commands": 8,
    "max_continuation_refs": 4
  },
  "required_capabilities": {
    "role": "coding",
    "protocol_versions": ["taisan.worker.request/2"],
    "capabilities": ["invocation_transport.argv-v2", "report_json", "workspace_write", "process_control"],
    "resume": "unsupported",
    "verification_egress_hosts": []
  },
  "continuation": [],
  "task": {}
}
```

`task.kind` selects one of the following. All referenced bodies are
immutable and content-addressed. `digest` means SHA-256 over the exact
retained bytes (tagged by the body's own type). `order` is the group
order and is significant; readers never sort it.

```json
{"kind": "coding",
 "goal": {"ref": "goal-7", "media_type": "text/markdown", "bytes": 812, "digest": "<64 hex>"},

   {"order": 0,

    "source_revision": "9",
    "snapshot_digest": "<64 hex>",
    "body": {"ref": "issue-17-v9", "bytes": 2048, "digest": "<64 hex>"}}
 ],
 "constraints": ["Do not change public API names"],
 "verification_argv": [["cargo", "test", "-p", "workloop-core"]]}
```

```json
{"kind": "fix",
 "goal": {"ref": "goal-7-fix-1", "media_type": "text/markdown", "bytes": 640, "digest": "<64 hex>"},
 "issues": [
   {"order": 0,
    "issue": {"host": "host-1", "repository": "repo-a", "issue": "17"},
    "source_revision": "9",
    "snapshot_digest": "<64 hex>",
    "body": {"ref": "issue-17-v9", "bytes": 2048, "digest": "<64 hex>"}}
 ],
 "predecessor": {"artifact_id": "inv-39/artifact.json", "manifest_digest": "<64 hex>", "produced": "<40 hex>"},
 "origin": {"kind": "review",
            "target": {"change": "change-5", "base": "<40 hex>", "head": "<40 hex>", "diff_digest": "<64 hex>"},
            "round": "round-3",
            "judgment": "judgment-9",
            "findings": [
              {"occurrence": "occ-2", "source": "review-source-3", "digest": "<64 hex>", "order": 0}
            ]},
 "constraints": ["Address only the selected finding"],

```

For a pre-publication correction, `origin` is
`{"kind":"prepublication","failed_evidence":[{"evidence_id":"verify-12","kind":"verification","digest":"<64 hex>"}]}`.
It never fabricates a change-request identity. A review-origin Fix binds

```json
{"kind": "invariant_check",
 "artifact": {"artifact_id": "inv-39/artifact.json", "manifest_digest": "<64 hex>", "produced": "<40 hex>"},
 "invariant_set": {"id": "invariants-core", "revision": 4, "digest": "<64 hex>"}}
```

```json
{"kind": "code_review",
 "target": {"change": "change-5", "base": "<40 hex>", "head": "<40 hex>", "diff_digest": "<64 hex>"},
 "review_source": {"source": "review-source-3", "bytes": 4096, "digest": "<64 hex>", "source_revision": "3"}}
```

Continuation is an ordered list of previously retained bodies, never a
runtime session:

```json
{"continuation": [
  {"kind": "workspace_commit", "id": "work/w-7", "commit": "<40 hex>", "required": true},
  {"kind": "artifact", "id": "inv-39/artifact.json", "digest": "<64 hex>", "required": true},
  {"kind": "report", "id": "inv-39/report.json", "digest": "<64 hex>", "required": false}
]}
```

`required: true` means the body must be present and match before
dispatch. `required: false` is retained context and an absent body is
recorded as unavailable context, not silently omitted. The list is
bounded by `budget.max_continuation_refs`.

### 4.3 Dispatch preconditions and refusal

Missing, stale, or undeliverable required bodies refuse dispatch. The
refusal happens before any process exists and is recorded as a typed
`dispatch_refused` fact against the request. A refused request is
terminal for its own `request_id`; the work needs a new Core-authorized
request, not a silent retry under the same identity.

| Role | Required body | Freshness/exactness check | Refusal code |
| --- | --- | --- | --- |
| Coding | goal, every ordered Issue snapshot, constraints, verification argv, base commit, spec | Body digest resolves; ordered snapshot set equals the approved spec source set in order; each `source_revision` and body digest equal the spec snapshot; base object is present and is the workspace's start; spec digest equals the approved revision | `request.snapshot_missing`, `request.snapshot_stale`, `request.base_unavailable`, `request.spec_mismatch` |
| Fix (pre-publication) | goal, ordered Issue snapshots, predecessor artifact, failed evidence, base/spec | Predecessor row is acknowledged and its ref resolves to `produced`; every failed-evidence digest resolves; spec and base match | `request.artifact_unavailable`, `request.evidence_missing`, `request.evidence_stale` |
| Fix (review) | goal, ordered Issue snapshots, predecessor artifact, target, round, judgment, selected finding occurrences | Target equals the sealed judgment target; round is immutable and unreleased; every selected occurrence belongs to that judgment and sealed snapshot; head is the current accepted head; predecessor is acknowledged | `request.head_stale`, `request.finding_missing`, `request.judgment_stale`, `request.artifact_unavailable` |
| InvariantCheck | exact artifact, invariant set, spec | Artifact is acknowledged and resolves to `produced`; set revision/digest equals the approved set; spec digest matches | `request.artifact_unavailable`, `request.invariant_set_missing`, `request.invariant_set_stale` |
| CodeReview | exact target, materialized review source | Target head equals the current accepted head and base/change match; source snapshot is retained, digest matches, and source revision is the requested one | `request.head_stale`, `request.review_source_unavailable`, `request.review_source_stale` |
| All | continuation entries marked `required` | Each named body exists and matches its digest/commit | `request.continuation_missing` |

A body is never fetched by the Worker. An adapter that tries to fetch
remote review input or rewrite a snapshot is invalid, not "helpful".
A missing optional continuation body is recorded as unavailable and
cannot satisfy a later gate by itself.

## 5. Declaration and version negotiation

### 5.1 `describe` output

The v2 declaration has a closed envelope and is checked before request
binding and again before launch:

```json
{
  "format_version": "taisan.worker.declaration/1",
  "adapter": "example-adapter",
  "adapter_version": "1.0.0",
  "runtime": {"product": "example-runtime", "version": "4.2.0"},
  "protocol_versions": ["taisan.worker.request/2", "taisan.worker.report/2"],
  "roles": ["coding", "fix", "invariant_check", "review"],
  "capabilities": ["invocation_transport.argv-v2", "report_json", "workspace_write", "workspace_read_only", "process_control"],
  "resume": "unsupported",
  "checkpoints": "workspace_commits",
  "runtime_artifact_store": null,
  "local_retries": "runtime_internal"
}
```

The declaration is still effect-free and fail-closed. A probe that is
refused, times out, exits non-zero, is unparseable, has no adapter id, or
has no exact `format_version` is `adapter.declaration_unavailable`; no
synthetic declaration is compared, bound, or dispatched.

### 5.2 Exact negotiation

- A v2 request requires the declaration's `protocol_versions` to contain
  **both** `taisan.worker.request/2` and `taisan.worker.report/2`, and
  the declaration's `roles` to contain the request `role`.
- `required_capabilities.capabilities` must be a subset of the declared
  capabilities. A missing one is `capability.missing` naming the exact
  capability.
- The request `role` must equal `task.kind`'s role mapping
  (`coding`→`coding`, `fix`→`fix`, `invariant_check`→`invariant_check`,
  `code_review`→`review`). A mismatch is `adapter.role_mismatch`.
- `resume` must equal `unsupported` for v2. A Worker declaring resume
  support is not selected for v2 unless a later owner decision adds a
  resume contract; the current continuation contract is new work, not
  runtime session resume.
- Version lists are sets for digest purposes but are compared exactly
  for negotiation. Order in the list never selects a version. An
  unknown version, a missing required version, or a declaration that
  offers only a different major version refuses; there is no
  best-effort parse.
- A declaration that differs from the request's stored binding by any
  field is a configuration repair: `adapter.identity_mismatch`,
  `adapter.version_mismatch`, `runtime.version_mismatch`, or
  `capability.digest_mismatch`. It authorizes no start and is terminal
  for that request's binding. A legitimate upgrade is a new request
  that binds the new declaration.

## 6. Report `taisan.worker.report/2`

### 6.1 Envelope and classes

A report is a single JSON object in `/taisan/out/report.json`, at most
`budget.max_report_bytes` bytes. It echoes the exact identity and request
digest. The Worker-authored `status` is one of `success`, `negative`,
`unavailable`, `refused`, `limit_reached`, or `failed`. The supervisor
classifies the envelope as one of `success`, `negative`, `unavailable`,
`failure`, `invalid`, or `absent`:

| Classification | Who can produce it | Meaning |
| --- | --- | --- |
| `success` | Worker `status: success`, then supervisor validation | A valid positive claim for this exact request. It is still only evidence. |
| `negative` | Worker `status: negative`, then supervisor validation | A valid negative result: failed declared checks, invariant violations, or review findings. It is not success and not a publication. |
| `unavailable` | Worker `status: unavailable`, or supervisor finding a declared required input/body unavailable | The Worker or a required body was unavailable. It cannot be counted as a negative result or as absence of findings. |
| `failure` | Worker `status: refused`, `limit_reached`, or `failed`, then supervisor validation | A typed failure with a closed reason. No automatic outer retry is authorized by the report. |
| `invalid` | Supervisor only | The report exists but is malformed, oversized, wrong version/identity/role/digest, or has unknown fields/reasons. Retained with its exact reason; never parsed leniently. |
| `absent` | Supervisor only | No report after confirmed exit, within the bounded recovery rule. Not an empty success and not "zero findings". |

A report from another `request_id`, `invocation_id`, role, or
`request_digest` is `invalid` and cannot be adopted. A report whose
`report_digest` does not match is `invalid`. A missing report is
`absent`; it never becomes a report with empty fields.

### 6.2 Reason codes

`reason.code` is a closed provider-neutral set. Provider prose belongs
only in the bounded `runtime.log`, never in a reason field, Command
result, Attention text, or report digest input that escapes the log.

| Status | Allowed reason codes |
| --- | --- |
| `success` | `completed` |
| `negative` | `checks_failed`, `invariant_violated`, `findings_reported` |
| `unavailable` | `provider_unavailable`, `auth_unavailable`, `missing_required_input` |
| `refused` | `provider_refused` |
| `limit_reached` | `deadline_reached`, `max_turns_reached`, `output_limit_reached` |
| `failed` | `invalid_request`, `unsupported_role`, `internal_error` |

Supervisor-only invalid reasons are `report.malformed`,
`report.oversize`, `report.wrong_version`, `report.wrong_request`,
`report.wrong_invocation`, `report.wrong_role`, `report.digest_mismatch`,
and `report.unknown_field`. Supervisor-only absent reason is
`report.absent`.

### 6.3 Body

```json
{
  "format_version": "taisan.worker.report/2",
  "request_id": "e-7:inv:2",
  "invocation_id": "inv-41",
  "request_digest": "<64 hex>",
  "report_digest": "<64 hex>",
  "role": "coding",
  "status": "success",
  "reason": {"code": "completed"},
  "claimed_head": "<40 hex>",
  "claimed_checks": [
    {"argv": ["cargo", "test", "-p", "workloop-core"], "exit_code": 0, "output_digest": "<64 hex>", "status": "passed"}
  ],
  "findings": [],
  "invariant_items": [],
  "continuation": {"workspace_commit": "<40 hex>", "report_refs": []},
  "runtime_usage": {"turns": 42, "elapsed_ms": 12345, "runtime_product": "example-runtime"},
  "log": {"path": "runtime.log", "bytes": 4096, "truncated": false, "digest": "<64 hex>"}
}
```

- `claimed_head` is a claim only. The handoff decides the produced
  artifact. A claim that differs from the handed-off commit is retained
  as an invalid claim, never used to move the artifact.
- `claimed_checks` are claims. Only a supervisor `VerificationResult`
  on the exact artifact/argv/commit can satisfy a mechanical
  requirement. Provider text is not a check result.
- `findings` are claims for one `code_review` source, bound to the exact
  target/source digest. They cannot settle a newer head.
- `invariant_items` are claims for the exact invariant set; coverage,
  validity, and disposition belong to the evidence gates.
- `runtime_usage` is bounded and optional. It never carries credentials
  or unbounded provider prose.
- `log` describes the bounded log body. A truncated log is retained and
  marked truncated; the missing tail is not reconstructed.

### 6.4 Bounds and termination

The supervisor enforces the effective bound before paying the cost:
report size before JSON parsing, log size while copying, deadline before
each child wait, and output caps before reading a tail. A report over
`max_report_bytes` is `invalid` (`report.oversize`) and is not parsed.
A log over `max_log_bytes` is truncated and marked truncated. A
deadline or max-turn stop stops the process tree; a produced commit may
still be handed off, but no report is fabricated. The out directory is
never reused, and an absent report is recovered only within the existing
bounded recovery policy.

Worker completion is evidence, never publication or Work completion. A
success report still requires stop proof, durable handoff, supervisor
verification, any enabled gates, and reconciliation of required host
effects before Core may record an Outcome. A Worker cannot request a
retry, change Work state, publish, or waive a guard; any such output is
ignored and recorded as invalid.

## 8. One owner per field and per decision

| Field or decision | Sole owner | Other parties may | Must never |
| --- | --- | --- | --- |
| `request_id`, `execution_id`, `work_id` | Core/supervisor | Echo them exactly | Mint, rewrite, or reuse for another attempt |
| `role`, `task.kind`, task references | Core | Read and echo | Let the adapter choose or widen the task |
| `base`, `spec` revision/digest | Core | Read | Accept a Worker-supplied replacement |
| Ordered Issue snapshot set and order | Core/spec admission | Render/materialize | Sort, deduplicate, or substitute a fresher snapshot silently |
| `budget` and deadline | Core/supervisor | Observe and stop at the bound | Extend, reset, or ignore |
| `required_capabilities` | Core/supervisor | Declare support | Claim a capability it does not implement |
| Adapter declaration and capability digest | Adapter, checked by supervisor | Declare | Be synthesized by the supervisor |
| Request body bytes and `request_digest` | Supervisor | Read | Be edited by the Worker; be recomputed under a new tag |
| Workspace mount and out directory | Supervisor | Use as granted | Let the Worker choose another path or reuse an out directory |
| `claimed_head`, `claimed_checks`, `findings`, `invariant_items` | Worker | Claim with exact refs | Be treated as the artifact, a passing check, or a settled judgment |
| `report_digest` | Worker | Produce | Authorize success without supervisor envelope validation |
| Report classification (`invalid`/`absent`) | Supervisor | Record | Be speculated by the Worker or Core |
| Artifact `produced`, `manifest_digest`, handoff ref | Supervisor/Core | Read | Be copied from Worker prose |
| `VerificationResult` | Supervisor | Read | Be supplied by the Worker as a passing result |
| Publication and host effects | Core + repository host adapter | Observe | Be performed or retried by the Worker |
| Work state, retry, Outcome, completion | Core | Observe | Be changed by a Worker report or adapter |
| Isolation profile and enforcement | Installation/supervisor | Declare the recorded profile | Be silently downgraded or replaced by hygiene alone |

## 9. Versioning and cutover

### 9.1 Immutable history

The existing narrow export (`taisan.worker.request/1`, digest tag
`worker-request-v1`) remains readable and immutable. Its stored
`digest`, `request_id` (`worker:<invocation_id>`), `profile_id`,
`workspace_root`, state, and launch binding are never recomputed,
rewritten, or upgraded in place. Historical `InvocationRequest` rows,
first adapter bindings, artifact handoffs, verification results,
observations, and Outcomes are likewise untouched.

### 9.2 Cutover rules

| Situation | Rule |
| --- | --- |
| New request after v0.3 cutover | Created as `taisan.worker.request/2`; a new attempt gets a new `request_id`/`invocation_id`; no dual write and no synthesis of a v1 export for it |
| Historical v1 export already acknowledged or terminal | Read-only historical evidence; never re-digested or migrated |
| In-flight request created before cutover and not yet launched, with no v2 body | Not silently upgraded. It either completes under its recorded legacy behavior if the bound adapter still supports it, or is abandoned with `request.version_unsupported` and the work is re-issued as a new v2 request |
| In-flight legacy request whose body/version is unknown or unparseable | Refuse with `request.version_unknown`; terminal for that request; no fallback parse, no downgrade, no re-binding |
| Adapter declares only v2, request is legacy | `request.version_unsupported`; no start; abandon and re-issue |
| Adapter declares only v1, request is v2 | `request.version_unsupported`; no start; no downgrade |
| Store migration | Additive only: new nullable columns or tables keyed by request/invocation. No row rewrite of digests, bindings, or evidence. The exact next store format number is a dependent implementation decision; it is not claimed here |
| Rollback | Stop creating v2 requests; existing v2 rows remain readable. Never convert a v2 request to v1 or reuse a v1 digest tag for v2 bytes |

A request's format is fixed at creation. A supervisor restart reads the
recorded format; it never infers a format from the current
configuration. A configuration change affects only requests not yet
bound, exactly as the existing adapter-binding rule already requires.

### 9.3 Verification of history

A v2 reader may validate a v1 export only by its recorded v1 digest and
schema. It must not re-canonicalize a v1 row under v2 rules, compare a
v2 digest to a v1 digest, or treat a missing v2 body on a v1 request as
"absent v2 report". Historical evidence remains evidence for the
behavior it actually exercised, no more.

## 12. Design aspects and remaining limits

| Aspect | Application and remaining limit |
| --- | --- |
| State transitions | Request creation → dispatch preflight → bound declaration → spawn → report ingest → stop proof → handoff → verification. A refusal is terminal for its request; a retry/re-run is a new request/invocation, never a mutation of the same one. Existing Execution states are unchanged. |
| Failure semantics | `invalid` and `absent` are distinct from a valid `negative` result and from `unavailable`. A partial report/log or a timed-out runner leaves retained evidence and authorization for nothing further; no conclusion is drawn from absence beyond the recorded reason. |
| Trust boundaries | The Worker and all source/review text are untrusted. Core owns references, budgets, and decisions; the supervisor owns process, out directory, handoff, and verification; only the host adapter publishes. The model channel remains outside this contract's protection. |
| Identity invariants | Request/invocation identity is unique per attempt; report is bound to both plus the request digest; artifact identity is the handoff manifest; review identity is the sealed target/source triple; finding identity is the exact occurrence in a sealed judgment. |
| Information preservation | Invalid/absent evidence, WIP, claims, logs, and version mismatches are retained with honest flags. v1 history is never rewritten. Missing bodies are marked unavailable, never fabricated. |
| Resource bounds | Report and log caps before parse/copy, deadline and max-turn before each wait, verification per-command timeout/output caps, bounded recovery attempts, and continuation/ref limits. The implemented verification values remain a recorded gap until OD-6 is settled; they are not silently redefined here. |

## 13. Non-claims

This document does not claim that the v2 transport, report ingestion,
role/capability negotiation, cutover, read-only review workspace,
namespace isolation, egress proxy, preflight, or live four-role Worker
exist. It does not claim that a fixture/contract pass is a live
integration. It does not authorize runtime implementation, credentials,
automation, live execution, publication, or Work completion. The
implementation units that follow must retain their own tested commit,
sanitized configuration, named scenarios, and actual results, and must
recheck current `main` and overlapping PRs before starting.
