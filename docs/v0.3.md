## 1. Scope, claims, and evidence boundary

This is a public, provider-neutral contract. It names no private source
repository, private implementation, private URL, or private symbol. A
Worker is any process that executes one bounded Invocation through the
approved transport; a "reference adapter" below means only the first
conforming adapter behind the same boundary.

The contract reuses existing U1–U8/v0.2 behavior and evidence where it
is already safe. It does not create a parallel control plane or weaken a
previously approved guard; a mismatch between an approved default and
the implementation is recorded as a gap and an owner decision.

The inventory in section 2 is derived from source and tests at the
baseline. "Actual" means the behavior the code can currently exercise.
"Designed" means the target stated in the Worker design. A closed
fixture issue, a retained fixture record, or a contract test is evidence
for the narrow behavior it exercises only. It is never evidence of live
integration, a real coding-agent runtime, namespace isolation, egress
enforcement, a live four-role Worker, publication, or Work completion.

At the baseline there is live evidence for the authorized isolated S1
scenario through a scenario bridge and a deterministic scenario shim,
but that evidence does not exercise this v0.3 executable request/report
transport, a real coding-agent runtime, four distinct Worker roles, or
the namespace/egress profile. Those remain unclaimed gaps.

## 3. Common wire rules

### 3.1 JSON, canonicalization, and digests

- Every body is UTF-8 JSON with string object keys. Unknown fields at any
  level are refused, not ignored, unless this document names the field
  as extensible.
- Canonical bytes are produced by recursively sorting object keys,
  emitting arrays in order, no insignificant whitespace, and the
  primitive encoding used by `canonical_json`
  (`workloop-core/src/domain.rs:77`).
- `request_digest` is SHA-256 over the tag `worker-request-v2`, one
  ASCII colon, and the canonical bytes of the request object **with the
  `request_digest` member omitted**. `report_digest` uses tag
  `worker-report-v2` and omits only `report_digest`. No other field is
  omitted or normalized.
- Hex is lowercase, exactly 64 characters. Timestamps are integer Unix
  seconds. Durations are integer seconds. Byte sizes are integer bytes.
- `format_version` is a closed string, never a range. A reader that does
  not know the exact value refuses; it never guesses, downgrades, or
  partially parses.

### 3.2 Identities

| Identity | Owner and exact meaning |
| --- | --- |
| `request_id` | Core/supervisor durable dispatch identity of one attempt, `<execution_id>:inv:<sequence>` (`domain.rs:690`). Immutable once the request row exists. |
| `invocation_id` | Supervisor identity for the one spawned process tree, allocated in the consume commit (`supervisor.rs:1155`). One request produces at most one Invocation. |
| `request_digest` | Supervisor-produced SHA-256 of the exact request body, excluding its own member. Stored with the export/invocation binding. |
| `report_digest` | Worker-produced SHA-256 of the exact report body, excluding its own member. Never used to decide success without the envelope checks below. |
| `capability_digest` | Supervisor-produced digest of the exact `describe` declaration surface (`adapter.rs:60`). |
| `manifest_digest` | Supervisor-produced digest of the canonical artifact manifest (`handoff.rs:598`). |
| `environment_digest` | Supervisor-produced digest of the exact verification argv, produced commit, and ref (`handoff.rs:790`). |

The same `request_id` never names a second execution attempt. A retry,
re-run, or continuation is a new `request_id` and a new `invocation_id`.
`invocation_id` is never reused, including after its record is terminal. A report is valid only for the
pair `(request_id, invocation_id)` and the exact `request_digest`; it is
not transferable to another attempt.

## 4. Executable request `taisan.worker.request/2`

### 4.1 Transport

For v2 the approved transport is `argv-v2`:

```text
<worker_argv...> describe
<worker_argv...> run --request /taisan/request.json --out /taisan/out
```

- `describe` is effect-free and must not read the workspace as an input
  or write outside its bounded stdout. It is run in its own process
  group with a bounded wait; a wedged probe is killed with its group.
- `run` receives exactly one request file and one fresh out directory.
  The request file is a read-only bind; the out directory is read-write
  and belongs to exactly one Invocation. The workspace is read-write
  only for `coding` and `fix`, and read-only for `invariant_check` and
  `review`.
- A Worker that cannot implement this exact argv must not be selected
  for a v2 request. No shell expansion, shell fallback, stdin protocol,
  or "equivalent" transport is allowed for v2 without an owner decision
  (OD-1). The existing fixture/contract Worker modes are test harnesses,
  not an approved v2 transport.
- The supervisor validates the request file's digest before spawn and
  requires the Worker not to mutate it. The Worker writes at most
  `report.json`, `runtime.log`, and `checkpoint.json` into the out
  directory; anything else in the out directory is not evidence.

### 4.2 Envelope and task bodies

A request has these top-level members. The `task` body is exactly one of
the four variants below; `role` and `task.kind` must agree.

```json

  "request_id": "e-7:inv:2",
  "invocation_id": "inv-41",
  "request_digest": "<64 lowercase hex>",
  "store_id": "store-1",
  "work_id": "w-7",
  "execution_id": "e-7",
  "role": "coding",
  "repository": {"host": "host-1", "repository": "repo-a"},
  "base": {"repository": {"host": "host-1", "repository": "repo-a"}, "object": "<40 lowercase hex>"},
  "spec": {"revision": 3, "digest": "<64 lowercase hex>"},
  "workspace": {"workspace_id": "ws-w-7", "mount": "/workspace", "read_only": false},
  "budget": {
    "deadline_unix_seconds": 1800000600,
    "max_runtime_seconds": 1800,
    "max_turns": 200,
    "max_report_bytes": 1048576,
    "max_log_bytes": 33554432,
    "max_verification_commands": 8,
    "max_continuation_refs": 4
  },
  "required_capabilities": {
    "role": "coding",
    "protocol_versions": ["taisan.worker.request/2"],
    "capabilities": ["invocation_transport.argv-v2", "report_json", "workspace_write", "process_control"],
    "resume": "unsupported",
    "verification_egress_hosts": []

  "continuation": [],
  "task": {}

```

`task.kind` selects one of the following. All referenced bodies are
immutable and content-addressed. `digest` means SHA-256 over the exact

```json
{"kind": "coding",

 "constraints": ["Do not change public API names"],

```

```json
{"kind": "fix",
 "goal": {"ref": "goal-7-fix-1", "media_type": "text/markdown", "bytes": 640, "digest": "<64 hex>"},
 "issues": [
   {"order": 0,
    "issue": {"host": "host-1", "repository": "repo-a", "issue": "17"},
    "source_revision": "9",
    "snapshot_digest": "<64 hex>",
    "body": {"ref": "issue-17-v9", "bytes": 2048, "digest": "<64 hex>"}}
 ],
 "predecessor": {"artifact_id": "inv-39/artifact.json", "manifest_digest": "<64 hex>", "produced": "<40 hex>"},
 "origin": {"kind": "review",
            "target": {"change": "change-5", "base": "<40 hex>", "head": "<40 hex>", "diff_digest": "<64 hex>"},
```

```json
 "artifact": {"artifact_id": "inv-39/artifact.json", "manifest_digest": "<64 hex>", "produced": "<40 hex>"},

```


Continuation is an ordered list of previously retained bodies, never a
runtime session:

```json
{"continuation": [
  {"kind": "workspace_commit", "id": "work/w-7", "commit": "<40 hex>", "required": true},
  {"kind": "artifact", "id": "inv-39/artifact.json", "digest": "<64 hex>", "required": true},
  {"kind": "report", "id": "inv-39/report.json", "digest": "<64 hex>", "required": false}
]}
```

`required: true` means the body must be present and match before
dispatch. `required: false` is retained context and an absent body is
recorded as unavailable context, not silently omitted. The list is
bounded by `budget.max_continuation_refs`.

### 4.3 Dispatch preconditions and refusal

Missing, stale, or undeliverable required bodies refuse dispatch. The
refusal happens before any process exists and is recorded as a typed
`dispatch_refused` fact against the request. A refused request is
terminal for its own `request_id`; the work needs a new Core-authorized
request, not a silent retry under the same identity.

| Role | Required body | Freshness/exactness check | Refusal code |
| --- | --- | --- | --- |
| Coding | goal, every ordered Issue snapshot, constraints, verification argv, base commit, spec | Body digest resolves; ordered snapshot set equals the approved spec source set in order; each `source_revision` and body digest equal the spec snapshot; base object is present and is the workspace's start; spec digest equals the approved revision | `request.snapshot_missing`, `request.snapshot_stale`, `request.base_unavailable`, `request.spec_mismatch` |
| Fix (pre-publication) | goal, ordered Issue snapshots, predecessor artifact, failed evidence, base/spec | Predecessor row is acknowledged and its ref resolves to `produced`; every failed-evidence digest resolves; spec and base match | `request.artifact_unavailable`, `request.evidence_missing`, `request.evidence_stale` |
| Fix (review) | goal, ordered Issue snapshots, predecessor artifact, target, round, judgment, selected finding occurrences | Target equals the sealed judgment target; round is immutable and unreleased; every selected occurrence belongs to that judgment and sealed snapshot; head is the current accepted head; predecessor is acknowledged | `request.head_stale`, `request.finding_missing`, `request.judgment_stale`, `request.artifact_unavailable` |
| InvariantCheck | exact artifact, invariant set, spec | Artifact is acknowledged and resolves to `produced`; set revision/digest equals the approved set; spec digest matches | `request.artifact_unavailable`, `request.invariant_set_missing`, `request.invariant_set_stale` |
| CodeReview | exact target, materialized review source | Target head equals the current accepted head and base/change match; source snapshot is retained, digest matches, and source revision is the requested one | `request.head_stale`, `request.review_source_unavailable`, `request.review_source_stale` |
| All | continuation entries marked `required` | Each named body exists and matches its digest/commit | `request.continuation_missing` |

A body is never fetched by the Worker. An adapter that tries to fetch
remote review input or rewrite a snapshot is invalid, not "helpful".
A missing optional continuation body is recorded as unavailable and
cannot satisfy a later gate by itself.

## 5. Declaration and version negotiation

### 5.1 `describe` output

The v2 declaration has a closed envelope and is checked before request
binding and again before launch:

```json
{
  "format_version": "taisan.worker.declaration/1",
  "adapter": "example-adapter",
  "adapter_version": "1.0.0",
  "runtime": {"product": "example-runtime", "version": "4.2.0"},
  "protocol_versions": ["taisan.worker.request/2", "taisan.worker.report/2"],
  "roles": ["coding", "fix", "invariant_check", "review"],
  "capabilities": ["invocation_transport.argv-v2", "report_json", "workspace_write", "workspace_read_only", "process_control"],
  "resume": "unsupported",
  "checkpoints": "workspace_commits",
  "runtime_artifact_store": null,
  "local_retries": "runtime_internal"
}
```

The declaration is still effect-free and fail-closed. A probe that is
refused, times out, exits non-zero, is unparseable, has no adapter id, or
has no exact `format_version` is `adapter.declaration_unavailable`; no
synthetic declaration is compared, bound, or dispatched.

### 5.2 Exact negotiation

- A v2 request requires the declaration's `protocol_versions` to contain
  **both** `taisan.worker.request/2` and `taisan.worker.report/2`, and
  the declaration's `roles` to contain the request `role`.
- `required_capabilities.capabilities` must be a subset of the declared
  capabilities. A missing one is `capability.missing` naming the exact
  capability.
- The request `role` must equal `task.kind`'s role mapping
  (`coding`→`coding`, `fix`→`fix`, `invariant_check`→`invariant_check`,
  `code_review`→`review`). A mismatch is `adapter.role_mismatch`.
- `resume` must equal `unsupported` for v2. A Worker declaring resume
  support is not selected for v2 unless a later owner decision adds a
  resume contract; the current continuation contract is new work, not
  runtime session resume.
- Version lists are sets for digest purposes but are compared exactly
  for negotiation. Order in the list never selects a version. An
  unknown version, a missing required version, or a declaration that
  offers only a different major version refuses; there is no
  best-effort parse.
- A declaration that differs from the request's stored binding by any
  field is a configuration repair: `adapter.identity_mismatch`,
  `adapter.version_mismatch`, `runtime.version_mismatch`, or
  `capability.digest_mismatch`. It authorizes no start and is terminal
  for that request's binding. A legitimate upgrade is a new request
  that binds the new declaration.

## 6. Report `taisan.worker.report/2`

### 6.1 Envelope and classes

A report is a single JSON object in `/taisan/out/report.json`, at most
`budget.max_report_bytes` bytes. It echoes the exact identity and request
digest. The Worker-authored `status` is one of `success`, `negative`,
`unavailable`, `refused`, `limit_reached`, or `failed`. The supervisor
classifies the envelope as one of `success`, `negative`, `unavailable`,
`failure`, `invalid`, or `absent`:

| Classification | Who can produce it | Meaning |
| --- | --- | --- |
| `success` | Worker `status: success`, then supervisor validation | A valid positive claim for this exact request. It is still only evidence. |
| `negative` | Worker `status: negative`, then supervisor validation | A valid negative result: failed declared checks, invariant violations, or review findings. It is not success and not a publication. |
| `unavailable` | Worker `status: unavailable`, or supervisor finding a declared required input/body unavailable | The Worker or a required body was unavailable. It cannot be counted as a negative result or as absence of findings. |
| `failure` | Worker `status: refused`, `limit_reached`, or `failed`, then supervisor validation | A typed failure with a closed reason. No automatic outer retry is authorized by the report. |
| `invalid` | Supervisor only | The report exists but is malformed, oversized, wrong version/identity/role/digest, has unknown fields/reasons, or its path is unsafe (not a regular file inside the Invocation-owned out directory — a symlink or other non-file entry is never followed). Retained with its exact reason; never parsed leniently. |
| `absent` | Supervisor only | No report after confirmed exit, within the bounded recovery rule. Not an empty success and not "zero findings". |

A report from another `request_id`, `invocation_id`, role, or
`request_digest` is `invalid` and cannot be adopted. The report `role`
must equal the request `role` exactly; a report that names the right
identity and digest but a different role is still
`invalid` (`report.wrong_role`), because the role selects the task body
and the report schema. A report whose `report_digest` does not match is
`invalid`. A missing report is `absent`; it never becomes a report with
empty fields.

### 6.2 Reason codes

`reason.code` is a closed provider-neutral set. Provider prose belongs
only in the bounded `runtime.log`, never in a reason field, Command
result, Attention text, or report digest input that escapes the log.

| Status | Allowed reason codes |
| --- | --- |
| `success` | `completed` |
| `negative` | `checks_failed`, `invariant_violated`, `findings_reported` |
| `unavailable` | `provider_unavailable`, `auth_unavailable`, `missing_required_input` |
| `refused` | `provider_refused` |
| `limit_reached` | `deadline_reached`, `max_turns_reached`, `output_limit_reached` |
| `failed` | `invalid_request`, `unsupported_role`, `internal_error` |

Supervisor-only invalid reasons are `report.malformed`,
`report.oversize`, `report.wrong_version`, `report.wrong_request`,
`report.wrong_invocation`, `report.wrong_role`, `report.digest_mismatch`,
`report.unknown_field`, `report.unsafe_path`, and
`report.unreadable` (the out directory stat or the report open/read
failed on the worker-owned surface — classified like the unsafe case,
never an infrastructure fault; an unreadable `runtime.log` is auxiliary
evidence and simply records no `log` body). Supervisor-only absent reason is
`report.absent`.

```json
{
  "format_version": "taisan.worker.report/2",
  "request_id": "e-7:inv:2",
  "invocation_id": "inv-41",
  "request_digest": "<64 hex>",
  "report_digest": "<64 hex>",
  "role": "coding",
  "status": "success",
  "reason": {"code": "completed"},
  "claimed_head": "<40 hex>",
  "claimed_checks": [
    {"argv": ["cargo", "test", "-p", "workloop-core"], "exit_code": 0, "output_digest": "<64 hex>", "status": "passed"}
  ],
  "findings": [],
  "invariant_items": [],
  "continuation": {"workspace_commit": "<40 hex>", "report_refs": []},
  "runtime_usage": {"turns": 42, "elapsed_ms": 12345, "runtime_product": "example-runtime"},
  "log": {"path": "runtime.log", "bytes": 4096, "truncated": false, "digest": "<64 hex>"}

```

- `claimed_head` is a claim only. The handoff decides the produced
  artifact. A claim that differs from the handed-off commit is retained
  as an invalid claim, never used to move the artifact.
- `claimed_checks` are claims. Only a supervisor `VerificationResult`
  on the exact artifact/argv/commit can satisfy a mechanical
  requirement. Provider text is not a check result.
- `findings` are claims for one `code_review` source, bound to the exact
  target/source digest. They cannot settle a newer head.
- `invariant_items` are claims for the exact invariant set; coverage,
  validity, and disposition belong to the evidence gates.
- `runtime_usage` is bounded and optional. It never carries credentials
  or unbounded provider prose.
- `log` describes the bounded log body. A truncated log is retained and
  marked truncated; the missing tail is not reconstructed.

### 6.4 Bounds and termination

The supervisor enforces the effective bound before paying the cost:
report size before JSON parsing, log size while copying, deadline before
each child wait, and output caps before reading a tail. A report over
`max_report_bytes` is `invalid` (`report.oversize`) and is not parsed.
A log over `max_log_bytes` is truncated and marked truncated. A
deadline or max-turn stop stops the process tree; a produced commit may
still be handed off, but no report is fabricated. The out directory is
never reused, and an absent report is recovered only within the existing
bounded recovery policy.

Worker completion is evidence, never publication or Work completion. A
success report still requires stop proof, durable handoff, supervisor
verification, any enabled gates, and reconciliation of required host
effects before Core may record an Outcome. A Worker cannot request a
retry, change Work state, publish, or waive a guard; any such output is
ignored and recorded as invalid.

## 9. Versioning and cutover

### 9.1 Immutable history

The existing narrow export (`taisan.worker.request/1`, digest tag
`worker-request-v1`) remains readable and immutable. Its stored
`digest`, `request_id` (`worker:<invocation_id>`), `profile_id`,
`workspace_root`, state, and launch binding are never recomputed,
rewritten, or upgraded in place. Historical `InvocationRequest` rows,
first adapter bindings, artifact handoffs, verification results,
observations, and Outcomes are likewise untouched.

### 9.2 Cutover rules

| Situation | Rule |
| --- | --- |
| New request after v0.3 cutover | Created as `taisan.worker.request/2`; a new attempt gets a new `request_id`/`invocation_id`; no dual write and no synthesis of a v1 export for it |
| Historical v1 export already acknowledged or terminal | Read-only historical evidence; never re-digested or migrated |
| In-flight request created before cutover and not yet launched, with no v2 body | Not silently upgraded. It either completes under its recorded legacy behavior if the bound adapter still supports it, or is abandoned with `request.version_unsupported` and the work is re-issued as a new v2 request |
| In-flight legacy request whose body/version is unknown or unparseable | Refuse with `request.version_unknown`; terminal for that request; no fallback parse, no downgrade, no re-binding |
| Adapter declares only v2, request is legacy | `request.version_unsupported`; no start; abandon and re-issue |
| Adapter declares only v1, request is v2 | `request.version_unsupported`; no start; no downgrade |
| Store migration | Additive only: new nullable columns or tables keyed by request/invocation. No row rewrite of digests, bindings, or evidence. The exact next store format number is a dependent implementation decision; it is not claimed here |
| Rollback | Stop creating v2 requests; existing v2 rows remain readable. Never convert a v2 request to v1 or reuse a v1 digest tag for v2 bytes |

A request's format is fixed at creation. A supervisor restart reads the
recorded format; it never infers a format from the current
configuration. A configuration change affects only requests not yet
bound, exactly as the existing adapter-binding rule already requires.

### 9.3 Verification of history

A v2 reader may validate a v1 export only by its recorded v1 digest and
schema. It must not re-canonicalize a v1 row under v2 rules, compare a
v2 digest to a v1 digest, or treat a missing v2 body on a v1 request as
"absent v2 report". Historical evidence remains evidence for the
behavior it actually exercised, no more.

## 12. Design aspects and remaining limits

| Aspect | Application and remaining limit |
| --- | --- |
| State transitions | Request creation → dispatch preflight → bound declaration → spawn → report ingest → stop proof → handoff → verification. | Failure semantics | `invalid` and `absent` are distinct from a valid `negative` result and from `unavailable`. A partial report/log or a timed-out runner leaves retained evidence and authorization for nothing further; no conclusion is drawn from absence beyond the recorded reason. |
| Trust boundaries | The Worker and all source/review text are untrusted. Core owns references, budgets, and decisions; the supervisor owns process, out directory, handoff, and verification; only the host adapter publishes. The model channel remains outside this contract's protection. |

| Information preservation | Invalid/absent evidence, WIP, claims, logs, and version mismatches are retained with honest flags. v1 history is never rewritten. Missing bodies are marked unavailable, never fabricated. |
| Resource bounds | Report and log caps before parse/copy, deadline and max-turn before each wait, verification per-command timeout/output caps, bounded recovery attempts, and continuation/ref limits. ### 14.3 Runtime mount, credential, and provider-config delivery

The sandbox is built by the supervisor, never by the runtime. The
mount set is fixed by the approved profile; an installation may choose
paths only where this section names a configurable source.

| Path in the sandbox | Mode | Owner and contents |
| --- | --- | --- |
| System directories the runtime and toolchain need | read-only | Host system; no owner home, other workspaces, store, handoff repository, or installation config |
| `/workspace` | read-write for `coding`/`fix`; read-only for `invariant_check`/`review` | The managed workspace; the only writable source tree for a writer |
| `/taisan/out` | read-write | Fresh, per-Invocation, never reused; `report.json`, `runtime.log`, optional `checkpoint.json`, and assessment scratch |
| `/taisan/request.json` | read-only bind | Supervisor-written canonical request; digest checked before spawn |
| `/taisan/runtime-auth` | read-only bind of exactly one file, when the runtime credential resolves to a file | The selected runtime credential only; never a repository-host credential, token helper, SSH socket, or keyring |
| `/taisan/provider-config` | read-only bind | Non-secret provider configuration rendered by the supervisor: model identity, endpoint host, turn/output limits, and an empty MCP configuration. It contains no credential value and cannot be replaced from `/workspace` |
| `/taisan/toolchain` (verification only) | read-only bind | Pinned host toolchain and read-only dependency caches; separate from the Worker sandbox |

Delivery rules:

- The runtime credential is resolved once at the supervisor boundary
  from the installation's `[worker].credential_ref` (never from the
  workspace). It is injected as a single allowlisted environment
  variable or a read-only file. Its value never enters argv, the request
  body, `runtime.log`, the report, evidence, or the provider config; a
  missing or unresolvable credential is an environment repair and
  refuses dispatch.
- Provider configuration is authored by the installation, not by the
  Worker. The supervisor renders it from validated configuration and
  mounts it read-only with a digest recorded in the launch environment
  identity. A workspace file that tries to shadow the endpoint, model,
  or credential is ignored; it is untrusted input, not configuration.
- The environment remains an allowlist. `HOME`, `TMPDIR`, and the git
  config are generated inside the sandbox; host credential paths,
  `SSH_AUTH_SOCK`, keyring sockets, repository-host tokens, and a
  credential helper are absent. The Worker's git transport stays local-only; verification
  egress is governed separately in §14.5.
- The mount set is the same for `describe` and `run`, except that
  `describe` does not receive a writable workspace or out directory and
  must answer within its bounded probe.
- No runtime-internal sandbox flag counts as enforcement. The
  supervisor's mount, PID, and network namespaces are the boundary.

### 14.4 Model-API egress

The v0.3 profile is network-denied except for the model API:

- The sandbox is created with `--unshare-net`; only loopback exists
  inside it.
- A taisan-owned CONNECT proxy outside the sandbox listens on a Unix
  socket bind-mounted into the sandbox. The runtime sees it as
  `HTTPS_PROXY` through an in-sandbox relay.
- The proxy accepts CONNECT only to the exact configured model-API host
  names on port 443, resolves DNS itself, and rejects every other
  destination. TLS is not inspected. Allowed and denied destinations
  are retained as bounded evidence.
- All four roles (`coding`, `fix`, `invariant_check`, `review`) use the
  same model-API-only proxy. Read-only assessment roles need model
  access too.
- The repository host, package registries, source hosts, arbitrary
  addresses, and the verification allowlist are not reachable through
  the Worker proxy.
- Proxy failure is an environment repair after stop proof. It is never
  a reason to switch to `--share-net`, hygiene-only execution, or an
  unrestricted network.

`[worker.egress].model_api_hosts` is a non-empty list of bare host
names for schema revision 2. It is disjoint from the repository host
endpoint and from the verification allowlist; a wildcard, URL, port,
or empty entry is a load error, never a wildcard grant.

### 14.5 Verification toolchain, dependency setup, and host allowlist

Verification is a supervisor effect, not a Worker Invocation and not a
second control plane.

- **Toolchain.** The host installs the pinned compiler/test toolchain
  before the loop starts. The supervisor binds the toolchain and a
  dependency cache read-only into the verification sandbox. The setup
  preflight must execute a trivial command with the resolved toolchain
  inside the profile; the read-only `check` only resolves the configured
  path and recorded version in existence. A missing toolchain is a
  preflight failure, not a download during verification.
- **Dependencies.** Dependency caches are prepared before the run by a
  trusted setup step under the declared allowlist and pinned by digest.
  Verification itself never installs from an open network. A command
  that needs an undeclared package host fails; opening the network is
  never an automatic fallback.
- **Inputs and scratch.** Each declared argv runs in an independent
  detached worktree of the exact handed-off commit. Tracked inputs are
  read-only; per-command writable scratch is separate and cannot shadow
  tracked paths. Verification carries no runtime credential, no Worker
  out directory, and no model-API proxy.
- **Egress.** Denied by default. The effective set is the
  installation-level `[verification.egress].allowlist` plus the Work's
  immutable `required_capabilities.verification_egress_hosts` declared
  at admission. It is enforced through the same CONNECT-only mechanism,
  exact bare host names on port 443, with DNS resolved by the proxy.
  It never contains a model-API host. The effective host set and
  toolchain/cache digests are part of the recorded environment
  identity.
- **Bounds.** The v2 target is the previously approved 30-minute
  per-command timeout and 8 MiB captured output, bounded by the
  Execution deadline. Report/log caps remain 1 MiB/32 MiB. A timeout
  or signal-killed runner is `Inconclusive`, never `Passed` and never a
  fabricated exit code. A bound already spent returns `Inconclusive`
  before enforcement resolution, toolchain/cache hashing, or worktree
  maintenance. Because no environment ran, that evidence carries the
  dedicated bound marker `bound-marker-v1:deadline:<64 lowercase hex>`
  — a digest over the canonical `{"kind":"deadline"}` under the
  `verification-bound-marker-v1` tag — instead of an
  `environment_digest`; the prefix keeps it structurally distinct from
  a real 64-hex environment identity. The implemented 300 s/64 KiB
  values are a recorded v1 gap (OD-6); a v2 implementation that keeps
  them must obtain an explicit re-approval and must not describe them
  as the approved profile.

### 14.6 Managed process lifecycle and assessment outputs

One Invocation is exactly one supervisor-owned process tree:

1. The supervisor prepares the scratch, validates the request digest,
   records the launch intent, and spawns the shim as the process-group
   leader inside the mount/PID/network profile.
2. The shim starts the runtime as its child. Runtime-internal servers
   (for example an MCP or language server) are descendants of the same
   tree, not separate Invocations. They inherit the same sandbox and
   die with the PID namespace init.
3. `stdout` and `stderr` are stream-copied into the bounded
   `runtime.log` (32 MiB cap, truncation recorded). Child-server output
   uses the same total log cap and cannot block the parent on a full
   pipe. The worker profile's per-stream `stdout`/`stderr` caps are
   truncation points under this same shared cap, never additional
   budgets that could total 64 MiB. `report.json` is capped at 1 MiB
   before parsing. Files in `/taisan/out` other than the named report,
   log, and checkpoint are not evidence.
4. Assessment roles (`invariant_check`, `review`) receive a read-only
   `/workspace`; their only writable assessment scratch is inside
   `/taisan/out`. The v1 snapshot copy remains a defence-in-depth
   substitute until the read-only bind lands, but it is not claimed as
   the mount enforcement.
5. Stop (v0.3 target): persist the stop intent and a descendant
   snapshot before any signal; re-verify every `pid + start time`;
   SIGTERM the group, wait the 10 s grace, SIGKILL the group; inspect
   every recorded identity and the namespace init as stopped; reap what
   the supervisor spawned. The rechecked baseline stop path sends
   SIGKILL directly without the SIGTERM stage or grace wait; adding them
   is part of this mapping. A child runtime server that ignores SIGTERM
   is covered by the group and namespace kill. Stop is never inferred
   from a closed proxy connection, an empty log, or exit of only the
   shim leader.
6. Restart: the next supervisor pass reads recorded request,
   Invocation, process identity, out directory, and binding. It
   re-attaches to a live or unproven writer; it never spawns a second
   writer, reuses the out directory, or adopts a child server from a
   dead runtime. Uncertainty retains the slot, reservations, and
   workspace until inspected stop proof.
7. Bounds are checked before the cost is paid: deadline before each
   child wait, report size before parsing, log size while copying,
   output caps before reading a tail, and stop grace before escalation.
   Continuation and retry never reset a bound.

### 14.7 Production host-driver binding and composition

**Decision (OP-6): the v0.3 production host driver is in-process
inside `taisan run`.** The loop holds the single run lease and composes
one `RepositoryHostPort` implementation from configuration. It does
not spawn a separate host-control process, and it does not treat the
scenario bridge as a production adapter.

Why in-process: the existing port already separates `ingest` from
`apply_outbox`; the execution loop already owns the outbox phase, the
tick deadline, and the run lease; credentials resolve at the adapter
boundary. A separate host process would add a second scheduling and
credential boundary without solving a single-host problem, and would
risk two writers. The scenario bridge remains a test/evidence harness
only; an installation that names a non-production adapter must fail
closed, not silently skip source refresh and host phases as the
current fixture-only composition does.

Configuration and binding:

| Concern | Owner and rule |
| --- | --- |
| Adapter identity and version | `[hosts.<instance>].adapter`, `endpoint`, `contract_version`; the installation record carries the same binding. A new Work binds the configuration current at acceptance; an existing Work keeps its recorded host/repository/adapter/contract/actor binding |
| Driver mode | `[host_driver].mode`; schema revision 2 accepts exactly `in_process` for v0.3. A missing key with a v1 profile keeps the historical behavior; an unknown or `separate` value is a load error, not a silent fallback |
| Credential roles | The existing `publication`, `review`, and `discussion` roles bind `(actor, credential_ref)`; the Worker has no repository-host credential. A same-actor renewal is permitted; a different actor applies to new Work only, and unresolved effects reconcile under the original actor |
| Sources | Each pass polls the declared allowlisted `use = "source"`/`publication` repositories for the active Works; there is no webhook ingress. The per-source timeout is 30 s and the pass cadence is 30 s by default. Delivery IDs deduplicate per `(host instance, adapter source, event id)`, with a per-subject discriminator for shared state such as a target branch; missing/unavailable is distinct from empty |
| Polling reads | Read-only: issue content/revision, branch head, change-request head/state, named checks, reviews/findings. A missing required source holds the dependent Work; it never becomes an empty result or a dispatch |
| Bounded outbox | At most 8 effect attempts per tick and at most 16 reconciliation items per tick; each action has its own durable ID and receipt; a partial push/comment/review chain keeps independent receipts |
| Original-action reconciliation | Reconcile unknown effects by the recorded action ID, payload digest, repository/branch/change identity, produced revision, and original actor binding. Read-back first, then apply remaining pending items only when the read did not resolve them. An unread surface stays `unknown`; it never authorizes blind replay, re-attribution, or a new write from the reconciliation path |
| Head guards | `push_ref` uses the absent/exact-prior-ref and fast-forward guard; head-bound updates/comments re-read immediately before writing and re-observe after. A moved head aborts, records a fresh head observation, and returns judgment to Core |
| Restart | The driver is stateless across restart except for durable actions and observations. A restart reconstructs outbox work from the store, reconciles under original bindings, and never restarts from in-memory PR numbering |

The scenario bridge is not a required component of this profile. If a
future owner decision adds a separately driven adapter, it must expose
the same `RepositoryHostPort` semantics, preserve the original action
and actor binding, and be explicitly selected; v0.3 does not assume it.

### 14.8 Compatibility and cutover

The v0.3 operational profile is additive. A later request may use the
new configuration; a request that started under an earlier binding
keeps it.

| Situation | Rule |
| --- | --- |
| Existing `schema_version = 1` profile | Loads and behaves exactly as recorded. It does not gain v2 enforcement and must not be described as namespace- or egress-enforced |
| New v2 request after cutover | Requires the v2 operational profile and the in-process production host driver. A profile that cannot satisfy preflight refuses dispatch; there is no hygiene-only or unrestricted-network fallback |
| Running or recorded v1 request | Keeps its recorded request format, adapter/declaration binding, host/repository/actor/credential binding, worker argv, isolation profile id, out directory, and budgets. Config reload cannot retarget it |
| Unbound request created before cutover | Not silently upgraded. It either completes under its recorded legacy behavior if that adapter is still available, or is abandoned with a typed version/configuration reason; the work is re-issued as a new v2 request |
| Changed operational configuration | Applies only to requests not yet bound. Mounts, credential delivery, egress hosts, toolchain, and host driver are fixed per bound request; changing them never rewrites a running Invocation |
| Malformed/incomplete v2 profile | Load or preflight refuses before dispatch. No partially enforced profile, no fallback to the matching v1 keys, and no synthetic provider config |
| Rollback | Stop creating v2 requests; existing v2 rows remain readable. Never convert v2 to v1, reuse a v1 digest tag for v2 bytes, or move a running Invocation to another profile/driver. A v2 request whose profile is removed is abandoned with a repair reason and re-issued |
| Store/history | No row rewrite of request digests, bindings, handoffs, verification results, receipts, or Outcomes. Any migration is additive and keyed by request/invocation |

The exact schema revision number and store format number remain
dependent implementation decisions. Whatever number is chosen, the
binding rule is fixed: format and profile are read from the recorded
request, never inferred from current configuration.

### 14.10 Design aspects

| Aspect | Application and remaining limit |
| --- | --- |
| State transitions | Preflight → bound profile → launch → child runtime tree → reported exit → inspected stop → handoff → verification → outbox reconciliation. A refused preflight never creates a process; restart re-enters from recorded identity; a config change affects only unbound requests |
| Failure semantics | Missing enforcement, proxy failure, toolchain failure, credential failure, and partial remote effects are typed and fail closed. `unknown`/`unavailable` never become success, a stop, or permission to replay; v1 history keeps its honest enforcement label |
| Trust boundaries | Workspace, issue/review text, child servers, and provider config supplied by the workspace are untrusted. The supervisor owns mounts, credentials, process, out dir, and verification; Core owns references and decisions; only the in-process host driver writes remotely under the original actor binding |
| Identity invariants | One request produces at most one Invocation; one Invocation owns one out dir and one process tree; the adapter/declaration binding, action ID, head, artifact manifest, and verification environment digest are immutable per recorded subject |
| Information preservation | Truncated logs, denied egress, invalid/absent reports, partial receipts, WIP, and original bindings are retained with flags. A removed profile/driver leaves readable evidence and an explicit repair reason, never a silent rewrite |
| Resource bounds | Preflight probes, probe/stop grace, child output, report/log, verification per-command time/output, outbox/reconcile per tick, and continuation refs are bounded before cost. No bound is replenished by a retry or a config reload |

### 14.11 Non-claims

This operational section does not claim that mount/PID/network
namespaces, the egress proxy, the in-process production host driver,
the v2 verification profile, the v2 configuration revision, the
operational preflight probes, or a live model/host interaction exist.
It does not claim that a fixture/contract pass proves live enforcement.
It authorizes no runtime setup, credential installation, model call,
host write, automation, publication, or Work completion. Every
dependent implementation unit starts `needs human`, rechecks current
`main` and overlapping PRs, and retains its own tested commit,
sanitized configuration, named scenarios, and actual results.
