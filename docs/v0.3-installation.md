# v0.3 installation and operation guide

Status: preparation document for #269. This guide describes how to
install, configure, preflight, operate, and roll back a v0.3
installation whose Workers speak the executable
`taisan.worker.request/2` / `taisan.worker.report/2` wire contract
([v0.3](v0.3.md), [worker protocol](worker-protocol.md)). It prepares
instructions only: it creates no live Issues, installs no credentials,
enables no normal-installation automation, executes no live models, and
performs no live host effects. Owner-run acceptance is a separate,
explicitly authorized activity governed by the
[owner-run checklist](v0.3-owner-acceptance-checklist.md) and the
[evidence template](v0.3-evidence-template.md).

Every command transcript quoted below was captured from a real,
non-live CLI session against the fixture host adapter and the
deterministic fixture Worker (`workloop-fixture-worker`). The raw
captures — command envelopes, the profile, the installation record,
run transcripts, and the final `tick_report` — are retained under
[`fixtures/v0.3-doc/`](../fixtures/v0.3-doc/README.md) with per-file
provenance. Those captures prove the command surface, the durable
record shapes, and the fail-closed boundaries — they are
**automated fixture evidence**, never owner-run live evidence, and
they never prove live Worker behavior, live host reads/writes, or live
model calls.

## Evidence boundary

| Claim class | What it covers here |
| --- | --- |
| Automated fixture/contract evidence | Everything quoted in this guide: `init`, `check`, `submit`, `run`, inspection queries, and the durable records they produce, all against the fixture host and fixture Workers |
| Owner-run live evidence | Only what the owner-run checklist records under explicit authorization: a real conforming Worker, the production `github` host driver, real credentials by reference, and real host effects on one isolated repository |

A fixture result can never mark an owner-run criterion passed. An
unexercised live scenario stays `unexercised`, never `pass` by
implication.

## Two configuration surfaces

v0.3 keeps the two-file model documented in
[v0.2](v0.2.md#two-files-the-profile-and-the-installation-record);
this section records only what changed for the Worker path.

**`config.toml` — the versioned profile.** Scaffolded by `taisan init`,
validated by `taisan check`, reloaded by the intake scheduler. Its
`[worker]` section declares the argv the profile validates at check
stage 5 (`argv` resolves deterministically, `runtime_version` matches
the observed binary, `isolation_profile` names an approved profile).
The profile's `[worker]` section is a *declaration* `check` verifies —
it is not the launch source.

**`<store>.config.json` — the installation record.** Every
store-backed command (`submit`, `run`, `work-*`, `capacity`, …) loads
this JSON record from `--config`, or as `<db-stem>.config.json` beside
`--db`. It is the actual launch binding: `worker_argv`,
`worker_isolation_profile`, the v0.3 Worker credential/egress keys,
and the optional `worker_dispatch` v2 profile. The first store-backed
command publishes a default record with `worker_argv: []` when the
file is absent — `taisan run` then queues Work under no supervisor and
no worker is ever launched. Write the record **before** the first
`taisan run`.

The sanitized v0.3 examples are
[`docs/examples/v0.3/config.toml`](examples/v0.3/config.toml) and
[`docs/examples/v0.3/workloop.config.json`](examples/v0.3/workloop.config.json).
They carry placeholder identities and reference-shaped credential
slots only — no secret values, no private repository names.

### v0.3 installation-record keys

These keys are new or load-bearing for the v0.3 Worker path. All are
optional at load; their absence means the strictest profile, never a
silent widening.

| Key | Meaning |
| --- | --- |
| `worker_argv` | The argv the supervisor launches. For the v2 transport the supervisor appends `run --request <path> --out <dir>` (or `describe` for the declaration probe); the bound argv itself carries the Worker's own mode/flag prefix |
| `worker_isolation_profile` | Approved isolation profile id. Absent names the reference profile `taisan-reference-v0.1`, which requires `bwrap`; `fixture-worker-v0.1` declares no sandbox primitive and exists for contract tests only |
| `worker_credential_ref` | The single runtime credential the contained Worker may receive, as an `env:`/`file:`/`command:` provider reference — never a value. Resolved once at the supervisor boundary and delivered only through the approved `/taisan/runtime-auth` path; absent means no runtime credential |
| `worker_provider_config` | Absolute path to a non-secret provider configuration file or directory, bound read-only at `/taisan/provider-config`. Must not contain the resolved credential value |
| `worker_model_api_hosts` | Bare host names the Worker CONNECT proxy may reach on 443. Empty denies all Worker egress; entries must be bare host names disjoint from the repository host and the verification allowlist |
| `worker_dispatch` | The v2 dispatch profile — see below. Present selects the complete bound-request transport for requests not yet consumed; absent keeps the recorded v1 argv-only launch; malformed is a load-time error, never a silent v1 fallback |
| `verification_toolchain`, `verification_cache_paths`, `verification_egress_allowlist` | The §14.5 verification sandbox surface: pinned read-only toolchain, read-only dependency caches, and installation-default egress hosts (the per-command set adds each request's declared `verification_egress_hosts` and never contains a model-API host) |

`worker_dispatch` shape (validated by `Installation::worker_dispatch`):

```json
"worker_dispatch": {
  "source_path": "/absolute/path/to/bound-repository-checkout",
  "budget": {
    "max_turns": 200,
    "max_report_bytes": 1048576,
    "max_log_bytes": 33554432,
    "max_verification_commands": 8,
    "max_continuation_refs": 4
  },
  "invariant_set": {
    "id": "invariants-1",
    "revision": 1,
    "items": ["no-todo", "tests-pass"]
  },
  "capabilities": ["artifact_json", "process_control"]
}
```

- `source_path` must be absolute: the supervisor-side local checkout
  of the bound repository that base resolution and managed workspace
  preparation fetch from. The Worker never sees this path.
- Every `budget` field is a positive integer — `0` is never
  "unlimited". These bounds are written into each immutable request
  body; a retry or config reload never replenishes them.
- `invariant_set` is the approved set InvariantCheck requests bind.
  Absent refuses every InvariantCheck dispatch as
  `request.invariant_set_missing`. A changed set is a new
  `(id, revision)` pair.
- `capabilities` is the capability floor every v2 declaration must
  cover; writer roles additionally require `workspace_write`.

## Clean installation

### 1. Build

```sh
git clone https://github.com/shimpeiws/taisan.git
cd taisan
cargo build --workspace
cargo install --path crates/workloop-cli --bin taisan
```

`cargo test --workspace` contract tests spawn
`target/debug/workloop-fixture-worker`, so `cargo build --workspace`
must precede `cargo test --workspace` in a fresh checkout.

### 2. Profile: `init` and `check`

Resolve the profile and state roots once:

```sh
export TAISAN_CONFIG="$HOME/.config/taisan/config.toml"
export TAISAN_STATE_DIR="$HOME/.local/share/taisan"
mkdir -p "$(dirname "$TAISAN_CONFIG")" "$TAISAN_STATE_DIR"
```

`taisan init` scaffolds `config.toml` only from observed evidence —
host endpoint, adapter id, contract version, repository stable ids,
role actors, credential references, and the egress allowlist. It
never fabricates identity and never rewrites an existing config.
Credential references name slots (`env:NAME`, `file:/abs/path`,
`command:argv`), never values.

`taisan check` then runs the ordered, offline, fail-closed preflight:
`config_parse` → `identity_tuples` → `credential_refs` → `paths` →
`worker_runtime` → `isolation_primitives` → `store`, stopping at the
first failing stage. `--probe` adds the opt-in `probe_capabilities`
stage, which currently fails closed because no probe backend is wired.

A captured failing stage — an unset `env:` credential slot stops the
sequence before any later stage runs:

```json
{
  "stage": "credential_refs",
  "status": "fail",
  "diagnostics": [
    {"code": "credential.missing",
     "key": "roles.discussion.credential_ref",
     "message": "credential slot env:TAISAN_GH_TOKEN for role 'discussion' is not set — define it before check can pass"}
  ]
}
```

```text
$ taisan: config: check failed at credential_refs: credential.missing — credential slot env:TAISAN_GH_TOKEN for role 'discussion' is not set — define it before check can pass
```

A missing isolation primitive fails `isolation_primitives` with
`runtime.missing` and leaves `store`/`probe_capabilities` `not_run`:

```json
{
  "stage": "isolation_primitives",
  "status": "fail",
  "diagnostics": [
    {"code": "runtime.missing",
     "key": "worker.isolation_profile",
     "message": "isolation primitive 'bwrap' required by profile 'taisan-reference-v0.1' is not present"}
  ]
}
```

```text
$ taisan: config: check failed at isolation_primitives: runtime.missing — isolation primitive 'bwrap' required by profile 'taisan-reference-v0.1' is not present
```

`check --probe` runs stages 1–7 normally, then fails closed at
`probe_capabilities` — no probe backend is wired, so the stage reports
`capability.unknown` rather than fabricating a result:

```text
$ taisan: config: check failed at probe_capabilities: capability.unknown — --probe was requested but no adapter probe backend is wired for this installation — probe reads require the host adapter; nothing was probed and nothing was written
```

A passing offline `check` emits every stage `pass` (with
`probe_capabilities: not_run`) and `"success": true`. Check success
proves declared prerequisites only — it is never a standing grant, a
live acceptance result, or proof of namespace/egress enforcement.

### 3. Installation record

Let a read-only command publish the default record, then edit it
before the first `taisan run`:

```sh
taisan --db "$TAISAN_STATE_DIR/store.db" work-list
# creates store.db and store.config.json under the state root
```

Write `worker_argv`, `worker_isolation_profile`, the v0.3 credential
and egress keys, and `worker_dispatch` per the record example. The
loader refuses an empty `capabilities` set, an empty `host_actors`
map, and `contract_version: 0`; `adapter`/`host_instance`/`repository`
default to the fixture binding (`fixture`/`host-local`/`local-repo`)
when omitted, so a hand-written record must name the installation's
real binding.

## The conforming Worker contract

A **generic conforming Worker** is any executable that implements the
v2 wire surface — it is not a specific product, runtime, or provider.
The contract a Worker must satisfy:

### argv surface

The supervisor launches the bound `worker_argv` with no shell:

```text
<worker_argv...> describe
<worker_argv...> run --request <request.json> --out <out-dir>
```

Under the approved containment profile the Worker sees the sandbox
paths `/taisan/request.json` and `/taisan/out`; uncontained launches
keep the host paths. `describe` is effect-free, bounded, and
fail-closed: a probe that is refused, times out, exits non-zero, is
unparseable, lacks an adapter id, or lacks the exact
`format_version` is `adapter.declaration_unavailable` — no synthetic
declaration is ever compared or dispatched on.

### Declaration (`taisan.worker.declaration/1`)

The `describe` output must carry `format_version`,
`adapter`/`adapter_version`, `runtime.product`/`runtime.version`,
`protocol_versions`, `roles`, `capabilities`, `resume`,
`checkpoints`, `runtime_artifact_store`, and `local_retries`. For a v2
request the declaration must:

- list **both** `taisan.worker.request/2` and
  `taisan.worker.report/2` in `protocol_versions`;
- list the request `role` in `roles`;
- cover every `required_capabilities.capabilities` entry — a missing
  one is `capability.missing`;
- declare `resume: "unsupported"` (v2 has no session-resume
  contract);
- match the request's stored binding field-for-field at launch — any
  drift is a configuration repair
  (`adapter.identity_mismatch`, `adapter.version_mismatch`,
  `runtime.version_mismatch`, `capability.digest_mismatch`), terminal
  for that request's binding.

### Request and report

The request body is canonical JSON
(`taisan.worker.request/2`) materialized immutably per Invocation
before launch — goal, ordered Issue snapshots, constraints,
verification argv, pinned base, spec digest, workspace identity,
budget bounds, required capabilities, and continuation refs, all
digest-bound. The Worker never fetches bodies; every required input
is delivered or dispatch refuses with a typed code
(`request.snapshot_missing`, `request.head_stale`,
`request.artifact_unavailable`, …).

The Worker writes exactly one `report.json` into its out directory
(`taisan.worker.report/2`, at most `budget.max_report_bytes`). Its
`status` is `success`, `negative`, `unavailable`, `refused`,
`limit_reached`, or `failed`, with a closed `reason.code` set. The
supervisor — never the Worker — classifies the envelope as `success`,
`negative`, `unavailable`, `failure`, `invalid`, or `absent`. A
report is evidence, never authority: publication still requires stop
proof, durable handoff, supervisor verification on the exact produced
commit, enabled gates, and reconciliation of required host effects.

### Fixture versus real

Two deterministic implementations ship for contract evidence:

- `workloop-fixture-worker` — argv-driven scripted modes
  (`clean-exit`, failure modes, `--wire v2`, `--git-commit`,
  `--claim-head`, declaration overrides) used by contract tests and
  runnable non-live installations.
- `workloop-contract-worker` — an independent implementation of the
  same wire surface that shares no response construction with
  `workloop-core`; the unchanged conformance suite runs against both
  binaries ([worker conformance matrix](worker-conformance-matrix.md)).

Both are **contract fixtures**: they prove the wire, validation,
scheduling, and recovery behavior in test harnesses. They are not a
real coding agent, they make no live model calls, and a pass against
them never evidences live Worker behavior. A real conforming Worker —
for example an adapter that drives a coding-agent runtime inside the
same argv/declaration/report contract — is supplied by the owner and
validated by the owner-run checklist.

## Pinned workspace and task delivery

For a `worker_dispatch` installation, every unconsumed request is
materialized before launch:

- The immutable request body is written durably and digest-bound in
  the same commit that consumes the request; a crash can never
  dispatch unbound bytes.
- The managed workspace is prepared from the request's pinned base —
  the fork point recorded in the immutable body — never from
  "whatever the branch looks like now". A successor Execution after a
  retry re-binds the same Work's workspace only when the live tree
  verifies exactly against the new request's pin; moved or dirty
  trees are refused and WIP is preserved.
- Per-Invocation input/output trees are fresh: `/taisan/out` (or the
  host out dir) is never reused across Invocations, so a stale
  `report.json` can never be adopted by a later request.
- `worker_dispatch.source_path` is the supervisor-side read path for
  base resolution; it is configuration, not a Worker-visible mount.

## Operating the loop

### Submit and run

```sh
taisan --db "$TAISAN_STATE_DIR/store.db" submit --intent "<intent>" \
  --idempotency-key <key> [--issue <repo:number> --issue-revision <rev> --issue-digest <digest>]... \
  [--constraint <text>]... [--verification "<argv>"]...

taisan --db "$TAISAN_STATE_DIR/store.db" run --ticks 6 --interval 1
```

`run` is a foreground process driving eight bounded phases per pass:
`source_refresh`, `dispatch_admission`, `in_flight_supervision`,
`host_outbox`, `timed_sweep`, `recovery_scheduling`,
`retention_sweep`, `attention_derivation`. Each pass persists one
`tick_report` record in the store's `event_log` and prints one
progress line (`taisan: pass N: 8 phase(s)`) to stderr. There
is no OS timer — scheduling is internal to `taisan run` (v0.2
intake semantics unchanged).

A captured submit and its accepted decision:

```json
{
  "command": {"id": "cmd-1", "kind": "submit",
              "actor": "human:actor-doc",
              "idempotency_key": "doc-submit-1"},
  "work_id": "w-1",
  "execution_id": "e-1",
  "result": {"execution_id": "e-1", "kind": "work_created"}
}
```

Replaying the same idempotency key returns the persisted decision —
never a second Work:

```sh
taisan --db "$TAISAN_STATE_DIR/store.db" command-result \
  --origin cli --replay-key doc-submit-1
```

```json
{
  "result": {
    "command_id": "cmd-1",
    "committed_at": 1,
    "effect": {"execution_id": "e-1", "kind": "work_created"},
    "status": "accepted",
    "work_id": "w-1",
    "work_version": 1
  }
}
```

### Inspect

```sh
taisan --db "$TAISAN_STATE_DIR/store.db" work-list
taisan --db "$TAISAN_STATE_DIR/store.db" work-detail --work w-1
taisan --db "$TAISAN_STATE_DIR/store.db" attention
taisan --db "$TAISAN_STATE_DIR/store.db" capacity
taisan --db "$TAISAN_STATE_DIR/store.db" anomalies
taisan --db "$TAISAN_STATE_DIR/store.db" evidence ...
```

`work-detail` projects the durable evidence chain — process states,
artifact presence with digests, invocation ids, findings, judgments,
rounds, and the current Execution state. A captured detail after a
completed fixture-Worker run:

```json
{
  "work_id": "w-1",
  "current_execution_id": "e-1",
  "evidence": [
    "process:Running",
    "artifact:artifact.json:Present { digest: \"e7a06d6d…\" }",
    "process:Exited",
    "process:Running",
    "process:Exited"
  ],
  "executions": [{
    "execution_id": "e-1",
    "invocation_ids": ["inv-1", "inv-2"],
    "outcome": null,
    "ownership": "confirmed",
    "state": "waiting"
  }]
}
```

`attention` lists current evidence-backed human needs (empty in the
capture — `[]`); `capacity` shows occupied slots and workspace/branch
reservations; `anomalies` is the read-only stuck-lane census;
`evidence` is the bounded `rui-evidence/1` export surface.

### The host-effect boundary — read this before expecting completion

The captured run ended with the Execution `waiting` and **no**
`host_action_intents` rows. That is the honest non-live boundary, and
it is worth understanding precisely:

- Publish intents (`push_ref`, then `open_change_request`) are
  recorded by `maybe_publish` only when `capability_held` — a
  `CapabilityReport` observation for the bound host marking the
  capability `supported` + `authorized`.
- `CapabilityReport` observations are host-adapter evidence. On this
  tree the only producer is the scenario bridge (`s1-bridge`), which
  `taisan run` refuses as an adapter (v0.3 §14.7 fail-closed); the
  in-process `fixture` and `github` drivers do not emit capability
  reports, and `check --probe` has no wired backend.
- `maybe_publish` is edge-triggered: it re-runs on worker process
  exits, artifact observations, host-action receipts, and recovery
  intents — not on a timer. A capability report arriving after the
  worker pipeline finished does not by itself unblock a parked
  Execution.

Consequence: under `taisan run` alone — fixture **or** github adapter
— a Work's Execution parks at `waiting`/`reconciliation` after the
Worker evidence completes, holding its capacity slot, workspace, and
branch reservation. This is tracked as an open composition gap in
[#355](https://github.com/shimpeiws/taisan/issues/355); the owner-run
acceptance checklist marks every publish-dependent row
`unexercised` until that gap is resolved or the owner records an
explicit alternative evidence path. The captured `waiting` state is
the correct, fail-closed behavior — never a false success and never a
reason to bypass the capability gate.

### Stop and restart

`taisan run` is a foreground process, not a daemon. SIGINT/SIGTERM
stops new work at a phase boundary; an in-flight Worker Invocation is
owned by the supervisor's durable process identity, not by the CLI
process lifetime alone.

- **Graceful stop:** the loop finishes the current phase and exits;
  durable run/lease records remain.
- **Worker stop:** the supervisor owns stop proof — a durable stop
  intent, descendant snapshot, `pid + start time` re-verification,
  state-not-presence inspection, SIGTERM → grace → SIGKILL
  escalation, and reaping. An unproven writer retains its slot,
  reservations, and WIP; it is never assumed dead.
- **Restart:** start `taisan run` again against the same `--db` and
  record. Dispatch re-attaches by recorded identity — no second
  writer for the same Execution, no reused out directory, no
  duplicate host effect. Unknown liveness, stop, or effect outcomes
  stay `unknown`/`uncertain` with ownership retained until inspected
  evidence resolves them.
- **Recovery scheduling:** the `recovery_scheduling` phase consumes
  due intents under their own transactions; transport retries are
  bounded by the Work's durable counter, which survives restart and
  successor Executions.

### Reading a tick report

Each pass persists one `tick_report` record in the store's
`event_log` (retained capture:
[`fixtures/v0.3-doc/out-tick-report.json`](../fixtures/v0.3-doc/out-tick-report.json)).
A captured steady-state report:

```json
{
  "schema_version": "1",
  "kind": "tick_report",
  "deadline_exceeded": false,
  "aborted": false,
  "phases": [
    {"phase": "source_refresh",       "status": "completed", "processed": 0},
    {"phase": "dispatch_admission",   "status": "completed", "processed": 0},
    {"phase": "in_flight_supervision","status": "completed", "processed": 0},
    {"phase": "host_outbox",          "status": "completed", "processed": 0,
     "reason": "reconciled(applied=0 failed=0 unknown=0) applied=0 failed=0 unknown=0 unsupported=0 credential_blocked=0 skipped=0"},
    {"phase": "timed_sweep",          "status": "completed", "processed": 1,
     "reason": "stops_recorded=0 terminal_failures=0 completed=0"},
    {"phase": "recovery_scheduling",  "status": "completed", "processed": 0,
     "reason": "requeued=0 failed_terminal=0 retired=0"},
    {"phase": "retention_sweep",      "status": "skipped", "processed": 0,
     "reason": "cadence"},
    {"phase": "attention_derivation", "status": "completed", "processed": 0}
  ]
}
```

(`started_unix_seconds`/`deadline_unix_seconds` are also recorded;
elided here for readability.)

Interpretation rules:

- `completed` with `processed: 0` is a healthy idle phase, not a
  stall.
- `skipped` carries its reason (`cadence`, `retention_disabled`,
  `work_scope`, `pass_aborted`, `shutdown`, `already_running: …`) —
  a skip is explicit, never silent.
- `deferred`/`held` entries name the exact items a phase could not
  settle this pass; they reappear next pass.
- `failed` aborts the pass (`pass_aborted` skips later gated phases);
  the failing phase name is the diagnostic.
- `deadline_exceeded: true` means the tick deadline fired mid-pass;
  deferred work is reported, not lost.

## Safe disable and drain

Before changing or removing a Worker binding:

1. Stop new admission: `cancel` outstanding submits or let the queue
   drain; intake `enabled = false` stops scheduled admission on the
   next settings tick.
2. Let in-flight Invocations finish or stop them through the
   supervisor's durable stop path; verify stop proof in
   `work-detail` (no `process:Running` without a matching
   `process:Exited`/`Uncertain` resolution).
3. Confirm no unresolved writers, intents, or reservations remain for
   the Work (`capacity`, `work-detail`, `anomalies`).
4. Only then edit `worker_argv`/`worker_dispatch`/credential
   references. A bound request keeps its recorded argv, declaration
   binding, profile, credentials delivery, and budgets — config
   changes apply only to requests not yet bound (v0.3 §14.8).
5. Drain means every owned child is accounted for: no orphaned
   worker process, no unreaped out directory, no outstanding
   `host_action_intent` left `pending`/`unknown` without a recorded
   reconciliation path.

## One-repository cutover and rollback

This procedure enables the v0.3 Worker path on **one** repository
while the legacy operator system still owns everything else, then
drains the legacy path for that repository only. It mirrors the
ordering discipline of [cutover-plan](cutover-plan.md): at no point do
both systems accept Work for the same repository, and no replacement
writer starts while a legacy writer is unproven. Every step's evidence
is recorded in the owner-run evidence template; a step is not
complete until its evidence exists.

### Cutover

1. **Freeze legacy admission for the target repository.** Disable
   every legacy entry point that can admit or dispatch work for that
   repository (scheduler lanes, hooks, manual submit paths). Evidence:
   each entry point recorded disabled; a probe submission is not
   admitted.
2. **Inventory legacy ownership.** Enumerate in-flight items for the
   repository: non-terminal runs, active/unknown writers, unresolved
   remote effects (open PRs, pending comments/reviews, unknown-write
   receipts), and held resources (workspaces, branches, PR heads).
   One ledger row per item with its disposition.
3. **Drain or hand off.** Each item gets exactly one disposition —
   drain to terminal, verified stop with retained evidence, or an
   explicit human handoff that preserves artifacts and re-expresses
   the work as a new Submission. An item still owned by an unfinished
   legacy writer is never re-submitted — that is the duplicate-Work
   guard.
4. **Archive read-only.** Freeze the legacy records for the
   repository as read-only reference; record location and cutoff.
5. **Install and preflight the v0.3 installation** for that
   repository: profile + installation record per this guide, `check`
   passing, `worker_dispatch` bound, credentials by reference only.
6. **Probe admission.** Submit one probe Work for the repository and
   verify it is accepted, dispatched through the v2 wire, and reaches
   its expected state — including the documented host-effect
   boundary. General admission stays off until step 7.
7. **Enable admission** for the repository in the v0.3 installation
   and resume normal operation. Legacy admission for that repository
   stays off permanently; the legacy system remains for
   read-only reference and other repositories.

### Rollback

Rollback is a distinct procedure, not "keep running both":

1. **Stop new-system writers.** Cancel or drain in-flight Executions;
   required evidence is verified stop proof (or write-prevention
   proof) for every writer the v0.3 installation started. An unproven
   writer blocks rollback — it is never assumed dead.
2. **Reconcile state.** Every outstanding host effect reaches a
   terminal receipt or is recorded `unknown`; capacity and
   reservations are reconciled; Attention is current.
3. **Stop the v0.3 loop.** Halt `taisan run` so no new admission or
   dispatch can occur.
4. **Preserve v0.3 state as its own read-only archive.** v0.3 records
   are never converted back into legacy form; in-flight Work follows
   the same drain/handoff procedure in reverse under an explicit
   human decision.
5. **Re-enable legacy admission** for the repository if the owner
   decides to return, or leave it disabled if the cutover is abandoned
   outright. The decision and its evidence are recorded by the owner.

Rollback criteria — any one triggers the procedure: a Worker
contract violation that cannot be bounded, a containment or egress
escape, unreconciled `unknown` host effects, duplicate dispatch with
the legacy system, or an owner decision to revert. None is waived by
a fixture or contract pass.

## Evidence boundaries for owner acceptance

- Fixture/contract evidence (everything in this guide, the conformance
  suite, and `cargo test`) proves contract, validation, scheduling,
  protocol, recovery, and interchange behavior in test harnesses. It
  never proves live selection quality, real Worker behavior, real
  GitHub reads/writes, or owner-run installation behavior.
- Owner-run live evidence is recorded separately per the
  [evidence template](v0.3-evidence-template.md): tested revision,
  sanitized profile and installation record, commands, timestamps,
  observed results, and durable run/proposal/command/Work links.
- An unexercised live scenario is recorded `unexercised` with a
  reason — never `pass` by implication, and a fixture result cited
  alongside it is supplemental only.
- Retained public evidence is sanitized: credential reference names
  only, never values; bounded references to remote objects, not pasted
  bodies.
