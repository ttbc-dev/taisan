# U3.6e per-scenario authorization draft — issue #119

Draft for the owner's per-scenario authorization of the isolated
live GitHub cases. Each scenario requires its own recorded approval
before `docs/u3.6e-live-runbook.md` may be executed for it. Approval
is recorded as an issue comment on #119 (or a linked approval record);
the comment URL becomes the run's `TAISAN_U36E_AUTH` /
`authorization_reference`.

## What is being authorized

For each scenario below, authorization covers exactly:

- One run of the named `#[ignore]`d test in
  `crates/workloop-github/tests/u36e_live.rs` on the named isolated
  installation and repository.
- The remote effects listed — probe commits minted through the git
  database API (unreferenced objects; no branch), scratch `u36e/*`
  branches (created and deleted by the harness), at most one pull
  request (opened and closed), at most one comment (posted, carrying
  a `u36e-marker-*` tag), and the read calls the adapter contract
  requires.
- Retention of the resulting `live_evidenced` evidence record and
  its transcription into `docs/evidence/u3.6e.md` plus the
  consolidation into `docs/evidence/u3.6d.md` (with the matching
  `u36d_docs.rs` expectation updates).

Authorization does **not** cover: any repository other than the named
isolated one, any branch outside `u36e/*`, merges, force pushes,
webhook server setup, or reuse of the approval for a re-run — a re-run
is a new scenario execution and needs its own recorded authorization.

## Credential requirements per scenario

| Scenario | Credential |
| --- | --- |
| `live_partial_push_then_create_failure` | write scope on the isolated repository (creates a branch) |
| `live_lost_response_reconciles_by_marker` | write scope (branch, PR, comment) |
| `live_stale_head_refused` | write scope (branch create/move; the guarded write itself is refused by design) |
| `live_duplicate_delivery_single_effect` | write scope (branch, PR) |
| `live_denied_permission_refused` | **read-only** — a token without write scope, so the host's refusal is exercised |
| `live_git_transport_push_ref` | write scope on the isolated repository (pushes a branch through the git object transport — the #420 smart-HTTP auth path) |

`gh auth login` is not required; `GH_TOKEN`/`GITHUB_TOKEN` in the
environment or an existing `gh` credential suffices.

## Authorization record template

Post one comment per scenario on #119:

```text
U3.6e authorization — <scenario test name>

I authorize one isolated live run of `<test-name>` against
`<owner/repo>` under installation `<install-id>` with the credential
scope listed in docs/u3.6e-authorization.md.

Recorded: <date> — <approver>
```

The comment's URL is the `TAISAN_U36E_AUTH` value for that run.

## Scenarios

### `live_partial_push_then_create_failure` — partial_effects

Push a scratch branch at an existing remote commit, then attempt a
change-request create into a nonexistent base branch. Expected: push
receipt `applied`, create receipt `failed` (definite 422), no change
request exists, branch deleted. Proves partial effects keep
independent receipts on the real host.

### `live_lost_response_reconciles_by_marker` — lost_responses

A `gh` wrapper drops the first comment POST's response after the
effect lands. Expected: intent records `unknown`; a clean reconcile
pass settles it by marker (`find_comment`) with no repost — exactly
one remote comment carries the marker. PR closed, branch deleted.

### `live_stale_head_refused` — stale_head

Seed a scratch branch, move it externally, then attempt the guarded
write recorded against the old position. Expected: definite `failed`
(`stale_head`), remote head unchanged. Branch deleted.

### `live_duplicate_delivery_single_effect` — duplicate_events

Open a real PR from a scratch branch, deliver the same webhook event
twice. Expected: second delivery deduplicates (`IngestReceipt::
Duplicate`), exactly one pull request exists for the branch. PR
closed, branch deleted.

### `live_denied_permission_refused` — permission_drift

Attempt a ref write with a read-only credential. Expected: definite
`failed` — never `unknown` — and no remote effect. Requires the
operator to supply the read-only token for this run only.

### `live_git_transport_push_ref` — push auth scheme

Mint a commit in a fresh local object store (a stand-in for the
installation-owned handoff repository of #411) and push it to a
scratch branch through the real `git push` path under the ambient
credential. Expected: intent `applied`, remote head reads back the
minted commit, branch deleted. Proves the smart-HTTP auth scheme
against the real endpoint — the #420 defect (`Bearer` refused for
`gho_`) was invisible to every mock transport.

## Withheld authorization

A scenario the owner does not authorize is recorded `not_authorized`:
`claim_class: "not_authorized"`, `result: "skipped"`, empty action /
observation / read-back arrays, no `authorization_reference`, and the
intended `isolation_scope`. The consolidated `github` row stays
`unexercised` and its notes cite the withheld authorization. The
schema rejects every other `not_authorized` shape — see
`crates/workloop-github/src/evidence.rs`.
