# U3.6e verification evidence — separately authorized isolated live GitHub cases

Slice: U3.6e (`crates/workloop-github/src/gh_cli.rs` — `GhCliApi`, the
v0.1 `GitHubApi` transport over `gh api`;
`crates/workloop-github/tests/u36e_live.rs` — the five live scenario
harnesses gated on `TAISAN_U36E_AUTH`;
`crates/workloop-github/src/evidence.rs` — `isolation_scope`,
`authorization_reference` and the `not_authorized` claim class;
`docs/u3.6e-live-runbook.md` and `docs/u3.6e-authorization.md` — the
operator procedure and the per-scenario authorization drafts). Parent:
#119 under umbrella #107; the live-class rows consolidate into
[u3.6d](u3.6d.md).

Claims boundary: the records below are **`live_evidenced`** results —
each cites its own owner authorization comment on #119 and the
`isolation_scope` it ran under (`install-u36e-1` on
`shimpeiws/coding-worker-smoke`, a dedicated smoke repository, never a
working repository). A `live_evidenced` record supports claims only
about the recorded scope; fixture results remain contract claims and
never satisfy a live claim. All five scenarios have now executed
under their own authorizations — the `permission_drift` case
(`live_denied_permission_refused`) ran last under a read-only
credential, and three scenarios were re-run under the authorized
installation after a record/authorization mismatch was flagged in
review (see Retained records).

## Authorization

Each run executed under its own recorded owner authorization — one
comment per scenario on #119, never reused across runs or reruns. The
`authorization_reference` of each retained record below is the exact
comment URL the run cited via `TAISAN_U36E_AUTH`; the harness refuses
to make a host call without it, and the evidence schema rejects a
`live_evidenced` record lacking both the reference and
`isolation_scope`.

## Configuration under test

All five scenarios bind the same authorized installation identity
(`host_instance = install-u36e-1`, `repository =
shimpeiws/coding-worker-smoke`, adapter `github`, contract version 1)
to the `GhCliApi` transport. `config_digest` is the canonical sha256
of that installation's configuration projection — identical across
all five records because they share one installation. Each scenario
ran under its own recorded authorization comment; the installation is
shared, the authorizations are not.

## Retained records

One `live_evidenced` record per executed scenario, all `pass`, retained
at `target/u3.6e-records/<name>.json` as the run's working artifact and
transcribed here verbatim. Remote effects were cleaned up after each
run — scratch `u36e/*` branches deleted, change requests closed; probe
commits minted for the scenarios are unreferenced git objects and inert
once no branch points at them.

Three scenarios — `live_lost_response_reconciles_by_marker`,
`live_stale_head_refused`, `live_duplicate_delivery_single_effect` —
were **re-run** after review flagged that their first-run records cited
per-scenario install labels (`install-u36e-2`/`-3`/`-4`) while every
authorization comment named `install-u36e-1`. The records below are the
re-run records under the authorized installation; the first runs'
remote effects were cleaned up and their records are superseded. The
`lost_response` re-run also counts marker-bearing comments on the
change request at run time and asserts exactly one — the earlier
record's "found once" receipt was a fixed string after a single
`find_comment` hit.

## Post-run state

All five U3.6e scenarios have executed under their own recorded
authorizations — no scenario remains pending. Three scenarios were
re-run under `install-u36e-1` (the installation every authorization
comment named) after the first-run records cited per-scenario labels;
the cited records above are the re-run records. The local read-only
token file was deleted after the run; revoking the PAT itself is the
operator's remaining step in the GitHub UI. Probe commits minted for
the scenarios are unreferenced git objects and inert.
