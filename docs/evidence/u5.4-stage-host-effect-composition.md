## Design notes

- `StageEvidence` is append-only and is persisted through the existing
  durable observation log (`ObservationFact::StageEvidence`), so a crash can
  lose an unrecorded attempt but cannot rewrite or erase committed evidence.
- `StagePipeline::next_stage` scans in the fixed order, so a later lane is
  never offered while an earlier enabled lane has only `Entered`, `Partial`,
  or `Failed` evidence. A disabled optional lane is offered as an explicit
  record to write before publication can open.
- Only `Complete` (or an explicit `Disabled`) closes a lane. A `Complete`
  record must carry at least one typed `EvidenceRef`; completion without
  facts is refused before persistence.
- The current head moves only through `observe_head` on the first observation
  or `record_current_head` on an authoritative Core transition. Any later
  differing observation is retained in `head_history`/`stale_heads` and
  cannot satisfy a stage.
- Every `record` binds to the recorded current head: evidence against a
  stale head or a foreign repository is refused with `StaleRevision`
  before it can satisfy a lane. On replay, `from_observations` rebuilds
  `current_head`/`head_history`/`stale_heads` from `change_head` facts and
  evidence-pinned head moves. The pin is the only durable trace an
  authoritative `record_current_head` move leaves, so a
  same-repository pin restores the move — including a head a
  `change_head` observation marked stale, which is exactly what live
  adoption of an observed head looks like — and only when the record
  itself is accepted. A pin to a foreign-repository revision or to a
  head the pipeline already held and moved past is refused, so a
  foreign or backward revision can never promote itself to the
  recorded head after a restart.
- Stage records are Core-authored durable state: the ingest path
  (`handle_observation`) refuses a delivered `StageEvidence` fact, so no
  adapter or external producer can write pipeline history.
- `StagePipeline::bind`/`bind_from_observations` tie the pipeline to the
  Work's frozen `spec.payload.lanes`: a differing policy is refused with
  `LanePolicyMismatch`, so an existing Work is never re-judged under a
  drifted installation config.
- The push receipt is committed by the fixture outbox inside an admitted
  execution's publication window while the change-request capability is
  still unconfirmed, so no `open_change_request` intent can exist yet;
  reopening the store proves the applied `RefPublished` receipt survives
  the simulated crash, the missing create is never inferred, and the
  next publish pass after reopen records and applies it from the durable
  receipt.
