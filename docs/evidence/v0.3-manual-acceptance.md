# v0.3 manual acceptance evidence — issue #270 (record skeleton)

Status: prepared 2026-11-25 as codeable preparation for
[issue #270](https://github.com/shimpeiws/taisan/issues/270). Every
`TO RECORD` field is filled by the explicitly owner-authorized run
executed per
[docs/v0.3-manual-acceptance-checklist.md](../v0.3-manual-acceptance-checklist.md).
Until that run completes and the owner approves §8, this record asserts
**no live claim** and no #270 acceptance criterion is satisfied.

## Claims boundary

Every row below carries exactly one label:

- **owner-run live evidence** — a real installation, a real conforming
  Worker implementing `taisan.worker.declaration/1` +
  `taisan.worker.request/2` + `taisan.worker.report/2` (for example the
  in-repo reference adapter `taisan-worker-claude` driving a real
  coding-agent runtime), the production in-process `github` host driver
  inside `taisan run`, real credentials by reference, and real host
  effects on **one** isolated repository under the recorded owner
  authorization. The commands may be run by the owner or an
  owner-designated operator named in that authorization.
- **automated fixture/contract evidence** — scripted adapters
  (`s1-bridge`), fixture sources or Workers (`workloop-fixture-worker`,
  `workloop-contract-worker`), temporary/in-memory stores, contract or
  unit tests. Citable only as supplemental context; a fixture or
  contract result **never** satisfies a row here.

Rules that bind this record:

- No scenario bridge or scripted coding/review shim substitutes for the
  real profile — a row produced through `s1-bridge`, a fixture Worker,
  or a test-harness path does not qualify.
- A row that did not run is `unexercised` with a reason — never `pass`
  by implication, never silently absent.
- An `unknown`, `failed`, or `uncertain` result stays exactly that —
  recorded, never coerced.
- The executing agent/operator can never approve this record; approval
  is the owner's separate act (§8).
- Credential **values** never appear — `env:`/`file:`/`command:`
  reference names only. A leaked value is an incident: stop, redact,
  rotate.
- No private source repository is named: the live target is *the
  isolated repository*, other systems by role only.

## 6. Outcome citation format [AC5]

Transcribe the terminal outcome **verbatim** from `work-detail` — the
citation the approval reviews:

```json
TO RECORD — outcome block: state, code, detail ("verified target <head>"),
evidence_refs [ {id, digest}, … ], recorded_seq
```

`evidence_refs` is the frozen typed set: `spec:<work>:<rev>`,
`target:<work>`, `artifact:<invocation>:<kind>` per Done Invocation's
required artifacts, `action:<action_id>` per applied intent,
`round:<round_id>` for the deciding round.

| Identity class | Values to record |
| --- | --- |
| Request identities | `TO RECORD` — materialized request body ids/digests per Invocation (`worker_request_bodies`) |
| Invocations | `TO RECORD` — ids, roles (`coding`/`fix`/`invariant_check`), states, out-dir digests |
| Artifacts | `TO RECORD` — artifact ids/kinds/digests incl. any `missing`/`invalid` records kept |
| Verification | `TO RECORD` — `verification_results` ids, argv, exit evidence, environment digest |
| Assessment | `TO RECORD` — assessment observation refs on the final target |
| Heads | `TO RECORD` — base target revision, H1 SHA, H2 SHA |
| Actions | `TO RECORD` — every `host_action_intents` id, action, status, receipt for the Work |
| Stop evidence | `TO RECORD` — process states/stop proof ids for every launched process tree |
| Commands | `TO RECORD` — `(origin, actor, idempotency_key)` → `command_id` for every mutation |
| Work / Executions | `TO RECORD` — Work id and every Execution id (incl. retries/successors) with terminal codes |
| Explicit negatives | `TO RECORD` — every `unknown`/`failed`/`unexercised` item kept explicit, with its reason |
