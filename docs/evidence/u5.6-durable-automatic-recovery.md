## What this slice added

U5.7 noted the remaining producer gap: no production path persisted a
`recovery_intents` row inside a deciding transaction. This slice closes
it:

- `pause_for_repair` writes a `pending` `requeue` intent (due at the
  deciding clock) in the same transaction as the pause decision — an
  explicit hold keeps it `pending`, unmet prerequisites hold it,
  terminal evidence retires it.
- A definite no-effect transport `Failed` receipt writes a `pending`
  `retry` intent due at `now + transport_backoff_seconds(attempt)`
  with `evidence_basis = recovery.transport.max_retries` — persisted
  before any action — and `maybe_publish` defers to a pending retry
  intent instead of re-issuing the failed effect inside the receipt.
- Phase 6 gains the `retry` kind: revalidation, terminal retirement,
  `operator_hold`/`execution_paused`/`execution_active` holds, a
  Work-wide budget re-check (`transport_budget_exhausted`
  suppression), `consumed` recorded before the publish chain re-drives.
- `work_usage.last_progress_basis` (store format 7, additive guarded
  migration) plus `MaterialProgress`/`MaterialProgressSignal`
  derivation: a readable clock (timestamp with a recorded basis, or
  first dispatch when never progressed), `NotStarted`, or `Unknown` —
  surfaced as `progress_unknown` Attention, never progress, never
  death.
- `FailureClass` maps each observed failure class to its `recovery.*`
  budget key; `WorkPolicy.transport_backoff_seconds` is the
  configurable persisted schedule (default `[10, 30, 90]`, last entry
  repeating).

## Residual risks / open items

- `backoff_until` maps onto the pinned schema's `due_at`, and the
  issue's `budget_key` onto `evidence_basis` (the closed
  `recovery_intents` table has no dedicated budget-key column); the
  persisted value is the documented `recovery.*` key string.
- A `retry` intent whose Execution leaves `waiting` for good is held
  (`execution_active`/`execution_paused`), never consumed — it clears
  by retiring on terminal evidence or by firing harmlessly when the
  publish chain is already satisfied (a no-op `consumed`).
- `recovery.transport.backoff_jitter_ratio` is documented at `0.0`
  (deterministic schedule); no jitter was implemented.
- Fixture Work IDs/identities are deterministic only within a test;
  nothing here claims anything about live evidence classes.
