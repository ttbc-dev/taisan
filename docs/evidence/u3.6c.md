# U3.6c verification evidence — reconciliation suite: lost responses, permission drift, actor replacement

Slice: U3.6c (`crates/workloop-github/tests/u36c_records.rs` — the
shared reconciliation and drift scenario table retaining one U3.6
record per scenario per adapter;
`crates/workloop-github/src/sparse_fixture.rs` — the independent
fixture brought to the same reconciliation contract: host-instance
binding, the credential gate, per-actor `denied` grants, remote
branch/change attribution, `observe_effect`, and a read-only
`reconcile_outbox` that settles `unknown`/`pending` intents from the
remote's own reads before any write is attempted;
`crates/workloop-github/src/fixture.rs` — `ObservedEffect` made
crate-visible for the shared verdict type and an
`install_credentials` test control). The record format itself is the
U3.6a slice — see [u3.6a](u3.6a.md), the write-path precedent
[u3.6b](u3.6b.md), and
[repository-host-contract](../repository-host-contract.md#u36-evidence-record).

Claims boundary: every result below is a **fixture/contract** result
produced by local tests. It supports contract claims about this
repository only (`claim_class = fixture_contract` on every retained
record). No live host, Worker, or E2E scenario was run; any live claim
requires separately authorized live evidence under the
[implementation start gate](../design-closure.md#implementation-start-gate).

## Configuration under test

Each run binds the test installation (`host_instance = test-host`,
`repository = local-repo`, contract version `1`, publication actor
`pub-agent`) to one adapter implementation — `fixture-github` (the
GitHub adapter; the GitHub-shaped fixture the U3 contract targets) or
`sparse-host` (the independent fixture implementation: a scoped event
journal with its own remote model, no shared code with
`FixtureGithub`). `declared_capabilities` is populated from each
adapter's own declared set, so the `config_digest` differs per
adapter both by adapter id and by capability vocabulary.

`SparseHost` declares only `repository_read`, `branch_read`,
`push_ref`, `change_request_create`, `change_request_read`,
`checks_read`, and `review_findings_read`; its update/comment/review/
thread/readiness operations keep their explicit `unsupported`
receipts. For this slice its remote gained the reconciliation surface
the contract requires — host binding, credential authentication,
per-actor denied grants, planted branch/change state with actor
attribution, `observe_effect`, and read-only `reconcile_outbox` — so
every scenario below runs unchanged on both adapters.

Each record's `config_identity` cites the configuration the scenario's
Work and intents were actually accepted under — the digest covers the
role→actor bindings including each `credential_ref`, so it is never a
configuration the run did not exercise. The actor-replacement
scenario seats `env:TAISAN_U36C_CRED`/`env:TAISAN_U36C_CRED_NEXT`
slots and the restart scenario reconciles under a moved
repository/actor, so those records cite their own exercised
configuration digests (distinct from the shared `config()` digest the
single-configuration scenarios bind); the post-change configuration
each scenario also exercises is narrated in `read_back_receipts`.

## Retained records

One record per scenario per adapter, all `fixture_contract`, all
`pass`, produced by
`u36c_records.rs::reconciliation_records_retain_one_record_per_scenario_per_adapter`
and persisted at `target/u3.6c-records.json` under the fail-closed
stamp. `action_identities` names the durable outbox intents the
scenario exercised; `observation_identities` names the recorded typed
read deliveries; `read_back_receipts` cite each intent's receipt facts
and the fresh typed reads that re-observed the settled effects.
