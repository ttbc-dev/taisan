# U3.6b verification evidence — write-path suite: guarded writes and partial effects

Slice: U3.6b (`crates/workloop-github/tests/u36b_records.rs` — the
shared write-path scenario table retaining one U3.6 record per
scenario per adapter;
`crates/workloop-github/src/sparse_fixture.rs` — the independent
fixture's write path brought to the same guarded-write contract:
one-shot execution faults, queued racing-actor branch moves drained
before each read-back, recorded commit ancestry for
`Equal`/`Ancestor`/`Diverged` classification, and genuine post-write
reads on push and change-request create). The record format itself is
the U3.6a slice — see [u3.6a](u3.6a.md) and
[repository-host-contract](../repository-host-contract.md#u36-evidence-record).

Claims boundary: every result below is a **fixture/contract** result
produced by local tests. It supports contract claims about this
repository only (`claim_class = fixture_contract` on every retained
record). No live host, Worker, or E2E scenario was run; any live claim
requires separately authorized live evidence under the
[implementation start gate](../design-closure.md#implementation-start-gate).

## Configuration under test

Each run binds the test installation (`host_instance = test-host`,
`repository = local-repo`, contract version `1`, publication actor
`pub-agent`) to one adapter implementation — `fixture-github` (the
GitHub adapter; the GitHub-shaped fixture the U3 contract targets) or
`sparse-host` (the independent fixture implementation: a scoped event
journal with its own per-subject version tokens, no shared code with
`FixtureGithub`). `declared_capabilities` is populated from each
adapter's own declared set, so the `config_digest` differs per
adapter both by adapter id and by capability vocabulary.

`SparseHost` declares no `change_request_update`: update intents in
the chain and raced scenarios receive its explicit `unsupported`
receipt naming the operation — never an applied claim — and the
suite asserts that receipt rather than weakening the scenario. Its
push and change-request create now perform the same guarded write +
fresh read-back the GitHub adapter models, including racing-actor
mutations drained between write and read-back.

## Retained records

One record per scenario per adapter, all `fixture_contract`, all
`pass`, produced by
`u36b_records.rs::write_path_records_retain_one_record_per_scenario_per_adapter`
and persisted at `target/u3.6b-records.json` under the fail-closed
stamp. `action_identities` names the durable outbox intents the
scenario exercised; `read_back_receipts` cite each intent's receipt
facts and the fresh typed reads that re-observed the applied effects.

## Non-claims

- No real GitHub API call was made; `FixtureGithub` is the GitHub
  adapter model and `SparseHost` an independent fixture — fixture
  passes are modeled-behavior evidence only. The real adapter (#17)
  produces `fixture_contract`-shaped records under the same format
  when it runs this suite; live claims remain separately authorized.
- `core_revision`/`adapter_revision` equal `tested_revision` for these
  in-repo fixtures — the fields stay semantically distinct for a
  separately-built adapter.
- `SparseHost` still declares no change-request update (or comment,
  review, thread, ready) capability — its `unsupported` receipts are
  the honest answer, and update coverage on the write path is
  evidenced on the GitHub adapter only. Widening the sparse remote is
  later-slice work if a scenario needs it.
- Reconciliation of `unknown` effects beyond the receipt boundary and
  consolidated multi-scenario records are the U3.6c–d slices; the
  authorized isolated live cases are U3.6e.
- `GitlabFixture` stays out of scope — the issue scopes the write path
  to the fixture and GitHub adapter runs.
