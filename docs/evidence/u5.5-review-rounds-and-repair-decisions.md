  `recovery.max_fix_invocations` Work-wide bound.
- Heads: `CommitRevision` values on one trusted repository identity; each
  repair+reassessment cycle publishes a successor head.
- Findings: stable `finding_id` plus a `content_digest` pinning the observed
  content.
- Dispositions: `FindingChoice` (`Fix`/`Dismiss`/`Accept`/`Wait`) submitted as
  `FindingDisposition` sets.

## Design notes

- `ReviewRepair` (`crates/workloop-core/src/review.rs`) is a pure Core
  decision machine in the shape U5.4 established for `StagePipeline`: it
  consumes only supplied facts — the loop records heads and observed
  findings, operators supply dispositions — and Core alone decides whether a
  repair pass may start. No loop, store, supervisor, or host wiring changed.
- There is exactly one round per head. Re-opening the same
  `(round_id, head)` pair is idempotent; rebinding a round id to a different
  head, or recording a second round id for an already-recorded head, is
  refused. A finding re-observed with identical content is idempotent; the
  same id with different content is `ConflictingFinding` — refused
  operations leave the recorded round byte-identical.
- `record_decisions` binds `decided_head` to the round's head AND requires
  it to be the recorded current head, so a decision for a different head or
  on a stale round is invalid. The submitted finding set must equal the
  round's current set exactly — missing, unknown, and duplicate ids refuse
  the whole submission atomically, so a partial set is never recorded.
- Decisions are append-only `FindingDecision` records: re-deciding a finding
  appends a newer record and never rewrites the old one, which is what lets
  per-finding disposition evidence survive later repair passes.
- `repair_gate` reports exactly the two prerequisites —
  `CurrentHead` (recorded current head equals the round's `decided_head`)
  and `FindingsDecided` (the round's current finding set is completely
  dispositioned and selects at least one `Fix` occurrence) —
  independently, so each missing prerequisite is visible on its own.
  The latest disposition per finding governs: fix publication binds the
  current exact-set judgment and its selected occurrences
  ([evidence gates](../evidence-gates.md#stage-effects-and-reconciliation)),
  so a fully dispositioned round with no `Fix` selection — all
  `Dismiss`/`Accept`, all `Wait`, or no findings — has no repair work
  and stays blocked. Decided non-fix findings settle without a pass and
  unresolved `Wait` findings route to Attention; neither consumes fix
  budget.
- `begin_repair` has exactly three outcomes: `Held` on a blocked gate (no
  budget charged), `Started` on an unlocked gate under the bound (one
  Work-wide fix invocation consumed, 1-based ordinal), and `Escalated` at
  the bound. Escalation records `BoundExhaustion` once under the
  `recovery.max_fix_invocations` key and every later attempt reuses that
  record — another pass never starts and the bound never replenishes across
  heads, rounds, or restarts.
- The contract types live in `workloop_core::review` deliberately separate
  from the durable store model (`domain::ReviewRound`, `RoundJudgment`,
  `command::FindingDecision`, and the pause-recovery
  `domain::RepairPrerequisite`): the durable layer keeps its sealed-round /
  generation semantics for persisted judgments, while this module states the
  per-head append-and-decide rule the repair transition is judged under.
