# U4.2 verification evidence — reference shim and isolated launch

Slice: U4.2 (supervisor-side translation of one approved Invocation into
the reference `WorkerRequest`; durable export written before launch;
deterministic `request_id`; launch binding of `request_id` to the
spawned process handle; `resume` refused with `Unsupported{reason}`;
store format v3 additive `worker_request_exports` table) in
`crates/workloop-core/src/worker.rs`, `crates/workloop-exec/src/supervisor.rs`,
`crates/workloop-store/`, and the fixture/contract suite in
`crates/workloop-exec/tests/shim_contract.rs`.

Claims boundary: every result below is a **fixture/contract** result
produced by local tests — an in-memory store and the scripted
`ProcessControlPort` (`workloop_exec::scripted`) modeling spawn/launch
faults no argv can produce. It supports contract claims about this
repository only. No live Claude Code CLI runtime, isolation primitive
(bubblewrap/namespace/egress proxy), host, or E2E scenario was run;
isolation-profile enforcement is U2.3/U2.4. The export records the
approved profile id; nothing about namespace or egress enforcement is
claimed or implemented here. Any live claim requires separately
authorized live evidence under the
[implementation start gate](../design-closure.md#implementation-start-gate).

Interpretation record: the issue text was flagged twice by
issue-refinement as spec-ambiguous (2026-11-09/10 comments). The
reviewed interpretation, approved before implementation, is:

1. The supervisor is the taisan-owned shim role for this slice: it
   receives exactly one Invocation (from the durable request log) and
   produces exactly one `WorkerRequest`. A separate
   `taisan-worker-claude` runtime-translation binary (prompt
   construction, stream-json parsing) is **not** in this slice; the
   approved design pins prompt semantics to a runtime version that is
   not available in this environment and inventing one would fabricate
   behavior no document authorizes.
2. The `profile id` the export names is a recorded declaration. The
   installation may set `worker_isolation_profile` in its installation
   profile; absent means the approved reference profile id
   `taisan-reference-v0.1`. Enforcement (bubblewrap, egress proxy,
   preflight) is U2.3/U2.4 and is not claimed here.
3. `request_id` for the export derives deterministically from
   `invocation_id` (`worker:<invocation_id>`). This is a new identity
   space; the admission-time `<execution_id>:inv:<n>` request id is
   unchanged.
4. A request asking for `resume` is refused with
   `Unsupported{reason}` at the export boundary
   (`WorkerRequest::build`); the supervisor can never construct a
   resume-kind request, so nothing launches and no export is committed
   for it.

## Design notes

- The export `worker_request_exports` row is committed in the same
  transaction as `InsertInvocation`/`MarkRequestConsumed` — crash order
  is export, then identity, then launch. The launch binding
  (`BindWorkerRequestExport`) is committed in the same transaction as
  `UpdateInvocation { state = running }`; if the binding cannot be
  written the whole commit fails and the Invocation stays `prepared`,
  so reconciliation can resolve the writer through the binding or not
  at all — never partially recorded.
- An export that never binds (faulted or lost launch) is the recorded
  crash window. Reconciliation (`reconcile_or_start`) finds the
  Invocation, reports `ProcessState::Unknown`, and spawns nothing; the
  Execution goes `uncertain` and keeps its slot and reservations.
- `worker_request_exports` is store format v3, additive only: v1 and
  v2 files open through the existing idempotent additive migration;
  a v2-stamped file missing v2-era tables is refused by the format
  gate (regression-tested by
  `contract_commands.rs::a_versioned_file_missing_the_v2_schema_is_refused`).
