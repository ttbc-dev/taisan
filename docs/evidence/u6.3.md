## Non-claims

- No live host/Worker/E2E evidence. Alternate admission acceptance is
  separate from S1; this slice does not claim it.
- `propose` runs the selector once over a supplied snapshot file; it
  introduces no automatic triage, grouping, or unattended scheduling —
  an operator or adapter still invokes it explicitly.
- The selector section configures the admission path only; it grants
  the selector no store handle or authority — every proposal still
  travels `handle_command`.
- A `propose` batch is not atomic: a store fault mid-batch can leave
  earlier proposals already committed. Those decisions are durable and
  recoverable — the error envelope lists their replay keys alongside
  the interrupted proposal's own, and re-running `propose` replays
  them. Envelope-status semantics, reconciled with the batch note on
  the CLI contract's `error` bullet
  (`../execution-loop.md#envelope`): a partial batch's
  terminal `error` (store class) means the *batch run* stopped and
  nothing was recorded for the interrupted proposal — the bounded
  `evidence_refs` are the replay keys of what *was* recorded, so a
  consumer must not read the envelope as "nothing exists" or retry
  with fresh keys; re-running `propose` replays the recorded
  decisions. An undetermined fate stays `unknown`, carrying the
  interrupted proposal's own `(origin, actor, idempotency_key)`
  mutation identity — never the propose run's query identity — with
  the same bounded `evidence_refs`. The fault itself is exercised by
  `a_mid_batch_store_fault_lists_replay_keys_for_recovery` (round-1
  review fix); the undetermined identity and the evidence bounds are
  exercised by
  `an_undetermined_batch_fate_reports_the_interrupted_proposal_identity`
  and `batch_evidence_refs_stay_within_the_envelope_bounds`
  (unresolved-thread review fix); the shared resolver's
  undetermined-fate branch remains covered by the envelope unit tests
  (`lost_response_with_unreadable_decision_stays_unknown`).
- `required_permissions` in the selector section is policy/identity
  provenance only: it shapes the proposal key but is not a command
  field, not recorded on the admitted Work, and not enforced by
  translation — capability coverage remains Core's check.
- `excluded` uses the `repo:number` grammar (same as `submit
  --issue`); the number matches a fact's opaque IssueId or its
  repository-scoped display number
  (`excluded_entries_match_by_display_number_for_opaque_issue_ids`),
  so an adapter whose IssueId is not the decimal number is still
  excluded by display number. A fact that carries neither (no display
  number and a non-numeric IssueId) cannot be named by this grammar —
  the same limitation `submit --issue` shares.
