## Non-claims

- No live host/Worker/E2E evidence. Alternate admission acceptance is
  separate from S1; this slice does not claim it.
- `propose` runs the selector once over a supplied snapshot file; it
  introduces no automatic triage, grouping, or unattended scheduling —
  an operator or adapter still invokes it explicitly.
- The selector section configures the admission path only; it grants
  the selector no store handle or authority — every proposal still
  travels `handle_command`.
- A `propose` batch is not atomic: a store fault mid-batch can leave
  earlier proposals already committed. Those decisions are durable and
  recoverable — the error envelope lists their replay keys, and
  re-running `propose` replays them. The recovery contract is
  exercised by replay tests; mid-batch fault injection is not covered.
- `required_permissions` in the selector section is policy/identity
  provenance only: it shapes the proposal key but is not a command
  field, not recorded on the admitted Work, and not enforced by
  translation — capability coverage remains Core's check.
- `excluded` uses the `repo:number` grammar (same as `submit
  --issue`); adapters issuing non-numeric IssueIds cannot express
  exclusions this way — a known limitation shared with the CLI.
