# U8.4 evidence — recovery variant (S1 live runs with authorized fault injection)

Slice: U8.4 (`crates/workloop-cli/src/bin/s1_bridge.rs` — the
scenario-local real-host bridge; adds two environment-gated, scenario-only
fault hooks: `S1_BRIDGE_KILL_AFTER_APPLY=push_ref`, die between the
landed push and the receipt write, and `S1_BRIDGE_INJECT_FAIL_OPEN_PR=1`,
record a definite no-effect failure for the create leg — these hooks are
the *only* behavioral change; `scripts/s1/worker-shim.sh` — the
deterministic scenario Worker, unchanged).

Arming rule (current revision): neither single-purpose variable is
consulted unless the bridge is a debug build **and**
`S1_BRIDGE_SCENARIO_FAULTS` names the exact repository configured for
this bridge (`shimpeiws/coding-worker-smoke` for this scenario). An
inherited or leaked hook variable on its own is inert — it cannot kill a
run or suppress publication in another installation. The runs recorded
below predate that master gate and armed the hooks directly at revision
`03d1513`; under the opt-in the injected branch is the same code, and no
live run was repeated after the gate was added. The gate predicate is
unit-tested (`crates/workloop-cli/src/bin/s1_bridge.rs`,
`fault_hooks_require_scenario_opt_in_for_this_repo`).

Claims boundary: these are **live** results. Three real Work items were
submitted through the real `taisan` CLI against the isolated repository
and dispatched by the real run loop. One (`w-3`) was carried to
`succeeded` through a real publish/review/fix cycle with the lost-response
fault injected at the push leg and later recovered; one (`w-4`) is the
fault-free control run that published a PR and drove it to `succeeded`;
one (`w-6`) ran the partial-effect fault — the push landed, the create
leg was refused by the injected failure, and no PR was ever created.
Remote effects went through real GitHub and real GitHub Actions runs
throughout. All Work went through the real `work::handle_command`/
`handle_observation` pipelines and the SQLite durable stores. Fixture
adapters produced **no** evidence in these runs: the installations
declare `adapter: s1-bridge`, which the run loop treats as an
out-of-process adapter.

**Authorization**: live execution of this isolated scenario was
explicitly approved by the owner in-session on 2026-11-11, before the
runs began. The approval covers the isolated scenario repository only.
The GitLab spike remains unrun and unauthorized; no cross-host claim is
made. No PR was merged or deployed; nothing was deployed.

Honest scope limits, stated once: (a) the host side is the **scenario
bridge**, not the production GitHub adapter (U3.x remains open) — it
performs real effects through `git`/`gh` and reports real read-backs;
(b) the Worker is a **deterministic scenario shim**, not a coding-agent
runtime (U4.2 remains open); (c) the "invariant-check" leg is an
Assessment fact verified on the real diff, not a separate Invocation
role; (d) `push_ref.produced` is the artifact payload digest per the
Core contract, while `observed`/`relation` record the real remote ref;
(e) the reviewer identity is `github-actions[bot]` — real
GitHub-authenticated pull reviews, not human or LLM judges;
(f) **the recovery-intent machinery has no production writer** —
`InsertRecoveryIntent` is applied only by tests; the live run therefore
exercises fault (c) with **scenario-seeded** pending intents (see fault
(c) below), because no production code path creates one on this
revision (that is U5.6, #96, open); (g) artifact handoffs for the
first-coding invocations of each Work were marked `invalid/ref_conflict`
because stores A and B share one `workspace_root` and therefore one
`.handoff/repo.git` (see Incidents §4); (h) cancellation of a paused
execution does not settle the Execution on this revision (see Incidents
§3).

## Fault (a) — lost response: worker killed between apply and receipt-write

Scenario: the bridge (the only actor in this installation permitted to
apply host effects — the Worker holds no host credential, so the
"writer killed between apply and receipt-write" surface is the bridge)
completed the `git push` for the seeded Work, and was killed by the
injected hook **before** it could write the receipt.

Timeline (all UTC, from the store's observations and this session's
commands):

1. `04:58:22Z`-era bootstrap: Work `w-3` submitted (`cmd-3`), dispatched,
   `inv-1` (coding, round 1) ran and produced `d9420ec` on `work/w-3`
   (worker shim log: `{"evidence": "s1-shim", "round": 1, "commit":
   "d9420ec9515190a180cb8a823fd9ce806c045dff", "verification_exit": 0}`),
   artifact Present at `04:59:04Z` (observation id 6).
2. `04:59:10Z` — `BranchState{branch:work/w-3, state:absent}` emitted
   (observation id 8); the push intent `act-6887ecd9-4c0b-4570-a509-`
   `95ae87465bfb` was Pending.
3. The bridge was restarted with `S1_BRIDGE_KILL_AFTER_APPLY=push_ref`
   (the tested revision needed only this variable; the current revision
   additionally requires the master opt-in described at the top).
   It re-read the remote (`absent`), pushed under
   `--force-with-lease=refs/heads/work/w-3:` (expected absent), the
   push **landed** (`git ls-remote` after the kill: `d9420ec9515190a180cb`
   `8a823fd9ce806c045dff refs/heads/work/w-3`) — and the process
   died by the hook before any receipt was written. The injected fault
   logged `s1-bridge: injected fault kill_after_apply push_ref
   act-6887ecd9-…`; the store still shows the intent `pending`.
4. **Hold** — capacity was queried at `2026-11-11T04:59:17Z` while the
   writer was unverified: `e-3` held `workspace:ws-w-3` and
   `branch:github.com/shimpeiws/coding-worker-smoke/work/w-3`
   reservations with no expiry, state `waiting`. (Hold timestamp recorded.)
5. **Restart and reconcile from host read-back** — at `04:59:25Z` the
   restarted bridge (no fault env) read the remote ref; it observed
   `d9420ec` at `work/w-3` (observation id 9). The re-push under the
   exact-lease read was a no-op; a receipt authenticated as
   `shimpeiws` recording `Applied` with
   `RefPublished{produced: 1dbbdb05… (the artifact payload digest the Core contract commits to the intent),
   observed: d9420ec9515190a180cb8a823fd9ce806c045dff (the real pushed commit), relation: ancestor}`
   was recorded at `04:59:26Z` (observation id 10 — the receipt of the
   no-op re-execution, not a settle-from-read record; the read-back
   evidence is id 9 plus the `verify:equal` emissions at id 13 and on
   the restart and republish ticks; note `produced != observed` and
   `relation: ancestor` — the relation is *not* `Equal`, because
   `produced` is a content digest, never a git object on this revision).
   A *separate* re-execution
   record follows under the same action id for the digest re-arm:
   `ref_published` re-recorded at `04:59:29Z` (observation id 13) and
   again on the republish leg at `05:00:49Z` / `05:00:50Z`.
6. The publish chain re-armed on the restart tick and created
   `open_change_request` `act-d2837364-48fc-41a4-8820-f3c8af5d9410`;
   one PR was created — `coding-worker-smoke#22` at `04:59:28Z`,
   `work/w-3` → `main` — **no duplicate PR exists** (verified:
   `gh pr list --state all` shows exactly one PR for the branch, and
   `head:PR_kwDOVM4cU88AAAABOSsZvw:d9420ec…` was recorded as ChangeHead

   (`130332845105` at `04:59:20Z`, `130332941011` at `04:59:39Z`),
   `review` success (`130332940898`); review `5854068886` by
   `github-actions[bot]` on `d9420ec` (2 findings, see below).
7. **Release** — after the reassessment reached `succeeded` on
   `6293efe`, `capacity` was queried again; the query output was
   `holders: []`, `reservations: []`, `used: 0`. The exact wall-clock of
   the release query itself was not separately logged (the query ran
   immediately after the `succeeded` transition); the hold is pinned to

   query — stated exactly, not padded.
8. Unverified-writer protection: between the kill (step 3) and the
   restart read-back (step 5), no second push and no PR creation were

   was not replayed blindly; it was settled from the host read.

Fault (a) named scenario: **`u84a-lost-response-restart`** — the record
above is the scenario's evidence; the read-back reconciliation record
(id 9 host read plus the `verify:d9420ec:equal` emissions id 13/25) and

the republish leg receipts id 24–26, distinct timestamps `04:59:29Z` /

What this does **not** show: Core does not yet resume a `paused`
Execution automatically through this path — after the receipt landed,
ordinary passes drove the run; no operator re-enqueue was used at any
point for reconciliation itself (the judgment commands below are the
ordinary review/fix lane, not recovery).

## Fault (b) — partial effect: push lands, subsequent effect fails

Scenario: Work C (`w-6`, `e-6`, issue #26), submitted through the real
CLI. Round 1 produced `adce5436` (worker shim log:
`{"evidence": "s1-shim", "round": 1, "commit":
"adce54369e7750f9f7a976fa5ee4efd8add18baf", "verification_exit": 0}`).
A tick with `S1_BRIDGE_INJECT_FAIL_OPEN_PR=1` then (same arming rule as
fault (a): the master opt-in is required on the current revision). The
hook also requires a recorded, `Applied` `push_ref` for the same Work and
source branch carrying a `RefPublished` effect; an armed variable with no
such receipt falls through to the real create path instead of fabricating
a partial-effect claim:

1. applied `push_ref` (`act-9c9408c9-2d09-40f7-b954-cd80f734af59`,
   Applied; remote `work/w-6` = `adce5436`, verified via `git ls-remote`);
2. re-armed the publish chain inside the same drain, which created the
   `open_change_request` intent `act-55e0ebfb-…`; the injected hook
   recorded a **definite no-effect failure** (injected fault) instead of
   calling the API.

The failure was **not** absorbed: because each `Failed` receipt re-arms
the chain, the drain created **three more** `open_change_request`
intents (`act-8b5b2023-…`, `act-4309f1a6-…`, `act-fcf74809-…`), all
recorded `Failed` with the same injected reason — the re-arm stopped
only when `transport_retries_used` exceeded
`policy.transport_max_retries` (`3`): `e-6` paused with
`pause_reason: transport retry bound reached; human action required`,
`repair_prerequisites: [OperatorDecision]`. Across three further
ordinary passes and two further bridge ticks (env unset) no further
create intent was created (re-arm stopped at the bound).

Host state, cited by read-back: `gh pr list --state all --head work/w-6`
returns `[]` — **zero PRs** for the branch; the branch ref exists at
`adce5436`. No duplicate effect occurred on the host.

Named scenario: **`u84-partial-effect-injected-failure`**. What this
does **not** show: an automatic resume after such a failure (by design
there is none on this revision — the Transport bound converts repeated
failure into an operator-decision pause), nor a success PR for this
Work; and the repeated re-arm itself (four create intents for one
logical effect) is recorded as an observation, not endorsed as the
desired design.

## Fault (c) — restart with a pending `RetryIntent`

No production code path writes `recovery_intents` on this revision
(`InsertRecoveryIntent` is applied only by tests — U5.6, #96, open).
Fault (c) therefore exercises the **automatic recovery path with
scenario-seeded intents**, on the live store, driven by the real
`taisan run --once` pass (phase 6 `consume_due_recovery_intents`), never
by an operator re-enqueue. The seeding is recorded here in full; the
seeded rows are marked with `evidence_basis` saying so:

| Intent | Work/Execution | Kind | due_at (UTC) | generation | Seeded |
| --- | --- | --- | --- | --- | --- |
| `rintent-u84a-1` | `w-3` / `e-3` | `requeue` | `05:01:42Z` | 1 | after H1 pause, before any restart |
| `rintent-u84a-2` | `w-3` / `e-3` | `requeue` | `05:04:31Z` | 1 | after `e-3` reached `succeeded` |

Observed:

1. **Pre-due pass, before restart** (`2026-11-11T05:00:19Z`,
   `eta ≈ 83 s before due`): `taisan run --once --work w-3` completed;
   `rintent-u84a-1` stayed `pending`, `due_at` and `generation`
   unchanged — **no early fire**.
2. **Post-due, while execution still live**: at `05:02:11Z` and later
   passes the intent was evaluated by the automatic path; the Execution
   was not paused at that time, so the intent stayed `pending`
   (`execution_active` hold — by design the automatic path never forces
   an active execution).
3. **After terminal settle**: by `2026-11-11T05:04:08Z` (three passes
   after due) `rintent-u84a-1` = `retired`, reason `execution_terminal`;
   by `2026-11-11T05:04:43Z`, `rintent-u84a-2` — seeded after terminal
   and evaluated only in later, separate processes — = `retired`,
   reason `execution_terminal`. Both were written **before** the
   restarts that consumed them; every pass was a separate process
   (restart durability is per-invocation).
4. **Terminal retirement is durable**: across three subsequent passes
   after retirement (including passes run after the final restart), the
   row remains `retired` / `execution_terminal` and never re-fired.
5. **Consumed intent id via the automatic path**: **absent** — no
   pause reachable through the real loop on this revision yields
   `Consumed{requeued}` (no pause in these runs yielded one — they all
   carried `RepairPrerequisite::OperatorDecision`; other prerequisite
   classes exist in the code but were not triggered here), and no
   production writer ever creates a `requeue` intent. The `Consumed` path is covered by the named
   contract scenarios in `crates/workloop-store/tests/fault_matrix.rs`
   (`lp_25_persisted_schedule_fires_exactly_once`,
   `lp_21_terminal_evidence_retires_the_intent`,
   `lp_27_timeout_recovery_sequence_orders_stop_reconcile_requeue`),
   which were run and green in this slice's gates. Marked **absent** for
   live coverage, not fabricated.
6. Persisted backoff/due-time survives restart: both intents retained
   `due_at_unix_seconds` and `generation` exactly as seeded through
   every pass; neither fired early.

Named scenario: **`u84-retryintent-restart`**.

## Incidents inside the runs (recorded, not hidden)

1. **Branch collision avoided before any push.** The first Work composed
   on this machine in store A would have reused `work/w-1`, which exists
   on the remote from U8.2 (PR #14) — reusing it would have force-pushed
   over retained evidence (the lease guard would have rejected it, but
   the intended Work would have died at publication). The first store
   was abandoned (`<scenario-state>/workloop-a-run1.db`, kept as evidence on the host); two
   burns per store were used to advance work-id sequencing so the real
   Works landed on `w-3` (A) and `w-6` (B); burns were cancelled before
   any dispatch. Remote `work/w-1`/`work/w-2` were never touched by
   these runs.
2. **Misfired fault injection (twice).** For fault (b), the bridge was
   expected to receive the failure hook before the create leg. In both
   earlier scenario runs (`w-4`, issue #18; `w-5`, issue #24) push and
   create were applied inside a single drain, so PRs `#23` and `#25`
   were created (open, never merged). A third run (`w-6`, issue #26)
   placed the hook on the publishing tick and landed the intended
   partial effect. `w-4`/`e-4` subsequently completed as the fault-free
   control run, so PR `#23` is retained as that control run's receipt
   (Run identities) — never as fault-(b) evidence; `w-5`/PR `#25` is
   retained only as an incident. All PRs and branches are retained as
   evidence; no revert or deletion was performed.
3. **Cancellation of a paused Execution does not settle it.** `w-5`
   (`e-5`, issue #24) and `w-4`'s earlier pause were requested
   `cancel` after their reviews landed; the commands were accepted
   (`state_changed`, slot released) but the Executions remain `paused`
   and nonterminal on this revision. `e-4` was later judged (`jdg-1` on
   `round-5efaa609-…`), released (`cmd-5`), fixed (`inv-3` →
   `204ab155`) and reassessed to `succeeded` — so its slot was released
   at terminal, and `e-5` remains paused (its reservation was released
   at the cancel, so `e-6` could dispatch). Settling a paused
   Execution without an operator decision is not implemented; this is
   recorded, not worked around.
4. **Shared `workspace_root` across stores.** Stores A and B were
   configured with one `workspace_root` (a shared scenario state root on the host)
   and therefore one `.handoff/repo.git`. The abandoned run-2 store left
   `refs/taisan/artifacts/inv-1/artifact.json` pointing at its
   produced object; every subsequent `inv-1` (and store-A's `inv-2` vs
   store-A's own reference) collided at `acknowledge_stage` and was
   marked `invalid/ref_conflict`: A's `inv-1` (`d9420ec`), B's `inv-1`
   (`a8eeba1`), B's `inv-2` (`0ce0cb5`). Consequences, all recorded
   verbatim: no `verification_results` row for those invocations; the
   Outcomes still froze Present artifact facts (digests cited above);
   the runs completed. No code change was made for this; the fix is
   configuration hygiene (one state root per installation), and the
   evidence records the gap rather than re-running to disguise it.
5. **Missing coding-leg verification.** Because of (4), the coding
   invocations of A's Work and of B's `e-4`/`e-5` recorded no
   `verification_results` row (the shim's own
   `verification_exit: 0` is present in the shim logs and is cited for
   `adce543…`/`0ce0cb…`/`a8eeba1…` at worker level). The Fix-leg verify
   (`verify-1` on `204ab155…` and `6293efe…`) and e-6's coding verify
   (`verify-2` on `adce5436`) **are** present. GitHub-side checks
   (`verify`, `review`) ran on every pushed head and are cited by
   check-run id.
6. **Duplicate create re-arm after an injected failure.** Fault (b)
   produced four `open_change_request` intents for one logical effect,
   bounded by `transport_max_retries = 3`, after which `e-6` paused
   with classification `transport_exhausted` and pause detail
   `transport retry bound reached; human action required`. Recorded
   for follow-up; not altered here.
7. **Terminal retirement race observed as designed.** `rintent-u84a-1`
   was due while `e-3` was still live; it stayed pending (`execution_
   active` hold) and was retired only after `e-3` reached `succeeded`
   (`execution_terminal`). No operator re-enqueue was used anywhere in
   fault (c).
