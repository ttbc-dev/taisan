# v0.1: built-in queue and replaceable control surfaces

## Goal

Prove that a GitHub-based development workloop can accept and complete one real Work item through its own queue without external Kanban system, then run the same command semantics through a second interface. This is a validation milestone, not a promise of general availability.

## Vertical slice

1. Configure an isolated installation with a GitHub repository allowlist, credentials, workspace, built-in queue/state store, and one executor.
2. Submit one Work item referring to one or more GitHub issues with intent, constraints, and a verification command. Query its queued E1 through the CLI before dispatch.
3. Start an Execution with a durable record, explicit ownership, checkpoints, and recorded output. Prove an old worker stopped or cannot write before transferring ownership.
4. Create or update a PR; bind verification and review results to the observed head SHA.
5. Run a bounded review-fix cycle, then record completion or a specific human gate.
6. Inspect, retry, resume, and cancel via the CLI as policy permits.
7. Connect a GitHub issue-comment adapter for status and a subset of the same commands. A Projects status projection is optional after the command path works.

Do not require the TUI, a visual dashboard, multiple executor providers, automatic issue selection, hosted tenancy, or public distribution for this milestone. The built-in queue and its CLI Query are required; the TUI will use the same Query and Command contracts after the vertical slice.

## Slice 0: core-truth harness

The minimal slice proves the lifecycle contract end to end without GitHub or a TUI. Everything below runs on one host against real processes; the implementation language is Rust and the state store is SQLite.

**Components**: commands `submit`, `retry`, `resume`, `cancel`, `acknowledge`, `judge_findings`, `release_judgment`, `claim_resources`, `release_resources`; internal dispatch; the `execution` supervisor with `ProcessControlPort` over real child processes; a fixture worker — a real process that writes to the managed workspace and reports evidence; a fixture GitHub adapter that records `PrActionIntent`s and emits synthetic Observations; the CLI; and Queries `work_list`, `work_detail`, `attention`, `capacity`, `command_result`.

**Excluded**: real GitHub, the TUI, multiple executors, automatic issue selection.

**Layout**: a Cargo workspace — `workloop-core` holds the domain types, `work` decision logic, `projection`, and the port traits with no I/O dependencies; `workloop-store` implements the SQLite store; `workloop-exec` hosts the supervisor and its POSIX `ProcessControlPort`; `workloop-github` implements the GitHub-integration port (fixture in slice 0); `workloop-cli` is the binary and composition root; `workloop-fixture-worker` is the real fixture process the contract tests spawn. Interface crates (CLI today, TUI later) depend on `work` and `projection` only through the Command/Query contracts.

**Verification comes first.** Contract tests are written before the implementation and cover at least:

| Area | Condition proven |
| --- | --- |
| Commands | Idempotent replay of every accepted Command; a payload change under the same key yields `idempotency_conflict`; a lost response is recovered via `command_result`. |
| Admission | `submit`/`retry` accepted at full capacity stay queued; dispatch picks the oldest eligible item; a blocked head does not stall later items and records a diagnostic. |
| Reservations | `retry`/`claim_resources` conflicts return `resource_conflict` with the holder; a dispatch-time conflict defers; claim TTL expiry frees and renewal retains; a `queued` Execution loses to an earlier external claim. |
| Launch | A crash after the `ready` commit replays the request exactly once; a crash near spawn leaves `uncertain` with no second start. |
| Stop proof | Cancel on `running` reaches `cancelled` only after stop proof; a `setsid`-escaped child survives a group signal but the descendant snapshot keeps the Execution `uncertain` until inspected; a zombie counts as stopped and the supervisor reaps its children; an injected persistence failure of the stop intent sends no signal; a supervisor `kill -9` mid-stop resumes from the durable intent after restart. |
| Recovery | Missing required evidence after worker exit runs bounded recovery; exhaustion records `failed`/`artifact_recovery_exhausted` with WIP preserved; `retry` claims the same workspace and branch. |
| Projections | `capacity` explains every slot holder, reservation, and deferral; `uncertain` beyond its threshold surfaces Attention; acknowledgement hides only that version. |

The fixture GitHub adapter exercises the `PrActionIntent → Observation` reconciliation path; the real adapter later runs the same contract tests against GitHub.

## Acceptance scenarios

| Scenario | Pass condition |
| --- | --- |
| No external Kanban system installed | Intake, queue inspection, dispatch, and terminal outcome work through the built-in store and CLI. |
| Capacity unavailable | `submit`, `retry`, or `resume` may be accepted with its Execution queued. Later dispatch reserves capacity once and creates at most one approved Invocation request. |
| Concurrent retry from CLI and GitHub | One new Execution; the other command observes or receives a clear rejection. |
| Queued cancellation races with dispatch | Either cancellation wins before request creation, or the approved request enters stopping/uncertain handling; no late worker is treated as safely cancelled. |
| Duplicate webhook delivery | One command effect under the same idempotency key. |
| Stale external view | Preconditions reject an invalid transition and return current state. |
| Process disappears after dispatch | Status distinguishes execution permission, process liveness, and evidence; recovery never reports a ghost run as healthy. |
| Ownership heartbeat is missed while an old worker may still write | Prevention of the old worker's writes or confirmed termination precedes replacement. |
| Worker escapes the process group or exits leaving unreaped children | The descendant snapshot recorded at stop intent names every identity to signal and inspect; a zombie counts as stopped; any uninspected survivor keeps the Execution uncertain. |
| Two writers target the same managed resource | `retry` and `claim_resources` conflicts are rejected with the current holder; a dispatch-time conflict leaves the Execution queued with a diagnostic. |
| Manual writer works outside the claim path | A claim on the managed branch is rejected as `resource_conflict`; an expired claim forfeits exclusion without proving the writer stopped, and a later unexpected head Observation triggers reconciliation. |
| Paused Work keeps WIP | Its write-resource reservation is retained while paused so another Work or claim cannot take the workspace or branch; the capacity slot is released. |
| Required evidence missing after worker exit | Bounded artifact recovery runs from the workspace, checkpoints, and worker-runtime store; exhaustion records `failed` with preserved WIP, and `retry` can claim the same workspace and branch. |
| Launch response disappears | The approved Invocation is reconciled by its stable identity; no second Invocation is launched from the missing response alone. |
| PR head changes after review | Prior conclusion is stale; review is required for the new head. |
| PR head changes while queued | Dispatch checks the current head; a queued judgment or review input for the old head cannot authorize work on the new head. |
| Review cannot converge within budget | Work stops with evidence and a current human action. |
| Adapter is offline | Core work continues where permitted, result remains queryable, projection catches up later. |
| Command accepted but response lost | Query by command ID or replay key yields the original result without a second effect. |
| Separate installation | Different state and credentials cannot mix Work or evidence. |

## Build order

1. Turn the [lifecycle states and transitions](lifecycle.md) into executable contract tests, then specify the event/evidence schema.
2. Implement the state store, built-in queue Query and dispatch reservation, execution-ownership safeguards, CLI, and a fixture executor.
3. Add GitHub PR/review integration and one real executor for the end-to-end slice.
4. Add the GitHub command adapter and reconciliation.
5. Exercise failure scenarios with deliberate process, webhook, and adapter interruptions.

The milestone is complete when the same Work can be controlled through two independent surfaces, and disconnecting the optional surface does not change execution truth.
