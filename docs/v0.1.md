# v0.1: built-in queue and replaceable control surfaces

## Goal

Prove that a GitHub-based development workloop can accept and complete one real Work item through its own queue without external Kanban system, then run the same command semantics through a second interface. This is a validation milestone, not a promise of general availability.

## Vertical slice

1. Configure an isolated installation with a GitHub repository allowlist, credentials, workspace, built-in queue/state store, and one executor.
2. Submit one Work item referring to one or more GitHub issues with intent, constraints, and a verification command. Query its queued E1 through the CLI before dispatch.
3. Start an Execution with a durable record, explicit ownership, checkpoints, and recorded output. Prove an old worker stopped or cannot write before transferring ownership.
4. Create or update a PR; bind verification and review results to the observed head SHA.
5. Run a bounded review-fix cycle, then record completion or a specific human gate.
6. Inspect, retry, resume, and cancel via the CLI as policy permits.
7. Connect a GitHub issue-comment adapter for status and a subset of the same commands. A Projects status projection is optional after the command path works.

Do not require the TUI, a visual dashboard, multiple executor providers, automatic issue selection, hosted tenancy, or public distribution for this milestone. The built-in queue and its CLI Query are required; the TUI will use the same Query and Command contracts after the vertical slice.

## Slice 0: core-truth harness

The minimal slice proves the lifecycle contract end to end without GitHub or a TUI. Everything below runs on one host against real processes; the implementation language is Rust and the state store is SQLite.

**Components**: commands `submit`, `retry`, `resume`, `cancel`, `acknowledge`, `judge_findings`, `release_judgment`, `claim_resources`, `release_resources`; internal dispatch; the `execution` supervisor with `ProcessControlPort` over real child processes; a fixture worker — a real process that writes to the managed workspace and reports evidence; a fixture GitHub adapter that records `PrActionIntent`s and emits synthetic Observations; the CLI; and Queries `work_list`, `work_detail`, `attention`, `capacity`, `command_result`.

**Excluded**: real GitHub, the TUI, multiple executors, automatic issue selection.

**Layout**: a Cargo workspace — `workloop-core` holds the domain types, `work` decision logic, `projection`, and the port traits with no I/O dependencies; `workloop-store` implements the SQLite store; `workloop-exec` hosts the supervisor and its POSIX `ProcessControlPort`; `workloop-github` implements the GitHub-integration port (fixture in slice 0); `workloop-cli` is the binary and composition root; `workloop-fixture-worker` is the real fixture process the contract tests spawn. Interface crates (CLI today, TUI later) depend on `work` and `projection` only through the Command/Query contracts.

**Verification comes first.** Contract tests are written before the implementation and cover at least:

| Area | Condition proven |
| --- | --- |
| Commands | Idempotent replay of every accepted Command; a payload change under the same key yields `idempotency_conflict`; a lost response is recovered via `command_result`. |
| Admission | `submit`/`retry` accepted at full capacity stay queued; dispatch picks the oldest eligible item; a blocked head does not stall later items and records a diagnostic. |
| Reservations | `retry`/`claim_resources` conflicts return `resource_conflict` with the holder; a dispatch-time conflict defers; claim TTL expiry frees and renewal retains; a `queued` Execution loses to an earlier external claim. |
| Launch | A crash after the `ready` commit replays the request exactly once; a crash near spawn leaves `uncertain` with no second start. |
| Stop proof | Cancel on `running` reaches `cancelled` only after stop proof; a `setsid`-escaped child survives a group signal but the descendant snapshot keeps the Execution `uncertain` until inspected; a zombie counts as stopped and the supervisor reaps its children; an injected persistence failure of the stop intent sends no signal; a supervisor `kill -9` mid-stop resumes from the durable intent after restart. |
| Recovery | Missing required evidence after worker exit runs bounded recovery; exhaustion records `failed`/`artifact_recovery_exhausted` with WIP preserved; `retry` claims the same workspace and branch. |
| Projections | `capacity` explains every slot holder, reservation, and deferral; `uncertain` beyond its threshold surfaces Attention; acknowledgement hides only that version. |

The fixture GitHub adapter exercises the `PrActionIntent → Observation` reconciliation path; the real adapter later runs the same contract tests against GitHub.

## Acceptance scenarios

| Scenario | Pass condition |
| --- | --- |
| No external Kanban system installed | Intake, queue inspection, dispatch, and terminal outcome work through the built-in store and CLI. |
| Capacity unavailable | `submit`, `retry`, or `resume` may be accepted with its Execution queued. Later dispatch reserves capacity once and creates at most one approved Invocation request. |
| Concurrent retry from CLI and GitHub | One new Execution; the other command observes or receives a clear rejection. |
| Queued cancellation races with dispatch | Either cancellation wins before request creation, or the approved request enters stopping/uncertain handling; no late worker is treated as safely cancelled. |
| Duplicate webhook delivery | One command effect under the same idempotency key. |
| Stale external view | Preconditions reject an invalid transition and return current state. |
| Process disappears after dispatch | Status distinguishes execution permission, process liveness, and evidence; recovery never reports a ghost run as healthy. |
| Ownership heartbeat is missed while an old worker may still write | Prevention of the old worker's writes or confirmed termination precedes replacement. |
| Worker escapes the process group or exits leaving unreaped children | The descendant snapshot recorded at stop intent names every identity to signal and inspect; a zombie counts as stopped; any uninspected survivor keeps the Execution uncertain. |
| Two writers target the same managed resource | `retry` and `claim_resources` conflicts are rejected with the current holder; a dispatch-time conflict leaves the Execution queued with a diagnostic. |
| Manual writer works outside the claim path | A claim on the managed branch is rejected as `resource_conflict`; an expired claim forfeits exclusion without proving the writer stopped, and a later unexpected head Observation triggers reconciliation. |
| Paused Work keeps WIP | Its write-resource reservation is retained while paused so another Work or claim cannot take the workspace or branch; the capacity slot is released. |
| Required evidence missing after worker exit | Bounded artifact recovery runs from the workspace, checkpoints, and worker-runtime store; exhaustion records `failed` with preserved WIP, and `retry` can claim the same workspace and branch. |
| Launch response disappears | The approved Invocation is reconciled by its stable identity; no second Invocation is launched from the missing response alone. |
| PR head changes after review | Prior conclusion is stale; review is required for the new head. |
| PR head changes while queued | Dispatch checks the current head; a queued judgment or review input for the old head cannot authorize work on the new head. |
| Review cannot converge within budget | Work stops with evidence and a current human action. |
| Adapter is offline | Core work continues where permitted, result remains queryable, projection catches up later. |
| Command accepted but response lost | Query by command ID or replay key yields the original result without a second effect. |
| Separate installation | Different state and credentials cannot mix Work or evidence. |

## Representative live acceptance scenario

The acceptance-scenario table above proves lifecycle conditions inside the slice-0 harness. This section defines **S1**, the single representative end-to-end scenario that validates the same conditions against a real issue, a real PR, and a real review/fix cycle on GitHub. It is a specification of what must be demonstrated; this milestone defines scope and does not authorize implementation or execution.

### Scenario selection and rationale

The [source workflow audit](source-workflow-audit.md) is the comparison basis. Candidate representative paths:

| Candidate | What it covers | Why it is or is not representative |
| --- | --- | --- |
| hermes scheduler auto-intake → Kanban card → `cw-dispatch` | The fullest source path, including unattended selection | Rejected: card-based queue and cron scheduler are personal-environment mechanisms the audit classifies as omit; they would test machinery v0.1 removes, not the lifecycle being extracted |
| Remote lane (`coding-worker-infra` containers) | Remote admission, SSH transport, container supervision | Rejected: multi-host/container execution is out of v0.1 scope; the audit classifies lane executor matrix and remote admission as omit |
| `devflow ship` standalone path (manual submission → worker → PR → review → converge) | Every retained lifecycle stage without the external board | **Selected**: exercises admission, queueing, dispatch, bounded execution, verification, publication, review/fix convergence, and settlement — exactly the stages v0.1 owns |

**S1** re-models the standalone path: one real issue is submitted manually, executed by a real worker, published as a real PR, reviewed by a real review source, fixed, republished, and reassessed to a terminal Outcome.

**Automatic selection and grouping are not part of S1.** The audit classifies scheduler auto-intake as omit and grouping as selector-internal detail. The representative input is a manual `submit`. The broader milestone acceptance in the [implementation plan](implementation-plan.md) also exercises a reference-Selector proposal as an alternate submission path; that check is outside S1 and must land on the same `submit` Command contract, never around admission. S1 itself requires no automatic issue selection. One Work in S1 references exactly one issue; multi-issue grouping and the relation between group identity and `work_id` remain an open question.

### Scenario definition

| Element | Specification |
| --- | --- |
| Input issue | One real GitHub issue seeded in the isolated test repository, requesting a small deterministic change with an independently checkable result. The issue is engineered so a real review produces at least one finding (e.g., it leaves a review-visible quality gap the reviewer flags). If a review returns zero findings, the review/fix leg is unexercised and the scenario must be rerun with adjusted input — a zero-finding pass does not satisfy S1 |
| Intent and constraints | `submit(intent, issue_refs=[the seeded issue], constraints, verification_argv, idempotency_key=K)`: intent names the change and its definition of done; constraints bound writable paths and forbid force-push; `verification_argv` is the test repository's real verification command |
| Permissions | A GitHub credential scoped to the test repository only (contents and pull requests read/write, issues read/write, checks read), recorded in installation config as a credential reference — never a value. The worker receives `AllowedEffects{workspace_write, local_git_write, github_write: false}`; every GitHub mutation funnels through a persisted `PrActionIntent` applied by the GitHub adapter |
| Runtime environment | One host, one workloop installation: SQLite state store, managed workspace root, real GitHub adapter, the reference Worker adapter, network access to GitHub. No external Kanban service, cards, or database; the built-in queue in the store is the only state authority |
| Observed facts | `issue`, `pr_head`, `check`, `review`, and `pr_action_result` Observations — each check and review bound to the head SHA it examined |
| Stage owners | Intake: operator via CLI `submit` (or reference Selector proposal). Admission, queue, dispatch, budget, settlement: `work`. Process supervision and stop proof: `execution`. Coding/review/fix attempts: the Worker adapter under Invocation requests. Publication and fact ingestion: GitHub adapter. Finding judgments: operator via `judge_findings`/`release_judgment` (or declared policy). Merge/deploy: a human decision outside the scenario |

### Expected path

1. `submit` accepted → `W1` and `E1` `queued` in one commit; `work_detail` shows no Invocation.
2. Internal dispatch: capacity slot, write-resource reservation (`workspace` + `(test-repo, work/<work_id>)`), and the first Invocation request commit atomically → `E1 ready` → `I1` (`coding` role) `running`.
3. `I1` produces the change artifact in the managed workspace; `verification_argv` passes with evidence bound to `I1`.
4. `work` saves `publish_pr` `PrActionIntent`; the GitHub adapter pushes `work/<work_id>` and opens the PR → `pr_action_result: applied` and `pr_head` Observation `H1`.
5. Real checks and a real review arrive on `H1` as Observations; the review carries at least one finding.
6. `judge_findings` (`expected_pr_head H1`) → `fix` → fix-stage `I2` → `update_pr` with `expected_head H1` → new head `H2`.
7. Reassessment on `H2`: required checks pass and the review for `H2` shows no unresolved finding.
8. `work` records `succeeded`: the Outcome stores the PR reference and verified head `H2`, the passing checks, the `H2` review evidence, and writer-stop evidence.

Branches off this path:

- Failed checks or further findings → another bounded fix round under the same Execution.
- A review finding requiring human judgment per policy → `paused(human_judgment)` → Attention → `judge_findings` → `release_judgment` → requeue.
- An external head change stales current evidence → a new review/judgment on the live head, never a silent rebind.
- Budget or deadline exhaustion → `stopping` or `uncertain` (desired `fail`) until writers and outstanding effects are safe, then `failed` with the exhausted limit recorded → Attention offering retry/repair decisions.
- Unresolved ownership or evidence uncertainty past its threshold → `uncertain` holds capacity → Attention.

Every terminal path ends in `succeeded`, `failed`, `cancelled`, or an actionable Attention — never a silent stall.

### Abnormal-input matrix

| Injected condition | Expected states | Verification evidence |
| --- | --- | --- |
| Duplicate `submit` (same key and payload) | Original `accepted` decision replayed; one Work, one Execution | `command_result` returns the saved decision; store holds a single W/E |
| Duplicate `submit` key with changed payload | Rejected `idempotency_conflict`; no state change | Recorded rejection with original retained |
| Duplicate Observation delivery (same source event) | One effect; the duplicate recorded as `duplicate` | `IngestReceipt` and event log |
| Installation stop/restart while an Invocation may be live | On restart, the approved request is reconciled against recorded process evidence; no second writer starts while the old one is unproven | Restart leaves the Execution `uncertain` or correctly `running`; descendant snapshot + PID/start-time re-verification in evidence |
| Publication result unknown (push/PR-create response lost) | The intent is reconciled by `action_id`, branch, and PR existence; a matching effect is adopted; an ambiguous result fails closed | `pr_action_result: unknown` → reconciliation evidence; no second `publish_pr` for the same artifact |
| Stale review or stale head (review for `H1` arrives after head moves to `H2`) | The review remains evidence for `H1` only; `judge_findings` carrying `expected_pr_head H1` is rejected `stale_pr_head`; a delayed old-head webhook never moves the current head backward | Rejection evidence; projection shows `H2` as unreviewed |
| GitHub adapter outage | Observations marked `unavailable`; `QueryResult.sources` distinguishes "no findings" from "review source unavailable"; execution continues where policy permits and the projection catches up on restore | `availability` on `QueryResult.sources` in query results; recovery Observations after restore |
| Budget exhaustion (`max_invocations`, `max_review_rounds`, or `runtime_limit_seconds`) | `stopping` or `uncertain` (desired `fail`) while a writer, request, or external effect may still act; `failed` with the exhausted limit code once safe, with WIP and evidence preserved; Attention offers the retry/repair decision; `retry` creates `E2` claiming the same workspace and branch | Stop/reconciliation evidence, terminal Outcome with limit code and preserved evidence; `E2` reservation records |

### Completion boundary

`succeeded` means verified completion: required checks pass on the recorded head, the review evidence for that head has no unresolved finding, writers are confirmed stopped or prevented from writing, and no `PrActionIntent` remains unresolved. It does **not** mean merged or deployed; merge and deploy are separate human or future-policy actions and are never performed by the scenario. A head change after `succeeded` does not rewrite the Outcome, but the PR-readiness Projection must show the newer head as unreviewed; follow-up requires a new Work item.

### Isolated environment, rerun, and cleanup

- **Test repository**: a dedicated, allowlisted repository owned by the installation operator (e.g., `workloop-e2e`); the installation allowlist contains only it. Seeded input issues are created by a documented fixture procedure.
- **Credentials**: the scoped credential reference above, plus whatever the configured worker runtime requires; both live in installation config, never in the repository or evidence exports.
- **Rerun**: S1 is rerunnable — each run submits a new Work against a freshly seeded issue (and therefore a fresh `work/<work_id>` branch) on the same test repository.
- **Cleanup**: cancel any in-flight Work; external claims and reservations are released through the terminal path. PRs, issues, checks, and reviews produced by a run are retained as evidence and are never deleted by cleanup; only seeded inputs may be reset.
- **Evidence retention**: the `event_log`, Command keys and decisions, Invocation records, and evidence references are retained indefinitely in v0.1. Exported or summarized evidence carries bounded codes and stable references (PR number, head SHA, check identity), never raw remote text or secrets.
- **Fixture boundary**: passing slice-0 contract tests and fixture-adapter tests does **not** satisfy live-integration acceptance. S1 requires real GitHub reads and writes, a real worker, and real review evidence; a fixture-only green run is recorded as live acceptance unexercised, never as success.

### Execution evidence validity

Whether evidence supports a stage assessment is decided by three classes:

| Class | Meaning | Effect on the scenario |
| --- | --- | --- |
| Absent | No recorded Invocation, Observation, or artifact covers the fact being assessed | The stage cannot be assessed; success must not be claimed. Reconciliation or bounded artifact recovery runs; exhaustion or an unavailable source surfaces Attention |
| Valid | The evidence's Invocation ID, PR head, and required checks all match the stage being assessed | The evidence may satisfy the stage's pass condition |
| Invalid | Evidence exists but contradicts the stage: wrong head, a different Invocation, a missing required check, or a prose worker claim without artifacts | Counts as evidence against the claim and drives the corresponding failure or branch path; it is never dropped or relabeled |

A check that passed on `H1` is not valid evidence for the `H2` reassessment; a review finding attached to `I1` cannot close a stage assessing `I2`.

### Design aspects of this scenario

Following the audit and the issue, each aspect records applicability, rationale, and open questions for S1 — no rule beyond the settled contracts is decided here.

| Aspect | Applicability in S1 | Rationale | Open questions |
| --- | --- | --- | --- |
| State transitions | Traverses `queued → ready → running → waiting → (fix rounds) → succeeded/failed/paused` | S1 exercises the retained atomicity — transition, reservation, and request in one commit — against real external waits | Whether `waiting` for checks versus `waiting` for review needs distinct recorded reasons in the v0.1 projection |
| Failure semantics | Unknown publication, uncertain stops, stale heads, and budget exhaustion are explicit branches | Tri-state results (`applied`/`failed`/`unknown`, liveness tri-state) are the audit's retained distinctions | Whether an `evidence_unavailable` terminal class is needed beyond `failed` codes (audit open question) |
| Trust boundaries | Worker `github_write: false`; publication only via `PrActionIntent`; worker reports are evidence; reviewer text is bounded | Retained from hermes-setup #389 (double publication) and #445 (verdict without effect) | Per-adapter credential and permission scope (issue #35); whether a declared-risk review gate belongs in v0.1 |
| Identity invariants | `work_id`/`execution_id`/`invocation_id`/`action_id` are the scenario's identities; issue/PR numbers and head SHAs are references | Retained: external identifiers were never stable identities in the source | How `work_id` relates to multi-issue group identity and any external card IDs — S1 deliberately stays single-issue; finding-ID durability across review surfaces |
| Information preservation | `event_log`, evidence refs, findings history, and preserved WIP carry the scenario's memory across restart | Direct response to prune/reclaim evidence loss in the source | Retention-versus-export-safety minimums (decisions.md Q4); artifact digest requirements |
| Resource bounds | `max_invocations`, `max_review_rounds`, `runtime_limit_seconds`, claim TTLs, artifact-recovery bounds, uncertain threshold | Re-modeled from previously implicit operational limits; per-run bounds are already settled — artifact recovery is bounded separately from Invocation budgets and the uncertain threshold has a recorded default | Per-host versus per-repository capacity scope; artifact-disposition state modeling |

## Worker adapter interchangeability

A separate acceptance item from S1: v0.1 must also demonstrate that the Worker port is interchangeable, not just usable by one implementation. This validates the [adapter boundary](adapter-boundaries.md); it does not weaken S1's requirement for a real worker and real GitHub.

**Boundary.** Worker-specific launch mechanics, request/result translation, authentication to the worker runtime, internal session state, and resume behavior live inside the adapter. Core types, state transitions, and Outcome decisions carry no product-specific assumptions. The adapter is selected through installation config only — today the `worker_argv` entry point — with no Core change.

**What v0.1 proves.** Two conforming implementations run behind the unchanged Core contract: the reference real Worker adapter used by S1, and a second, independently implemented contract-verification adapter (a scripted implementation that replays deterministic results and exercises the failure paths — it is not required to be a real coding agent). The shared Worker contract suite runs against both, covering lost start response, duplicate request delivery, unobservable liveness, stop proof, missing artifacts, and stale-head evidence, plus the swap-invariance check: Command, queue, budget, and Outcome semantics are identical under either adapter.

**Explicit non-claims.** Passing the contract-verification adapter does not satisfy S1 — S1 requires real GitHub reads and writes, a real worker, and real review evidence. Compatibility between two real Worker implementations is not verified in v0.1; multiple production-grade worker providers are deferred. Interchange applies to new Invocation requests only — a running Invocation is never handed to a different Worker, adapter-internal saved state is not migrated, and no dynamic plugin mechanism is required. Optional capabilities such as `resume` are declared per adapter and are never silently emulated.

## Build order

1. Turn the [lifecycle states and transitions](lifecycle.md) into executable contract tests, then specify the event/evidence schema.
2. Implement the state store, built-in queue Query and dispatch reservation, execution-ownership safeguards, CLI, and a fixture executor.
3. Add GitHub PR/review integration and one real executor for the end-to-end slice.
4. Add the GitHub command adapter and reconciliation.
5. Exercise failure scenarios with deliberate process, webhook, and adapter interruptions.

The milestone is complete when the same Work can be controlled through two independent surfaces, and disconnecting the optional surface does not change execution truth.
