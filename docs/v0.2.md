# v0.2: installation, scheduled intake, and owner-run acceptance

Status: v0.2 documentation. This guide publishes the clean-install
path, one-adapter intake operation, and the owner-run acceptance
material for the public reference path and a configuration-only generic
adapter replacement. It reuses the completed v0.1 proposal, submit,
source-overlap, execution, and Outcome contracts. It authorizes no live
execution by the implementing agent and claims no owner-run result.

The normative scheduler and reload semantics live in the
[execution loop](execution-loop.md#intake-scheduling), the protocol and
its bounds in the [Selector protocol](selector-protocol.md), and the
configuration schema in [installation configuration](installation-config.md).
This page is the operator-facing walkthrough over those contracts.

## What v0.2 adds

- **One Selector adapter per installation.** Exactly one
  `[intake.selector]` binding exists in `config.toml`. The binding
  names the adapter identity, selection-semantics version, policy
  revision, and direct argv vector. A second declaration, duplicate
  key, or unknown field is refused structurally.
- **An internal scheduler, not an OS timer.** `taisan run` hosts the
  scheduler next to the execution loop. It evaluates intake state on a
  fixed **60-second settings tick**. No cron entry, systemd unit,
  launchd job, or separate intake daemon is required or specified.
- **Durable one-shot intake.** `taisan intake` runs one invocation
  under the same durable single-flight lease as the scheduler. It works
  while automatic intake is disabled; it only needs a configured
  selector binding.
- **History as a Query contract.** `taisan intake-runs` and
  `taisan intake-detail` expose recorded runs and candidates from the
  store. Nothing is scraped from logs.
- **Configuration-only adapter replacement.** A configuration-only
  adapter swap changes only `[intake.selector].adapter` and `argv`,
  selecting another conforming adapter at the next settings tick. Core,
  queue, execution, and Outcome semantics do not change.

## Documented defaults

These are the v0.2 defaults when the keys are omitted. They are
internal to `taisan run` or read from the durable settings record;
no OS timer is required.

| Setting | Default | Effect |
| --- | --- | --- |
| Selector bindings | exactly one `[intake.selector]` | One adapter identity per installation. Manual `submit` remains available without it. |
| `intake.enabled` | `false` | Automatic scheduled intake is off. The one-shot `taisan intake` verb still works. |
| `intake.interval_minutes` | `30` | Scheduled runs are 30 minutes apart on the internal grid. |
| Settings tick | `60` seconds | The scheduler reloads and re-validates `config.toml` on each tick, independent of the execution pass cadence. |
| `intake.timeout_seconds` | `120` | The adapter invocation deadline; at most 300 seconds. |
| `intake.pending_queue_limit` | `10` | Installation-wide bound on queued Work; applies to manual and Selector submissions inside the submit transaction. |
| Execution pass interval | `30` seconds | `taisan run` pass cadence, independent of the intake grid. |
| Tick deadline | `120` seconds | The execution pass stops starting new work and reports unfinished items for the next pass. |

The intake timeout and the execution tick deadline are separate bounds
even though both default to 120 seconds. The timeout covers one adapter
exchange; the tick deadline covers one execution pass.

## Clean install

### Prerequisites

- Rust with edition 2024 support, to build this checkout.
- One host and one installation: one config file, one state directory,
  one SQLite store.
- A source-host credential scoped to the reference repository, supplied
  as a credential reference (`env:`, `file:`, or `command:`), never as
  a literal in the config or on argv.
- A conforming Selector executable on the configured argv path. The
  packaged `public-issue-selector` is the public reference; any
  conforming adapter can replace it by configuration.

No public ingress, external board, database service, or OS scheduler is
required.

### Build and install

```sh
git clone https://github.com/shimpeiws/taisan.git
cd taisan
cargo build --workspace
cargo install --path crates/workloop-cli --bin taisan
```

The workspace contract tests spawn the fixture worker binary, so build
the workspace before running the tests.

### Configure

The versioned profile is `config.toml`. Resolve it through `TAISAN_CONFIG`
or the XDG default; resolve state through `TAISAN_STATE_DIR` or the XDG
default. An explicit flag, when used, must name an absolute path.

```sh
export TAISAN_CONFIG="$HOME/.config/taisan/config.toml"
export TAISAN_STATE_DIR="$HOME/.local/share/taisan"
export TAISAN_GH_TOKEN=...   # resolution stays at the adapter boundary
mkdir -p "$(dirname "$TAISAN_CONFIG")" "$TAISAN_STATE_DIR"
```

The sanitized, structurally valid example is
[`docs/examples/v0.2/config.toml`](examples/v0.2/config.toml). It uses
placeholder identities, a publication repository, a distinct reviewer
role, and exactly one intake selector. Copy it and replace the observed
identities, repository id, actor names, credential references, worker
argv, and adapter argv with the values your adapter reports.

The intake block starts disabled, so the clean install cannot begin
scheduled intake by accident:

```toml
[intake]
enabled = false
interval_minutes = 30
timeout_seconds = 120
pending_queue_limit = 10

[intake.selector]
adapter = "public-issue-selector"
selector_version = 1
policy_revision = 1
argv = ["public-issue-selector", "select", "--github-endpoint", "https://api.github.com"]
```

`pending_queue_limit` is installation-wide and applies even while
`enabled = false`; disabling automatic scheduling does not release the
admission bound. The selector inherits source-read authority from the
repositories declared with `use = "source"` or `use = "publication"`.
No credential reference belongs in `[intake]`.

### Validate before operating

`taisan check` is the ordered, read-only, fail-closed preflight over the
profile. It creates no Work and mutates no config or remote state.
`taisan check --probe` adds the opt-in read-only adapter capability
read.

```sh
taisan check
taisan check --probe
```

A non-passing stage names the failed prerequisite and stops later
stages; fix the named key, path, credential reference, runtime, or
isolation primitive before continuing. `check` success is a validated
configuration, never a standing grant or a live acceptance result.

## Operation walkthrough

The sequence below is what an owner runs. Each step states its expected
result; a command transcript is not proof unless the evidence record
links the exact command, revision, and result.

### 1. Install, configure, and verify

Run the build, install, and `check` commands above. Keep `enabled =
false` for the first intake exercise.

Expected: both checks exit zero with structured per-stage passes, or
the exact failing stage is named. No Issue, Work, or remote write was
created by the checks.

### 2. Run one explicit intake with automation disabled

`taisan intake` is a one-shot driver. It acquires the intake lease,
launches the configured argv once, validates the whole response, admits
candidates through the normal submit path, and reports the recorded run.
It is synchronous and does not depend on `enabled = true`.

```sh
taisan intake
taisan intake-runs --limit 5
taisan intake-detail --run <run-id>
```

Expected: one run record with trigger `manual`; candidates are reported
in order as `accepted`, `replayed`, `rejected`, `capacity_deferred`, or
`unknown`. A missing profile or selector is a bounded config refusal,
not a crash. A busy lease refuses `intake_busy` without launching a
second adapter. With `enabled = false`, no scheduled run exists.

### 3. Enable and disable automatic intake

Enable intake by editing the profile, then start the loop:

```toml
[intake]
enabled = true
```

```sh
taisan run
```

Expected: on process start with intake enabled, the first run is
immediately due. The scheduler then advances `next_due` by whole
intervals on the internal grid. Setting `enabled = false` is observed on
a later 60-second settings tick: the pending due is cancelled and no
new automatic run starts. An in-flight invocation is not killed; its
durable run and lease carry it to completion or restart recovery.

### 4. Observe startup, interval change, and restart

- **Startup:** with intake enabled and no active run, intake is
  immediately due; the schedule anchors from that startup rule rather
  than replaying missed slots.
- **Interval change:** change `interval_minutes` and wait for the next
  settings tick. `next_due` resets to that reload tick plus the new
  interval; it does not catch up or fire a burst. A change from 30 to
  10 waits the new interval from the reload, not from the old slot.
- **Adapter or policy change:** changing only the selector binding
  preserves `next_due`; adapter identity never moves the schedule.
- **Restart:** stop `taisan run` at a phase boundary. On restart, a
  live/uncertain intake run is reconciled through its durable record and
  lease-owner evidence; with no active run and intake enabled, the
  startup rule makes intake due again. Missed periods collapse to the
  next future grid point; there is no catch-up burst.
- **Busy slot:** a due time that arrives while a run is active is
  skipped, not queued, and no second adapter is launched.

### 5. Replace the adapter by configuration only

Keep one `[intake.selector]`. Replace `adapter` and `argv` with the
conforming adapter's identity and executable:

```toml
[intake.selector]
adapter = "another-conforming-selector"
selector_version = 1
policy_revision = 1
argv = ["another-conforming-selector", "select"]
```

Wait for the next settings tick. Expected: the new binding is resolved
atomically; `next_due` is preserved; an in-flight invocation finishes
under the settings it captured; accepted Work keeps its recorded
profile, repository/credential binding, budgets, and unresolved effects.
No Core change, code edit, or restart is required for the swap. The
optional generic adapter is validated separately by its own owner; it
is not a release dependency of the public reference path.

### 6. Inspect history and Work

```sh
taisan intake-runs --limit 20
taisan intake-detail --run <run-id>
taisan work-list
taisan work-detail --work <work-id>
taisan capacity
taisan command-result --origin selector --replay-key <proposal-key>
```

Expected: run history is newest-first with trigger, state, bounded
detail code, settings revision, and candidate counts. Detail preserves
candidate order and links each candidate to its command and Work
decision. `work-list` and `work-detail` show the admitted Work through
the existing lifecycle. `capacity` explains occupied slots and pending
positions. Replaying a proposal key returns the saved decision; it does
not create a second Work.

### 7. Stop the loop

`taisan run` is a foreground process, not a daemon contract. Send
SIGINT/SIGTERM; the current phase boundary finishes and the process
exits. A selector invocation is not killed by the loop; its durable run
record and lease ownership are recovered on the next start. No OS timer
or supervisor tree remains behind.

## Evidence classes and the live boundary

Every result recorded for v0.2 must be labeled with exactly one of
these classes:

| Label | Produced by | What it can satisfy |
| --- | --- | --- |
| **automated fixture/contract evidence** | Scripted adapters, fixture sources/workers, in-memory or temporary SQLite stores, contract tests, the automated v0.2 matrix | Contract, validation, scheduling, reload, recovery, and interchange behavior in the test harness |
| **owner-run live evidence** | A real installation with real eligible Issues, real source reads, an owner-supplied worker, and real host effects under owner authorization | The owner-run live acceptance criteria only |

A fixture result never marks an owner-run live criterion as passed. A
green contract suite can support a claim about the queue, scheduler, or
protocol; it cannot support a claim about live selection quality, a real
Worker, real GitHub reads/writes, or an owner-run installation. A live
result is recorded separately, with its tested revision, sanitized
profile, commands, timestamps, observed results, and durable
run/proposal/command/Work links.

The automated cross-component matrix and its remaining gaps are in the
[v0.2 intake end-to-end acceptance matrix](evidence/v0-2-intake-e2e-218.md).
The owner-run material is:

- [Owner-run acceptance checklist](v0.2-owner-run-checklist.md) — who
  does what, which scenarios, and the expected result for each.
- [Owner-run evidence template](v0.2-evidence-template.md) — the
  record to copy, fill, label, redact, and retain.

## Boundaries

This guide changes no execution, review, or convergence policy. It adds
no automatic merge or deploy path, no dependency on private
integrations, and no second production host. Optional generic adapters
may be validated separately by their owner without becoming a release
dependency.

Preparing this documentation creates no live Issues, enables no
normal-installation automation, and launches no real Workers. A live
owner run additionally requires explicit owner authorization and the
separate owner-run review described by the checklist.
