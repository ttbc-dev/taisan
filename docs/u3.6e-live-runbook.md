# U3.6e live scenario runbook — issue #119

How to execute the five separately authorized isolated live GitHub
cases of #119 (slice U3.6e of #107). Every case drives the real
`GitHubAdapter` over the `gh` CLI transport (`GhCliApi`) against an
isolated installation and repository, and retains one
`live_evidenced` evidence record per run. The companion authorization
document is [`u3.6e-authorization.md`](u3.6e-authorization.md) — the
owner records per-scenario approval there before any run.

## Authorization boundary

A live run is authorized **per scenario**. `TAISAN_U36E_AUTH` must
cite the recorded owner authorization for the scenario being run —
the issue comment or approval record URL. The harness refuses before
any host call when it is absent: no authorization reference, no live
claim, and the scenario stays `unexercised`/`requires_live` in the
consolidated record.

Fixture results never satisfy a live claim. A scenario whose
authorization is withheld is recorded `not_authorized` (see
*Withheld authorization* below) — never silently skipped.

## Prerequisites

- Rust toolchain per `rust-toolchain.toml`; `cargo build --workspace`
  is not required for these tests but `cargo test -p workloop-github`
  builds what it needs.
- The `gh` CLI on `PATH` (or `TAISAN_U36E_GH` naming the executable),
  authenticated for the isolated repository — `GH_TOKEN` /
  `GITHUB_TOKEN` in the environment or a prior `gh auth login
  --with-token`. No browser flow is required.
- For `live_denied_permission_refused`: a **read-only** credential in
  `GH_TOKEN` — a token without write scope on the isolated repository.
- An isolated repository the scenarios may mutate: scratch branches
  `u36e/*` are created and deleted, one pull request is opened and
  closed, one comment is posted. Never point this at a working
  repository.
- Two distinct commit SHAs on the isolated remote for the push and
  stale-head cases — `TAISAN_U36E_SHA` / `TAISAN_U36E_SHA_B`, or the
  two newest commits on the default branch are used automatically.

## Environment

| Variable | Required | Meaning |
| --- | --- | --- |
| `TAISAN_U36E_REPO` | yes | `owner/name` slug of the isolated repository |
| `TAISAN_U36E_INSTALL` | yes | installation id recorded in `isolation_scope` |
| `TAISAN_U36E_AUTH` | yes | the recorded per-scenario owner authorization reference |
| `TAISAN_U36E_GH` | no | `gh` executable path (default: `gh` on `PATH`) |
| `TAISAN_U36E_SHA` | no | first remote commit SHA (default: newest default-branch commit) |
| `TAISAN_U36E_SHA_B` | no | second distinct remote commit SHA (stale-head case) |

## Running a scenario

Each scenario is an `#[ignore]`d test in
`crates/workloop-github/tests/u36e_live.rs`. Run exactly one at a
time, after its authorization is recorded:

```bash
TAISAN_U36E_REPO=owner/isolated-repo \
TAISAN_U36E_INSTALL=install-u36e-1 \
TAISAN_U36E_AUTH=https://github.com/shimpeiws/taisan/issues/119#issuecomment-<id> \
cargo test -p workloop-github --test u36e_live -- --ignored --exact <test-name> --nocapture
```

| Test | Failure mode | What it does on the remote |
| --- | --- | --- |
| `live_partial_push_then_create_failure` | `partial_effects` | pushes `u36e/partial-*` at a remote SHA, then attempts a change-request create into a nonexistent base — push applies, create refuses (422), receipts stay independent; branch deleted after |
| `live_lost_response_reconciles_by_marker` | `lost_responses` | wraps `gh` so the first comment POST's response is dropped after the effect lands; intent records `unknown`, a clean reconcile pass settles it by marker without reposting; PR closed and branch deleted |
| `live_stale_head_refused` | `stale_head` | seeds `u36e/stale-*` then moves it externally; the guarded write refuses `stale_head`, remote position verified unchanged; branch deleted |
| `live_duplicate_delivery_single_effect` | `duplicate_events` | opens a real PR, delivers the same webhook event twice — second delivery deduplicates, exactly one PR exists for the branch; PR closed and branch deleted |
| `live_denied_permission_refused` | `permission_drift` | attempts a ref write with the supplied (read-only) credential — the refusal is definite `failed`, never `unknown`; branch deleted if created |

A passing run writes `target/u3.6e-records/<scenario>.json` — a
`live_evidenced` `EvidenceRecord` carrying `authorization_reference`
(the `TAISAN_U36E_AUTH` value), `isolation_scope`
(`{installation_id, repository}`), action identities, observation
identities and remote read-back receipts. The record validates against
the U3.6a schema before it is written; a schema violation panics
rather than retaining a bad record.

## Recording the results

After each authorized run:

1. Copy the retained record's salient fields into the consolidated
   record `docs/evidence/u3.6d.md`: replace the scenario's `github`
   row (`unexercised`/`requires_live`) with the live result —
   `scenario_record_ref` pointing at the retained record, `claim_class`
   `live_evidenced`, the tested revision, config identity and result —
   and add the record to the record index. Update the claims-boundary
   paragraph and the tested-revision table for the slice that carries
   the records.
2. For a scenario whose authorization is **withheld**, retain a
   `not_authorized` record instead: `claim_class: "not_authorized"`,
   `result: "skipped"`, empty `action_identities` /
   `observation_identities` / `read_back_receipts`, no
   `authorization_reference`, and `isolation_scope` naming the
   intended scope. The schema rejects any other shape; the
   consolidated row stays `unexercised` with the reason updated to
   cite the withheld authorization.
3. Commit the doc updates on the #119 branch; the named doc checks in
   `crates/workloop-cli/tests/u36d_docs.rs` keep the table honest —
   a `requires_live` row may only flip to a real result when its
   record carries both authorization and isolation evidence.

## Transport note (v0.1 → v0.2)

`GhCliApi` is the v0.1 transport: it shells out to `gh api`, passes
credentials through the environment (never argv), and maps definite
refusals to `ApiError::Refused` and uncertain outcomes to
`ApiError::Unknown`. The `GitHubApi` trait is the stable seam — a
direct HTTPS transport planned for v0.2 replaces `GhCliApi` without
touching `GitHubAdapter` or Core, and must pass the same contract
suites (`tests/github_adapter.rs` fixtures and
`tests/gh_cli_transport.rs` transport checks) unchanged. Until that
migration, `gh` on the host is a documented prerequisite; `gh auth
login` itself is not — a `GH_TOKEN`-style credential suffices.
