# v0.3 manual-acceptance operator checklist — issue #270

This checklist is the literal, command-by-command operator sequence for
the explicitly owner-authorized, single isolated-repository, real-Worker
manual end-to-end run that
[issue #270](https://github.com/ttbc-dev/taisan/issues/270) requires.
It prepares instructions only — it authorizes nothing, and no Phase-B-or-later
command may run before the owner records the authorization Phase A asks
for.

Scenario semantics are defined by the canonical
[v0.3 owner-run checklist](v0.3-owner-acceptance-checklist.md); this file
reuses its scenario ids (M-1…M-9) without redefining them and supplies
the literal commands plus the record target for each step. Installation,
configuration, drain, and rollback semantics come from the
[installation guide](v0.3-installation.md); this file does not repeat
them. The scheduler scenarios S-1…S-6 are #271 scope and are excluded.

Every result lands in the
[#270 evidence record](evidence/v0.3-manual-acceptance.md). Rules that
bind every step:

- A live row is never marked `pass` from a fixture or contract result.
- A step that did not run is recorded `unexercised` with a reason.
- A mutation that returns `unknown` or loses its response is recovered
  through `taisan --db "$DB" command-result --origin cli --replay-key <key>`
  or an identical replay — **never** by minting a fresh idempotency key.
- No merge, deploy, or auto-merge: the run ends with the change request
  open.
- Any credential value appearing in a retained surface is an incident:
  stop, redact, rotate, then continue.

## 0. Names used below

Set these once and keep them consistent across every phase.

```bash
export TAISAN_CONFIG="$HOME/.config/taisan/config.toml"   # TOML profile
export TAISAN_STATE_DIR="$HOME/.local/share/taisan"       # state root
DB="$TAISAN_STATE_DIR/store.db"                           # durable store
CFG="$TAISAN_STATE_DIR/store.config.json"                 # installation record
EVID="<run-state-dir>/evidence"                           # retained envelopes
REPO="<owner>/<name>"      # the ONE isolated repository
ISSUE=<issue-number>       # the real eligible Issue on $REPO
TAISAN=(taisan --db "$DB" --idempotency-key)               # prefix for mutations
```

For the production `github` driver the bound `repository` id **is** the
`owner/name` slug: `GhCliApi::slug` builds `repos/{slug}` calls straight
from the recorded `repository` value and refuses anything that is not
`owner/name`. So `$REPO` is the value the installation record's
`repository` key must carry. The profile's
`[[hosts.<alias>.repositories]] id` is a separate identity — the
adapter-resolved stable repository id (for `github`, the host-issued
numeric `id`, e.g. from `gh api repos/$REPO --jq .id`), with `display`
carrying `owner/name` as metadata only, never an equality key (see
[installation-config](installation-config.md)); each
`identity_evidence.<role>.repository` records that same observed stable
id. What `taisan check` proves here is narrower than that consistency:
preflight validates the profile's observed
`identity_evidence.<role>.repository` against the ids declared under the
bound host — it loads the JSON installation record only for the declared
verification boundary paths, so keeping the record's `repository` equal
to `$REPO` is the operator's own responsibility. A drift between the two still passes `check` and then
drives `repos/{slug}` calls at the wrong repository. A host-issued
numeric `id`/`node_id` is the profile's stable id — never the
installation record's bound value. (The sanitized `docs/examples/v0.3`
placeholders show that numeric shape in the record's `repository` too;
do not copy it into a real record — there the slug is required.)

`--idempotency-key` is a global flag; give every mutation its own stable
key (`<run>-submit`, `<run>-judge-h1`, `<run>-ack-1`, …) and record the
`(origin=cli, actor, key) → command_id` triple. Read-only queries
(`work-list`, `work-detail`, `attention`, `capacity`, `anomalies`,
`command-result`, `evidence …`) need no key. `<expected-version>` in
every mutation is the `version` field of `work-detail --work <id>` read
immediately before the command — the optimistic-concurrency token.

## Phase B — success sequence (M-1…M-7, one Work)

### B.1 Resolve the Issue identity and submit (M-1)

```sh
gh api "repos/$REPO/issues/$ISSUE" \
  --jq '{revision: .updated_at, title, body, state}' | tee "$EVID/issue.json"
python3 - "$EVID/issue.json" <<'EOF' | tee "$EVID/issue-digest.txt"
import hashlib, json, sys
d = json.load(open(sys.argv[1]))
print(hashlib.sha256(
    ("s1-issue-v1:" + d["title"] + "\n" + (d["body"] or "")).encode()
).hexdigest())
EOF
```

`revision` is the host's `updated_at`; the digest is the canonical
`s1-issue-v1` issue-content digest (`workloop-core` `issue_content_digest`)
— exactly the values `submit` requires, never fabricated.

```sh
"${TAISAN[@]}" "<run>-submit" submit \
  --intent "<intent>" \
  --issue "$REPO:$ISSUE" \
  --issue-revision "<revision>" \
  --issue-digest "<digest>" \
  --constraint "<text>" --verification "<argv>" \
  | tee "$EVID/10-submit.json"
# expected: accepted envelope — command.id cmd-…, work_id w-…, execution_id e-…
```

Record `cmd-…`/`w-…`/`e-…`; `accepted` means durably queued, not done.
Replay check: `taisan --db "$DB" command-result --origin cli --replay-key <run>-submit`
returns the same decision — evidence for the idempotent surface.

### B.2 Drive the loop — real coding (M-1)

```sh
taisan --db "$DB" run --interval 15        # foreground; runs until SIGINT
taisan --db "$DB" work-detail --work w-N   # poll from a second terminal
```

Expected: dispatch admission binds the immutable `taisan.worker.request/2`
body (`worker_request_bodies` row per Invocation), launches the real
Worker under the recorded argv/profile, and one Coding Invocation
reaches `Done` with the artifact `Present` + digest and a produced
commit in the managed workspace. Capture the per-Invocation wire set
(request body digest, `report.json` digest, `describe` binding) —
retain `work-detail` envelopes as `$EVID/20-work-detail-*.json`.
The Worker's `report.json` and `claimed_head` are claims, not facts.

### B.3 Independent verification (M-1)

Expected: `VerificationResult` rows come from the **supervisor's own
runner** re-executing the declared `--verification` argv against the
produced commit in a detached worktree — never a Worker-claimed check.
Record the `verification_results` ids, argv, and exit evidence.

### B.4 Invariant assessment (M-2)

Expected: one `invariant_check` Invocation on the exact produced
artifact with the configured `invariant_set` — `Done` **and** a proven
process exit `0`; `/workspace` read-only for that role; the request
carries invariant ids, not Worker-fetched bodies. A non-zero or
unverifiable exit must not open the publish gate; record the observed
gate behavior either way.

### B.5 Publication — head H1 (M-3)

Expected: `maybe_publish` records then applies `push_ref` (branch
`work/w-N` at the produced digest, receipt `applied` with
`ref_published` read-back) then `open_change_request` (receipt
`applied`, a real change request bound to that head). Record both
`action_id`s, receipts, the PR number, and the published head as **H1**.
Verify on the host: `gh pr list --repo "$REPO" --head "work/w-N"`.

### B.6 Real review with at least one finding (M-4)

```sh
# The review must be posted under the identity bound as
# host_actors.review in the installation record — a review reported by
# any other actor is recorded as an observation but never seals the
# round (seal_round's actor binding).
#
# Primary: an inline file-level finding — works under any review actor,
# including the PR author's own account:
gh api "repos/$REPO/pulls/<PR>/comments" \
  -f body="<finding>" -f commit_id="<H1-sha>" \
  -f path="<changed-file>" -f subject_type=file
# Alternative: a CHANGES_REQUESTED review body — requires the review
# actor to differ from the PR author (GitHub refuses request-changes on
# one's own pull request):
gh pr review <PR> --repo "$REPO" --request-changes --body "<finding>"
```

Only inline review comments and `CHANGES_REQUESTED` review bodies become
bounded occurrences (`review_occurrences`): a `COMMENTED` review body
(`gh pr review --comment`) counts as **zero** findings — do not use it.

Expected: source refresh observes the review; findings enter as bounded
occurrences; a `ReviewRound` seals against the exact target head and the
Execution pauses for judgment (`paused_judgment` — this is also the
Phase-C Attention observation point). A zero-finding round does **not**
satisfy review/fix — record `review/fix-unexercised` honestly rather
than reinterpreting a clean review as success.

### B.7 Judgment and bounded Fix (M-5)

```sh
taisan --db "$DB" work-detail --work w-N   # read version, head, occurrence ids
# decide_judge requires the decision set to cover the sealed round's
# occurrences exactly — repeat --decision once per occurrence id
# (<occ-id>:fix|dismiss|accept|wait[:rationale]); dismiss/accept need a
# :rationale, and an undecided or unknown occurrence is rejected
# invalid_request.
"${TAISAN[@]}" "<run>-judge-h1" judge-findings --work w-N \
  --expected-version <v> --head <H1-sha> \
  --decision <occ-id-1>:fix --decision <occ-id-2>:dismiss:<rationale>
# an accepted judge-findings bumps the Work version — the live accepted
# envelope's `result` is only the CommandEffect, so take <v2> from
# `taisan --db "$DB" command-result --origin cli --replay-key <run>-judge-h1`
# (the recorded decision carries `work_version`) or re-read work-detail;
# reusing <v> is rejected stale_work_version
"${TAISAN[@]}" "<run>-release-h1" release-judgment --work w-N \
  --expected-version <v2> --head <H1-sha>
```

Expected: the Execution requeues `next_role = fix`; the fix account is
charged once; the Fix Invocation launches on the current accepted head
carrying exact round/judgment/finding refs and produces a new artifact +
new produced commit. A stale `--head` or missing occurrence refuses with
a typed code — record a refusal verbatim if observed.

### B.8 Republish — head H2 (M-6)

Expected: a fresh `push_ref` intent for the new produced digest applies
(expected-prior = the freshest observed branch position); the branch and
change request now show **H2**. Record the second `action_id` + receipt
and the remote head read-back.

### B.9 Fresh reassessment to verified Outcome (M-7)

Expected: fresh invariant check and review target bound to H2; the
completion assessment sees exact current-target checks/reviews/lanes;
the Execution reaches `succeeded` (or a recorded human gate) with
`outcome.evidence_refs` frozen — transcribe the outcome block verbatim
into Record §6, including `recorded_seq`. No unresolved writer, gate,
or outgoing action may remain; if `work-detail` shows `waiting`/`ci`
with no outstanding cause, record `unknown`/`unexercised` — never a
claim.

## Phase C — Attention variant (M-9)

The `paused_judgment` gate in B.6 is the guaranteed Attention point —
it must be evidenced, not passed silently.

| # | Command / action | Expected evidence | Record at |
| --- | --- | --- | --- |
| C.1 | `taisan --db "$DB" attention` (and `--work w-N`) at the judgment pause | Evidence-backed item(s): id (work-scoped, versioned), reason `paused_judgment`, `next_action` naming the owed decision — consistent with `work-detail` | Record §4 |
| C.2 | `"${TAISAN[@]}" "<run>-ack-1" acknowledge --work w-N --expected-version <v> --attention <att-id>` | `accepted`; attention listing empties; the Execution **stays `paused`** — acknowledgement is presentation, not resolution | Record §4 |
| C.3 | Resolve the underlying condition via B.7's durable `judge-findings` + `release-judgment` | Attention clears only on resolved evidence — never on timeout | Record §4 |
| C.4 | If the run produces any other Attention condition — the real `attention` reasons beyond the `paused_judgment` gate are `confirmed_failure`, `uncertain_beyond_threshold`, `no_progress`, `progress_unknown` (an unclassifiable progress record — never progress, never death; a capacity deferral surfaces in `taisan capacity`'s `deferred`, not as an Attention reason): record the Attention, then the operator's named decision (`resume`/`cancel`/`retry`/`acknowledge` with `--expected-version`) | The pause's typed reason, the durable command envelope, the post-state; `unexercised` with reason if none arose | Record §4 |

## Phase D — restart/recovery variant (M-8)

Exercise **during** Phase B at a live point (a Worker Invocation in
flight or intents outstanding); alternatively run it on a second
isolated Work and link both records.

| # | Command / action | Expected evidence | Record at |
| --- | --- | --- | --- |
| D.1 | SIGINT/SIGTERM the foreground `taisan run` mid-lifecycle; restart with `taisan --db "$DB" run --interval 15` on the same store | Durable identities survive; dispatch re-attaches by recorded identity; the in-flight Invocation completes **exactly once** (no second writer, no reused out directory) | Record §5 |
| D.2 | `work-detail` + `capacity` + `anomalies` after restart | Unknown liveness/stop/effect outcomes stay `unknown`/`uncertain` with ownership retained until inspected evidence resolves them; no false terminal state | Record §5 |
| D.3 | Duplicate-effect census: `host_action_intents` for the Work + `gh pr list --repo "$REPO" --head "work/w-N"` + remote branch head read-back | Each publish stage `applied` **exactly once** per head; exactly one branch and one change request exist; no duplicate writer/PR/effect | Record §5 |
| D.4 | If a transport failure occurs: observe the bounded retry path | Retries bounded by the Work's durable counter across restart and successors; a definite failure re-issues under backoff; authorization verdicts pause for an operator decision; `unexercised` with reason if none arose | Record §5 |
| D.5 | Preserved partial evidence | A crash/bounded-failure Invocation keeps its artifact state (`missing` recorded, not hidden); WIP preserved on the workspace; nothing re-recorded or rewritten | Record §5 |

Note: the retained 2026-11-23 runs include one recovered-store attempt
that proved internally inconsistent (`store.db.corrupt-*` /
`store.db.recovered`) — a restart-clean store-recovery variant is **not**
yet evidenced. Do not pre-fill a pass; record the variant's actual
outcome honestly (`docs/release-acceptance-v0.3.md` §4).

## What this checklist does not cover

- The live run itself — this document is instruction, not execution.
- Scheduled intake (S-1…S-6) — #271 scope; `[intake] enabled = false`
  for the whole #270 run.
- Merge, deploy, visibility, or credential changes — out of scope by
  authorization and by design.
- Any path other than the production in-process `github` driver —
  `s1-bridge`, fixture Workers, and test harnesses produce
  fixture/contract evidence only and do not qualify a single row here.
