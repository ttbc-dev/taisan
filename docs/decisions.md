# Decisions and open questions

## Working decisions

- Target individuals and small teams, with GitHub as the first production repository host.
- Deliver a self-hosted, single-instance deployment first.
- Keep Work identity and execution authority in the core; interfaces translate commands and project state.
- Require a CLI and CLI-backed agent skills for v0.1 so users can operate through their existing coding agent. Keep direct CLI operation for diagnosis. Skills are planned, not implemented.
- Defer the existing TUI from initial-release requirements without deleting its code or tests. MCP is optional future work. No second independent control interface is a v0.1 gate; GitHub comments remain a candidate optional control adapter.
- Keep machine-readable CLI results, explicit rejected/failed/unknown outcomes, command-result recovery, and installation/invocation guidance in the CLI/skill delivery plan. See [agent interface requirements](agent-interface.md) and issue #47.
- Model one Work to many issues and one Work to many sequential Executions; a resumed Execution may have multiple Invocations.
- Make commands idempotent, version-aware, and auditable.
- Keep planning and prioritization human-led in v0.1.
- Implement the development queue in this repository. Its Kanban-style view is derived from the Work/Execution store; there is no separately synchronized card state.
- Do not require external Kanban system or migrate its historical cards for the initial personal-use deployment.
- Create E1 with accepted `submit`, create a queued E2 with an accepted `retry`, and requeue the same Execution with `resume`. Dispatch reserves capacity only when starting an Invocation request.
- Keep the v0.1 queue in committed enqueue order, dispatching the oldest eligible item so one unavailable source does not block independent work. An ordinary automatic wait retains its Execution capacity slot. A human handoff releases the slot only after writer-stop or write-prevention proof; host-effect uncertainty alone then retains affected-resource reservations, not compute capacity. Uncertain writer ownership retains the slot.
- Enforce write-resource exclusion across Work records and supported entry points. Work-level single-Execution rules alone do not protect shared workspaces or branches; unmanaged writers must not write to managed resources.
- v0.1 writer-resource key: a workspace ID plus `(repository, branch)`, both derived from the Work ID (workspace under a managed root, branch fixed as `work/<work_id>`) so a retried Execution resumes the same workspace and branch. The reservation is held while the Execution is nonterminal — including `paused` — and released in the terminal commit after writer-stop evidence and outstanding-effect reconciliation. Releasing a reservation does not delete the workspace.
- Conflicts are rejected at acceptance where the branch is knowable (`retry`, `claim_resources`); dispatch rechecks uniqueness atomically and leaves a conflicting Execution `queued` with a diagnostic. `submit` cannot conflict because its branch derives from a fresh Work ID.
- Manual writers register external claims on the same reservation store. A claim names `(repository, branch)` only, carries a TTL renewable by the claiming actor, and forfeits exclusion on expiry; expiry is not stop evidence. The managed workspace root is execution-only.
- Persist stop intent before signaling and require process-group/child-process stop proof or an equivalent write fence before releasing ownership.
- Stop proof, verified on this host: snapshot write-capable descendants at stop-intent time (orphans reparent and leave the process tree once the leader exits), re-verify each recorded `pid + start time` before signaling so a reused PID is never signaled, and inspect process state rather than presence — an unreaped zombie still lists but cannot write. The supervisor reaps processes it spawned. A `setsid`-escaped child survives a process-group signal, so the snapshot is mandatory, not optional.
- v0.1 specifies no separate write fence: a same-UID writer can undo permission changes, and a path-reopening writer defeats a workspace rename unless replacements never reuse the path. Instead, a replacement simply does not start while a writer is unproven.
- The name Lease is not adopted: ownership splits across the reservation, the TTL claim, and stop proof, and no single entity carries validity, renewal, and fencing together.
- Bound artifact recovery separately from Invocation/runtime budgets and from process-liveness reconciliation. `execution` performs each durable attempt from the workspace, checkpoints, and the worker-runtime artifact store, only after a confirmed worker exit; exhaustion transitions the Execution to `failed` with an `artifact_recovery_exhausted` code and preserved WIP, never to `uncertain`.
- v0.1 defaults per Execution: `max_invocations` 10 across coding, fix, invariant-check, and code-review Invocations, `max_review_rounds` 5 counting every code-review Invocation (a head-driven re-review also consumes a round), `runtime_limit_seconds` 6 h from first dispatch, artifact recovery 3 attempts / 30 min, uncertain investigation threshold 15 min.
- Acknowledgement is scoped to an Attention version; Attention resurfaces only when the version changes (new evidence, escalation, or a different required decision), never on a timer.
- A dedicated `capacity` Query explains queue stalls: slot holders, held reservations including external claims, and deferred Executions with their diagnostics.
- Slice 0 (core-truth harness): Rust, SQLite store, real fixture worker processes, a fixture GitHub adapter, CLI only. Contract tests covering the crash-recovery conditions are written before the implementation; real GitHub follows the harness. A fixture-backed TUI now exists, but TUI delivery is deferred from v0.1; CLI-backed skills remain required future work.
- v0.1 store model: hybrid — current-state SQLite tables enforce every expressible structural invariant (unique command keys, request/action/observation IDs, one nonterminal Execution per Work and one unresolved writer per Execution via partial unique indexes, a normalized resource-key space, N fixed `capacity_slots` rows, optimistic Work versions), while an append-only `event_log` carries audit and ordering (`EventSequence`). The store never evaluates transition legality, budgets, or gates; `work` does.
- Module delivery is in-process: the store is the durable handoff for approved requests, and `execution` reconciles by scanning on wake and after restart. Wakeups are at-least-once signals, not evidence.
- PR actions re-read the head immediately before writing. A mismatch aborts the write, records `pr_action_result: failed` plus a fresh `pr_head` Observation, and returns judgment to `work`; v0.1 never re-issues an action automatically. Under ADR-001, `push_ref` separately publishes the exact change with an absent-or-exact prior-ref guard and fast-forward requirement. `publish_pr` then creates only the PR after verified push evidence; it has no prior PR head and reconciles by repository, head branch, base, published head, and PR existence. `update_pr` changes metadata only. These target payloads require follow-up migration of the fixture implementation.
- Within an active StoreId, command keys and decisions are retained indefinitely in v0.1 so a lost response remains recoverable. Legacy keys remain inspectable only in the read-only archive; they are not replayed into a fresh store. Each adapter's actor identity comes from the installation config and stays stable across restarts.
- Slice 0 layout: a Cargo workspace whose crates follow the ownership boundaries — `workloop-core` (domain, `work`, `projection`, port traits; I/O-free), `workloop-store` (SQLite), `workloop-exec` (supervisor, POSIX `ProcessControlPort`), `workloop-github` (fixture adapter), `workloop-cli` (binary, composition root), `workloop-fixture-worker` (real fixture process). Interface crates share the Command/Query contracts so neither the existing deferred TUI nor a future optional MCP adapter adds execution authority. Planned skills call the CLI.
- Stage contracts are executor-independent (source-workflow incidents analyzed in the [audit record](source-workflow-audit.md); the invariant is tracked here as #21): a stage command defines its outcome by postconditions that hold in every executor cell, and an executor selects *where* a stage runs, never *what it may skip*. `converge` means bounded fix commits published to the PR head, marked replies posted, and the required draft-to-ready state verified through a reconciled action — the same outcome locally, remotely, or under a future provider.
- Publication ownership (issue #35): [ADR-001](adapter-boundaries.md#adr-001-core-authorizes-publication-github-integration-performs-it) selects Core-authorized `PrActionIntent`s and GitHub integration as the sole remote writer over stage-owned publication. Worker preparation and verification remain bounded Invocations; worker-side outer loops, independent claims, publication, and settlement are disabled in the managed entry point. Partial effects and unknown responses retain their own durable identity and cannot be blindly replayed. GitHub App installation and user-token authentication are integration configuration choices; actions bind actor/credential references, and publication/review may use different identities. Review Workers produce evidence without posting directly. Independent approval requires an eligible identity and cannot silently become a comment. This is a target design, not an implemented real adapter.
- A converge result is a structured record — `{head_before, head_after, pushed_sha, replies_posted[], threads_addressed[]}` (`workloop_core::stage::ConvergeRecord`) — never a free-text verdict, and counts as fixed only when the published head is the produced head (`pushed_sha == head_after`) and the coordinator verifies it against the live PR head (equal to it or an ancestor of it). A push that carried an older head than the fix produced does not publish the fix, even when that older head is the live head. A claimed-but-unpublished fix is a failure with the record preserved as evidence: the source workflow twice produced remote runs that claimed fixes existing only inside execution environments that were then destroyed before publication — such a claim must never classify as success (covered by `claimed_head_without_a_push_is_a_failure_that_preserves_evidence` and `produced_head_not_published_is_a_failure_even_when_the_old_head_is_live` in `crates/workloop-core/tests/stage_contract.rs`). A no-op that produced no new head is `nothing-to-fix`, never a published fix.
- The publication classifier does not verify replies, thread actions, ready state, stop proof, or the full Outcome gate. Core must assemble those independent receipts before full stage success; an ancestor publication match never makes old-head review valid for a newer head.
- The executor × reviewer matrix is orthogonal by construction: reviewer (`devin`/`shadow`/`both`) is never narrowed or defaulted by executor (`local`/`remote`). Unsupported combinations are refused at configuration-validation time (`workloop_core::stage::validate_review_matrix`, table `SUPPORTED_MATRIX_CELLS`); no cell silently degrades the reviewer axis (the source workflow once had a remote lane's shadow review silently no-op because an executor concern — the bot-author event filter — overrode the reviewer dimension; covered by `every_supported_matrix_cell_preserves_the_reviewer_axis` in the same test file).
- Bot-produced work is first-class: adapter event filters that drop bot-authored/bot-sent events exempt lane-produced PRs and heads — the installation's own GitHub App identity and the managed refs it opened — so the lane's own review loop is never starved by its own bot authorship (the silent-reviewer incident above). The exemption is keyed to managed identities, not a blanket "allow all bots".

- Repository-host portability: [ADR-002](repository-host-contract.md) selects one `RepositoryHostPort` with a mandatory semantic baseline and explicit optional capabilities. A conforming adapter meeting the Work's immutable requirements is selectable for new Work through configuration without Core changes. Missing/unknown/denied requirements cannot silently downgrade behavior. Host/repository/event/actor identities are scoped; old Work and unknown effects retain their binding. GitHub remains the v0.1 production target. The current Rust API is not yet this neutral contract; #36 plans caller/store/test migration, the GitLab mapping, and narrow live proof before claiming interchangeability.

## Identity/storage decisions from #50

The [concrete design](identity-storage.md) records maintenance-only cutover with a read-only legacy archive and fresh new-format Work, no legacy runtime/key-replay import, unfinished-Issue overlap rejection for both manual and Selector admission, and renewed approval of a same-Work specification revision when the final pre-dispatch read detects changed Issue content. Core requires and evaluates this read; the host adapter performs it and the CLI loop drives it. That read is the agreed version boundary, not an atomic lock against later remote edits. Reapproval cannot change host/actor/permission binding or reset budgets. Future configured invariant regeneration/auto execution is an extension, not a v0.1 requirement or permission to bypass approval policy. New-format command replay remains authoritative.

## Assessment policy decisions from #51

[Evidence and review gates](evidence-gates.md) records separate Work mechanical checks, optional invariant conformance with default on, independent code-review on/off, and explicitly configured additional GitHub CI. Conformance runs before publication and uses bounded fix/recheck or Attention; code review runs after publication with bounded fix/re-review or Attention. Native Approve, repository-rule import, and automatic code-review merge/draft barriers are excluded. Keep invalid evidence distinct from a valid negative result. Exact immutable finding-set/round guards apply at judgment, release and dependent authorization, including same-head growth. A disabled lane is not a passed assessment. Failure classifications, immutable recovery decisions, Work-wide usage across successor Executions, changed-evidence repair guards, and incident regressions follow [the detailed contracts](evidence-gates.md#failure-classification-and-recovery-decisions) and the #50-approved recovery defaults. Compute capacity and resource reservations remain independent during human or repair waits.

## Worker protocol decisions from #52

The [Worker protocol](worker-protocol.md) records the owner's choices: Claude Code CLI headless behind a taisan-owned shim as the reference Worker, with `resume` declared unsupported in v0.1; mechanical verification run by the supervisor against the handed-off commit, with Worker check results kept as claims; durable handoff as an acknowledged `refs/taisan/artifacts/<artifact_id>` ref in an installation-owned handoff repository with a manifest digest; and isolation by bubblewrap namespaces, environment/credential hygiene, and a mandatory model-API allowlist egress proxy. The owner additionally approved (2026-11-08): a sandboxed `git bundle` as the transient export transport with the handoff ref plus acknowledged store row as the durable body; a verification egress set of installation-default plus Work-declared hosts (denied by default, never model-API hosts, no runtime credentials); and the proposed numeric defaults. All 33 Worker-owned inventory targets are mapped in [worker requirements](worker-requirements.md); planner-phase requirements R16, R286, R288, and R307 are deferred under the approved planner-machinery milestone scope.

## Retention decisions from #54

The [retention policy](retention-policy.md) records the owner's choices (2026-11-08): durable metadata (identity, decisions, commands, judgments, counters, event headers, importer checkpoints) is never reclaimed; reclaimable bodies are worker out directories, workspaces, handoff-repo git objects, and content-addressed CAS objects holding payload/event/verification bodies. Every category has `max_age_seconds` and `max_bytes` — workspaces and out directories default to Work-terminal + 30 days and 20/10 GiB caps, handoff objects and CAS bodies to terminal + 90 days and 40/10 GiB caps, the legacy archive to `unlimited`; `unlimited` is explicit, `0` is a load error, and omitted keys take defaults. Only protective dependencies pin a body — nonterminal Execution/reservation, unacknowledged handoff, unresolved host effect, current gate, retry-eligible workspace, live external claim; historical evidence references never pin and resolve to `unavailable` after reclaim. Cleanup is a bounded periodic sweep in the CLI run loop (3600 s, ≤256 bodies or ≤1 GiB per pass, oldest-first) plus explicit `retention report`/`retention cleanup` commands (dry-run default); physical deletion is runtime tooling driven by store-authoritative state, never Core filesystem I/O. Reclaim is a two-phase `reclaiming`→`reclaimed` protocol, idempotent across crashes; pin creation on a non-`present` body is refused. If pinned bodies alone exceed a byte cap, `protected_over_limit` surfaces through Query and Attention — protected data is retained and admission continues. Delete failures retry per pass and escalate to Attention after three consecutive failures. Retention configuration is installation-wide with no per-Work overrides. All 18 retention-owned inventory targets are mapped in [retention requirements](retention-requirements.md).

## Installation and authentication decisions from #53

The [installation configuration](installation-config.md) records the owner's choices (2026-11-08): one TOML `config.toml` with a required `schema_version`, refused on unknown/newer/malformed content without mutation; credential references resolved only at the adapter boundary through `env:`/`file:`(mode-0600 enforced)/`command:` providers, with secret values never in Core, evidence, argv, logs, intents, or exports; three roles (publication/review/discussion) each binding `(actor, credential_ref)` — one user token for all roles is permitted while a distinct reviewer identity is the recommended configuration; XDG layout (`~/.config/taisan/` for config, `~/.local/share/taisan/` for state); `init` scaffolds only from observed evidence and `check` runs an ordered read-only fail-closed preflight, offline by default with opt-in `--probe`; capability checks repeat at config load, admission, dispatch, and effect boundaries. Same-actor credential renewal is permitted and never retargets existing Work; actor replacement is a binding change applying to new Work only, and unresolved effects always reconcile under their original binding. An unchanged broken configuration cannot create an automatic retry loop — resume requires fresh validated evidence of the failed prerequisite. Source-repo automation mechanisms (webhooks, cron, tunnels, installer convergence) are omitted and their retained obligations re-modelled onto configuration validation and preflight; no new deferrals were created. All 51 installation-owned inventory targets are mapped in [installation requirements](installation-requirements.md).

## Questions to resolve through a spike

1. ~~What execution-ownership mechanism prevents conflicting work in a single-instance deployment, including process crashes and delayed writes? Does it meet the requirements for a Lease?~~ Resolved: resource reservations, TTL external claims, and stop proof (verified on a single host); no Lease name, no separate fence. Remaining: prove host-level enforcement in the vertical slice.
2. Should the first GitHub command surface use issue comments, PR comments, or both? How is a multi-issue Work linked without implying one issue equals one job?
3. Assessment policy is specified in #51; setup defaults are specified in the [installation configuration](installation-config.md); exact runtime/CLI behavior remains #55 work. GitHub merge readiness is not a native Approve gate in automatic Work success.
4. What evidence must be retained to diagnose failures while keeping engagement data isolated and exports safe?
5. Which executor contract is minimal enough for a second executor without diluting checkpoint and recovery semantics?

Resolve these with a vertical slice and contract tests. Avoid introducing a general-purpose plugin framework before two real interfaces exercise the boundary.

## Approved recovery and configuration policy

The owner approved the [recovery and configuration policy](recovery-policy.md), including configurable defaults, durable Work-wide budgets, explicit policy updates, and safe human-wait capacity release. Process uncertainty retains capacity. A stopped worker with an unknown host effect can release compute capacity while the original action and affected-resource reservations remain held. Human release requeues the same Execution and reacquires capacity. This refines older ordinary-wait rules; it is target design, not current runtime behavior.

The [post-v0.1 milestone scope](post-v0.1-milestones.md) records the seven approved machinery deferrals and the safety requirements that remain mandatory in v0.1.
